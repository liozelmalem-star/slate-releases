The Sessions tab shows every AI-CLI session on this machine, live: Claude Code, Codex, Gemini, Cursor and OpenCode. Nothing to install or register — if the capture watcher can see a tool's transcripts, the tracker can see its sessions, including non-default config directories.

Where a tool can answer for itself, Slate asks it. Claude Code lists its own sessions (claude agents --json), so those rows carry the real session id, the process behind it, and whether a background job has finished. The other four are read from their transcripts and the process table. Every row shows the session's name when it has one — see Naming a session.

A session's sub-agents are not sessions. A CLI running sub-agents writes a transcript per helper, and none of those is a conversation you are having. They are kept out of the list as rows, and shown instead as children of the session running them: the row says how many are live beneath it and expands to name them, and each is a pip in a corona around its session on the map. Nothing offers to stop a sub-agent — it runs inside its parent's process, so there is nothing separate to stop. Only recently active sub-agents are listed, because a session open all day keeps every transcript it ever wrote.

What you see

The list is live sessions, on the whole Mac. A session that ends leaves it, and folds into Just finished and Earlier today, described further down. Each live session carries one of three states:

  • Needs you — the AI tool finished a turn (an answer, a question, or a permission prompt) and is blocked on you. ⌘⇧J takes you to the one that has waited longest, and again to the next. The count sits in this tab's header. When a session starts waiting and Slate is not the window in front, macOS shows one notification with its question — once per wait, never for what was already waiting when Slate opened. Tell me when a session needs me in Connect → Automations turns it off.
  • Working — the transcript is being written right now.
  • Idle — quiet, and you spoke last.

Branches waiting for review

A worktree branch whose agent has finished, with commits main does not have, is waiting for you. Slate finds these in every repository it knows. A worktree with a session still working in it is not waiting; one whose session is waiting or idle is, because its turn ended.

Each one is tagged on its own row in the list, under its project, beside its branch. The tag reads Review · n files ›, then behind n in amber when main has moved past the branch, then how long it has waited. The row is drawn even when nothing runs in that repository: it is the same checked out, nothing running row, with the tag in place of that sentence. When the branch still has a session in it, the tag sits under that session's row. When a project holds more than one repository, the row names the repository before the branch, as in editor · feat-x.

Click the tag to open the branch's review (see Reviewing the whole branch). Review & merge is also the first item in the row's ⋯ menu. Clicking the row itself does what it did before. The header counts the waiting branches as n to review, beside the working count; clicking it opens the branch that has waited longest. Above the review sit three actions:

  • Merge into main fast-forwards main to the branch, then removes the worktree (its project's On remove command runs first) and deletes the branch. It never makes a merge commit and never checks a branch out. When no checkout holds main, only the ref moves. When one does, that checkout moves with it, and the merge is refused if it has uncommitted changes to any file the merge would change. It is also refused while the worktree has uncommitted work, because removing the worktree would lose it.
  • A branch is measured against origin/main as well as the local main, because worktrees start from origin/main and the local one is often behind it. Commits either one holds are not the branch's work.
  • When either main has moved past the branch, the tag says behind n and the review offers Ask to rebase instead of Merge. It pastes Rebase this branch on main and run the tests again. at that session's prompt and does not press Enter. With no session in Slate there, the request is copied instead.
  • Keep leaves the branch where it is and turns its tag into a grey Kept, out of the count. Kept is remembered on this Mac only. If the agent adds commits to a kept branch, it is waiting again.
  • Discard first shows, in the page, every commit that is on no other branch and will be lost, and whether uncommitted work goes too. Confirming deletes the worktree and the branch.

After each action the next branch waiting opens, oldest first. Merge and Discard are refused while an agent is working in the worktree, and when the branch has new commits since the review you are reading was drawn: what is merged or deleted is only ever what you saw. Merge stays greyed out until the review has loaded. The repository's main branch itself is never merged or discarded from here.

Narrowing to a workspace or a project

The head of the list holds a workspace picker, on All workspaces — the whole Mac — whenever the tab opens. Pick one workspace and only its sessions stay, in the list and on the map; a session no workspace claims counts as Personal's. A project picker then appears below it, on All projects, listing that workspace's projects, even when the window is in another one. Picking a project keeps the sessions that run in it or in its repos and branches. Changing the workspace drops the project, and the header and an empty map name what you narrowed to. The choice lasts while the window is open and is back on All workspaces after a relaunch, like every other project picker.

Just finished and Earlier today follow the pickers too. Opening one of their pages, or All past sessions, from a workspace the window is not in switches the window to that workspace first, because a page belongs to one workspace only.

The map and the list

Two views of one list, side by side. The map shows the shape of the machine; the rail beside it reads it out. Hovering either lights up the other, and pointing at a project or a branch lights every row under it.

The map is a radial tree of your groups and projects. This machine is at the centre, and the tree grows outward along the spine the workspace uses everywhere else: group → project → branch → session — a project standing on its own sits on the first ring, and a project inside a group is one ring further out. Each level is a ring, so three limbs off main is three agents at a glance. A session with no project and no branch hangs from a Not in a project limb. When more than one workspace has work running, a workspace ring sits inside the group ring.

Every level divides its parent's angle in proportion to the sessions beneath it, so a group running six sessions is visibly wider than one running one. Colour says which workspace the work is in: every limb, node and name takes the colour you gave that workspace in the switcher, so the wheel and the rail's workspace badge agree, and a session no workspace claims stays colourless. This is the only view in the app that lists every workspace at once, which is why a hue is spent on that question here rather than on which group — two groups in one workspace share a colour, and their names are what tell them apart. Status is the halo around each dot, and a node wears the most urgent state anywhere beneath it.

Names sit horizontally beside their node, on a small chip. A branch keeps the start of its name, cut at fifteen characters (fix/sessions-gr…); point at it and it says the whole thing. A ring too crowded to hold a name sideways writes it along the ray instead, and one too crowded even for that drops the name — the rail still lists it.

Moving around the map. The map holds still: it always fits the panel, and there is no zoom, pan or scroll. Click a place node to go into it: the map is redrawn with that node at the centre, the rail narrows to the sessions inside it, and a crumb trail names where you are. Any crumb jumps to that level. All, a click on empty space, or Escape returns to the whole machine. Drag a node to re-order it among its siblings; only the order is kept, it survives a restart, and Reset layout puts it back.

Below about 1024px the map is dropped rather than squeezed — it needs roughly 500px before its rings separate — and the rail leads. It shows nothing the rail does not.

The rail has two levels: the group or project, then its sessions. Each row names its own branch on its first line — and its project too, when the group holds more than one — so the project and the branch need no heading of their own. That is the rail's only shape. A session waiting on you sits in its group or project like every other one, wearing the amber dot that says so — it is not lifted into a list of its own, because a row there could not say which group or project it belonged to. Every level is ordered by urgency before name: the group or project with the most blocked sessions leads, then the busiest, and two that tie go to the one whose session has waited longest. Inside one, blocked comes before working comes before idle, and the blocked are longest-waiting first. A session groups under the group or project the workspace files its folder under, even when you never declared that folder as a project. A session in a git repo that no project holds yet groups under the repo's name: Slate makes that repo a project the first time it records the session (see below). Anything else — a plain folder, your home folder, or no folder at all — groups under Not in a project, the page where Slate files that work.

When two workspaces have work running, each heading names its own — Work / Beacon — because this is the only screen in the app that lists every workspace at once, and the rail's switcher can only show one. With one workspace running there is nothing to tell apart and the heading says just the group or project.

Under its heading, a row is three lines, and the middle one is the one that moves. On top, what the session was asked to do — its opening prompt, cut to the line with the rest in the tooltip. Underneath, what it is doing right now: the question when it is waiting on you, what it just said it was doing when it is working, and the next unticked item from its page's plan when it has gone quiet with work still on it. The last line is quiet marks — the tool's, how long ago the session moved, how full its context window is, and how far the plan has got (0/4, which says what it counts when you point at it).

How full the context is comes from the session's own transcript, on its latest turn. A Codex session states its window, so it shows a small bar and 8% of 258k, turning amber past 75%. A Claude Code session does not state its window — the same model runs on two sizes — so it shows the count alone, 323k. Gemini, OpenCode and Cursor record nothing per turn, and their rows show nothing. The same mark sits on the session's tab, beside the lines its checkout changed (+318 −5).

An ask is the only one of the three the row emphasises: it is the one that wants something back from you.

Pointing at a row shows two controls: ⋯ and Stop. The ⋯ menu starts with the session's own two acts, each with a line saying what it will do:

  • Open beside puts the session next to the one you are in — see Two sessions side by side. ⌘-click on the row does the same.
  • Open PR opens the pull-request sheet — see Opening a pull request. With no commits ahead of the trunk it is greyed out and says why: On main: nothing to compare, No commits ahead of main, or Nothing committed yet (10 files changed). Once origin has a pull request for the branch, it reads PR #118 and opens it in your browser.

Below a rule it lists everything else the row offers — New session, Chat, Branch changes, Run preview, Second agent, and on a Claude Code row Copy resume, which copies its claude --resume <id> command. On a branch waiting for review, Review & merge comes first and takes the place of Branch changes, which opens the same view. A row whose branch has a pull request shows its number on the branch line (#118). A session that did real work and recorded no memory carries a small owed pill. A prompt written in Hebrew or Arabic is laid out right to left.

A row says what its checkout holds: the lines it adds and removes against where it left its base, committed and uncommitted together (+318 −5, untracked files not counted), how many commits it has that its base does not (↑3), how far the base has moved on without it (↓1), an amber dot when there is uncommitted work, and missing for a worktree git lists but cannot read. A branch that is clean and level with its base says nothing. A checkout with nothing running in it is listed too, saying checked out, nothing running, and wears the same badge.

A session is listed where its edits land. An agent started in one checkout can edit another worktree of the same repository by its full path, and its terminal never leaves the folder it started in. Slate lists it under the worktree its most recent edit went to, with that worktree's branch. Until it edits anything, it is listed under the folder it started in. An edit outside the repository, such as a scratch file, does not move it. Its row adds from <folder>, naming the folder it started in, which is where its terminal is.

The same rule decides the branch Slate briefs a session on, the branch its end-of-turn line names ("saved 3 memories · <branch>"), and the page its session and memories are filed under.

Park hides a checkout like that from the rail without deleting anything. Point at checked out, nothing running and click Park; the checkout folds into one Parked · n line at the end of its project, which opens to list them with Unpark beside each. A checkout that has a session running in it is never hidden, parked or not, and neither is a branch waiting for review, which offers no Park. Which checkouts are parked is remembered on this machine only.

Pointing at a row offers to open what its branch changed — the whole review, below — beside the + that starts a session there. It needs no session running: a branch outlives every session that worked on it.

Just finished sits at the foot of the rail for ten minutes, dim. Each row carries its tool's mark and when it ended, the same way a live row does, and opens the page the work belongs to.

Below it, Earlier today in \<workspace> folds every other session from today (the picked workspace or project, or the window's own on All workspaces), collapsed by default with its count on the fold; it leaves out whatever Just finished is already showing, and every session still running, so nothing is listed twice. "Today" is your local day. All past sessions in \<workspace> → opens the workspace's whole history, newest first, at /sessions?past=1, with no time limit.

Every row's own mark says where it runs: a terminal glyph for a session Slate is running, which you can type straight into, and an eye for one running in your own terminal, which Slate only follows along.

With nothing selected, the pane shows the map of every live session. The header counts what needs you, and ⌘⇧J walks the waiting sessions longest-waiting first — the same order the rail keeps inside each branch.

The rail lives in the app's own left pane, so it resizes by dragging the pane's edge, and ⌘\\ hides it when a terminal wants the whole width.

The keyboard

Tab reaches the rail's rows and Enter opens one. ↑/↓ or j/k move between them, Home and End jump to either end, and Escape hands focus back so the terminal can have it. Movement stops at the ends rather than wrapping. On the focused row, f starts a second agent in its folder and s stops it — s twice, and the arm expires on its own after four seconds.

Those letters belong to the list, not to the app: a global binding for j would fire while a terminal has focus, which in this tab is most of the time. They act only once focus is already inside the rail, and any modified chord (⌘⇧J, ⌘K) passes straight through. ⌘K's Focus the sessions list is the way in from anywhere.

Starting a session

Where you are looking is where it starts. Point at a group, project or branch — a node on the map, a heading or a row in the rail — and a + appears beside it: New session here. It starts a session there at once, on the tool it names as its default, under its account, and opens it in Slate. There is no picker, because the spot was already chosen by being pointed at. A project carries a second control, New worktree, which opens the worktree form with that project already chosen; in the rail it sits on the group heading when the group has one project, and on each row when it has several. A group or project with nothing to run in shows no control at all, and a refusal from the launch itself is shown on the tab in its own words.

New session, at the head of the list in the left pane, is for the group or project you have not looked at yet, and for choosing a different tool. It shows where a session can run as a tree — group → project → branch, with a workspace level above it when more than one workspace has work — and clicking a row starts one there. A row that carries its own folder shows it, because a name alone hides a wrong checkout. A git project's last row is New worktree…; a plain folder has no branches to make one from, so it is not offered there.

A session runs as the workspace its place belongs to, whichever workspace the window is showing. Sessions lists every workspace, so a work project picked while Personal is on screen starts on the work workspace's tools and account, and so does a worktree made of it. A refused start is shown at the top of the picker, and every start, refusal and failure is written to slate.log.

Start without a project, at the bottom of the picker, starts a session that belongs to no project, for a question, a plan or a quick script. It runs in a folder Slate keeps for the workspace you are in, inside Slate's own data folder, so the session never sees your home folder or a repo. What it records is filed in that workspace, and on the rail it groups under Not in a project.

Open folder… starts a session in any folder you pick, and Recent folders lists the last few folders your sessions ran in that no project holds yet. A folder another workspace already holds opens there, and the session runs as that workspace. Otherwise a folder opened either way becomes a project in the workspace on screen, by the same rules as the workspace menu's New project, onboarding, and a session row's Make a project:

  • A worktree or a subfolder of a repo stands for the repo.
  • A folder Slate already knows opens its page. A page in the Trash comes back.
  • A folder inside a group becomes a project in that group.
  • A plain folder that holds two or more repos asks first: Add as a group, Add as one project, or Not now.
  • Anything else becomes a project on its own.

Your home folder and the disk root are refused: every session on the computer would file under them. Recent folders leaves out temporary folders (/tmp included, where agents keep their scratchpads), the AI tools' own folders and Slate's data folder. When a folder becomes a project, the sessions that ran in it move out of Not in a project into it.

A repo you work in becomes a project by itself

You do not have to add a repo before working in it. The first time Slate records a session — from any of the five tools, or from its own terminal — in a git repo that no project holds, it makes the repo a project and files the session there. A worktree counts as its repo. The project goes to the workspace whose projects already come from the same owner on the repo's git host (a new clone from your company's organisation lands in your work workspace); otherwise it goes to Personal.

Slate never does this for your home folder, a temporary folder, an AI tool's own folder, Slate's data folder, a folder that is not a git repo, or a project you put in the Trash. A removed project stays removed: a session there, or its group finding the repo again, does not bring it back. Restoring the page or adding the folder yourself does.

What is left in Not in a project is work in plain folders. A row there offers Make a project behind its ⋯, which adds the session's folder by the rules above and moves the session into it. With more than one workspace, the menu names each one — Make a project in Work — with the session's own workspace first. A folder no workspace claims is filed in Personal until then, so its sessions are private by default, and they move into whichever workspace you pick.

Runs on is asked once, above the tree. It lists the AI tools connected in Connect → AI tools by the workspace in focus — the place the picker opened on, or the repo a worktree is being made in — and names that workspace when more than one has work. It starts on that workspace's default. Picking another tool changes this session only, not the default. The same control shows on the worktree form. Groups and projects with no linked folder are not offered. The button works while the tab is still scanning.

A chat instead of a terminal

Beside + on a group heading and on a node of the map, and in a row's ⋯ menu, there is also Chat. It starts the AI tool of that group or project in it, the way + does, but draws it the way Home does: each turn, each tool step as it runs, and an approval card wherever the AI tool needs your yes. The terminal would print a prompt there instead. A row's chat works in that row's own checkout, so a chat started on a worktree's row edits the worktree, not the project's main folder. The chat opens as a tab in the strip, named after the group or project, and its composer shows the folder where the scope picker would be, because the folder was fixed when it started.

The chat's AI tool is its own. It does not share Home's warm AI tool, so chatting in a worktree never restarts Home's conversation or its tool connections. The chat lasts as long as its tab: Close and end this chat stops its AI tool, and so does quitting Slate. Nothing records the chat as a session in the list. Use a terminal session for work you want to leave running or pick up later.

Cloud tasks

A cloud task runs on your AI tool's computer instead of this one, so it keeps going when your Mac sleeps. Claude Code and Codex have them. Gemini and OpenCode have none, and Cursor's command for them is not out yet (AI tool features).

Start one from New session → Cloud. Write the task, pick a project, and press Start in cloud. Only projects that are git repositories are offered, because the task works on a copy of the repository. Before anything leaves, the form says what will:

  • Claude clones the project's GitHub remote at its current branch, so push first. A project with no GitHub remote is uploaded instead — its history and uncommitted changes to tracked files, not untracked ones.
  • Codex runs in an environment you set up for the repository at chatgpt.com/codex, on its GitHub repository at your current branch. Type the environment's name; the names your Codex tasks have used are offered, and the last one used from a project is filled in next time.

The task runs under the project's account, and Slate asks that account's CLI whether it can start one before you can press Start. Claude needs a claude.ai sign-in: an account that uses an API key, a token, Bedrock or Vertex cannot, and the form says so. Codex needs a ChatGPT sign-in; one that has expired is told to run codex login.

Find it in the Sessions list, under the project it was started from, with a cloud where a session's status dot sits. A Codex row says where the task stands — working, ready, applied or failed — because Codex keeps a list Slate can ask, about once a minute while Sessions is open. Claude keeps no list, so a Claude row says its status is on claude.ai.

Its page shows what you asked and every message you sent it, and only the controls the tool really has:

ClaudeCodex
Send a follow-upyes — queued, answered on claude.aino
Show diffnoyes, read-only
Bring it backBring back — the task opens in a new worktree with its whole conversation, as a normal session on this MacApply in a worktree — its changes land, uncommitted, in a new worktree, and the branch's changes open

Neither tool offers Stop, and the page says so rather than showing a button that would do nothing.

When a task is deleted on the tool's site. Codex says so when Slate asks, and the task leaves the list. Claude says so only when Slate next sends the task something: the first Send to a task deleted or archived on claude.ai drops it, with a sentence saying why. Slate does not probe Claude on its own, because the only way to ask is to send a message, and a task that still exists would receive it. Forget in Slate removes one at any time.

Slate keeps its own record of the cloud tasks it started, because Claude offers no command that lists them. A task started on the web or the phone is not in that record.

What Slate remembers. A Claude task brought back writes its whole conversation into a normal transcript as soon as you send it a message, and Slate captures it like any session; one brought back and never used leaves no transcript. A Codex task brings back changes, not a conversation, so applying it notes the task on its project's page with what changed. While either runs in the cloud it has none of Slate's hooks and cannot reach Slate's memory, so what it decides there arrives as a record, not as saved memories. Why Slate drives cloud tasks only through each tool's own CLI is ADR 0071.

On your phone

A session can keep going from your phone while it runs on this Mac. Slate has no phone app of its own: you pick the session up in your AI tool's app. Today that is Claude Code, in the Claude app (the Code tab) or at claude.ai/code.

Start one on the phone by turning on Also on my phone in New session, under the places. Put a running session on the phone with Continue on phone at the top of its page. Either way, a card opens with three steps and the session's claude.ai link, with Copy and Open. On your phone at the top of the page opens that card again; Stop phone access in it turns it off.

A session on the phone shows a phone mark in the Sessions list, and the Sessions header counts them. Slate reads this from the session's own transcript, so it also shows a session you put on the phone yourself by typing /remote-control in your own terminal.

The control is on every session, and it is greyed out where it cannot work, with a line that says why:

It still runs here. The session keeps running on this Mac, so Slate's hooks, memory and capture work as they always do. While it is on, the conversation also goes through Anthropic, which keeps it. Why Slate does it this way is ADR 0072.

Worktrees

The worktree form asks for a Branch and a From branch to base it on (local branches only — nothing is fetched), and shows the Folder it will make, always a sibling of the repository. Then it starts a session inside it.

Carry over is what makes the new folder usable. git worktree add copies tracked files only, so a fresh worktree has no dependency tree, no .env and no build output. The form reads what the repository ignores at its top level and offers those as chips, so you tick node_modules and skip .DS_Store rather than typing paths. On a Mac each folder is cloned in one step, copy-on-write: it costs no disk until a file changes, and a change in the new folder never reaches the original. Elsewhere it is hard-linked file by file. Nothing carried is tracked. A dependency folder of 595,483 files takes about 30 seconds cloned (two and a half minutes linked), and the form says what it is carrying while Slate stays usable. If a path cannot be carried, nothing half-made is left behind: the form says which path is missing and offers Start anyway instead of starting a session that cannot build.

Then run is one command, run inside the new folder once the files are there — a build step, a codegen pass, a submodule fetch. Empty is the normal answer.

On remove is the other end: one command run inside the folder just before a worktree is removed, however it is removed — by hand, or because its session ended. Use it to stop a dev server, drop a local database or free a port. If it fails, the worktree is kept and the error shows what it printed.

Each worktree Slate makes has a port of its own. When the worktree is made, Slate picks a free port from 4100 to 4999 — one no other Slate worktree holds and nothing on the computer is listening on — and keeps it until the worktree is removed. It is the environment variable SLATE_PORT in Then run, in On remove and in every session terminal started in that folder or inside it, so two worktrees of one repo can each run vite --port $SLATE_PORT without fighting over the same port. The port shows on the worktree's row as :4101. A worktree you made by hand has none. The port is stored on this computer only, and is freed when the worktree is removed; a removal that is refused keeps it.

Run preview is the command that starts a checkout's dev server — yarn dev, say. Set it in the same form, or in the Settings of the group or project; it is stored there. A session's row in the rail then offers Run preview in its ⋯ menu: it opens the command's terminal beside the session, so a command that fails says why, and as soon as the server prints a local address (http://localhost:5173) that address opens as a Preview tab in the same strip. The preview can reload, open in your browser, or Stop, which ends the server's terminal and closes the tab. A preview also closes on its own when its terminal ends. A group or project with no Run preview command says so instead of starting anything.

Pick (the crosshair) turns the preview into a picker: point at anything on the page and it is outlined, click it and its description is pasted at the prompt of the session working in that folder — the page it is on, a CSS selector for it, its size and position, the styles that decide how it looks, and its HTML. Nothing is submitted; you add what should change and press Enter in the session. There is no screenshot: the preview comes from a different origin than the app, and the app is not allowed to read its pixels. To pick, the page is framed through a small proxy Slate runs on a loopback port of its own, which forwards everything to your dev server and adds one script. It answers only requests addressed to its own loopback address, so a web page cannot use it to reach your dev server; only a dev server on this machine can be proxied, and hot reload keeps working through it. Click the crosshair again to go back to the plain preview.

Both are remembered on the group or project, so every later worktree of every project in it is provisioned without asking.

A worktree made for a session ends with it. When the session you started in a new worktree ends — you exit the tool, or press Stop — Slate removes the worktree. Closing the session's tab is not an end: the session keeps running. What happens depends on what the worktree still holds:

  • Nothing uncommitted, branch merged or empty — the folder and the branch both go, and a strip at the top says so.
  • Commits that are not merged — the folder goes and the branch stays, so the commits are still there to merge.
  • Uncommitted changes — Slate asks once: Keep worktree or Delete anyway.

It waits while any other session is still working inside the folder, and it never touches a worktree it did not make for a session: one you made by hand, one another tool made, or one whose session was still running when you quit Slate. The folder leaves at once and its contents are deleted in the background, so a worktree with a large dependency tree does not hold anything up.

Removing a worktree by hand is offered on a branch row in New session, under the trash icon. It refuses a checkout that still holds uncommitted work unless you say to discard it, and it can delete the branch as well. That is why a dirty branch is marked before the click rather than after, and why a worktree git cannot read says missing rather than nothing — an undecorated row reads as clean, and clean reads as safe to remove.

Starting a session from a page

A branch, project or group page carries a Start session button in its header. It runs the tool that page's group, or project on its own, connected, in the folder the page stands for, under the account that group or project assigns to that tool, and opens it inside Slate. Beside it, any page with a folder carries a button for a plain terminal.

If the page has a Goal, that line is seeded into the CLI's prompt together with the next unchecked item of its plan (Continue on feat/x: … — next: …). It is typed, never sent: you read it, edit it, and press Enter yourself. It is always one line, because a newline in a terminal prompt is a send.

Whether it arrived is checked rather than assumed. Slate watches the session's own output for the line it sent. When a CLI's startup repaint swallowed it, the terminal says so and offers the line back to Insert it or copy.

When a session cannot start, the refusal names what to do: "Acme does not use gemini. Sessions under /code/acme use: claude. Add it in Connect → AI tools to allow it here." A page with no folder is refused the same way.

A page also shows what is running on it. Sessions working towards a page appear in its header as needs you, working or idle, and clicking one opens that session. Starting a second session on a branch that already has one working is the mistake this removes.

The terminal

A session Slate hosts runs on a real pseudo-terminal the app owns, so the CLI behaves exactly as it does in Terminal.app — colours, spinners, the full TUI. It is the same CLI running its own tool loop under its own limits; Slate supplies the folder, the account and the context, and stays out of the conversation. It is captured like any other session, so the watcher, your memory and this tab treat a hosted session and a terminal session identically.

Terminal | Conversation, above the session, switches what the stage shows. Conversation is the session read from its transcript — each message formatted, each tool step as it runs — with a prompt under it: Enter there is Enter at the terminal's prompt, and Shift+Enter is a new line. / lists the skills the session's tool loads in its folder, and @ names a page, session, memory, task, routine or report, whose content is sent in front of your words — the same as Home. The terminal keeps running underneath, so switching back loses nothing. Menus and permission dialogs the tool draws itself only show in Terminal. When the session is waiting and its newest step is a call with no result yet, a bar above the prompt names the call, says the tool may be asking you to allow it, and Open Terminal switches the stage there. Steps leaves the rail while the conversation is the stage, since it would show the same thing twice. Every session opens on Terminal, the tool itself; a pick of Conversation holds for that session only. A plain shell has no conversation and no switch.

Slate starts a Claude session as a background job (claude --bg, which begins idle and spends no turn) and opens a view onto it. That session belongs to no terminal, so you can pick it up in Slate, in any terminal, or after Slate has quit. A tool with no such mode is started the ordinary way.

The CLI is told where it is: TERM_PROGRAM=Slate, the app's version, and SLATE_TERMINAL_ID. It is opened at the size the pane will give it, so a CLI does not lay its interface out twice.

Navigating away does not end a session — the process belongs to the app, not to the view — and coming back replays what it said while you were gone. A session drawing a full-screen interface is asked to paint itself again instead. Reloading the app loses none of it.

The terminal gets the window. A session's tab draws no page chrome: the tab strip is the top edge, the session's own rail is the right edge, and everything between is the agent's screen, down to its last row.

The session rail is a column of icons down the right edge, the same kind as the app's rail on the left, and it works the same way: an icon opens its pane beside the terminal, and clicking the open one hides the pane so the terminal has the width. The rail itself never hides. Each icon has its name under it — Session, Steps, Changes, Turns, About — and Changes and Turns carry a count: files the branch changed, and checkpoints. The Session icon wears the session's state as a dot, amber when it is waiting on you, so it reads with the pane shut. The pane you last chose is the one a session opens on, and its width is remembered. The map icon at the foot goes back to the map.

The Session pane answers, top to bottom, what a glance at an agent needs:

  • Does it need you, and since when. Its state — Working, Needs you, Idle — and how long it has been that way. Waiting on you is the only state drawn as a filled block.
  • What it said. Once it has stopped — waiting on you or done — its whole latest message, formatted, and replaced by the next one as soon as it arrives. A long report scrolls inside the box. While it works: one line of what it says it is doing, else its window title or the next item of its plan. There is no input here: the terminal beside the inspector is the prompt.
  • One action, chosen by the state. Stopped with changes: **Review n files, which opens the branch review. Working: none — beside it are Review so far and your editor. Stopped: Open PR beside it, which opens the pull-request sheet — greyed out with the reason when the branch has no commits ahead, and PR #118 once origin has one. Everything else is in ⋯, each with a line saying what it will do: ask for a review (typed at its prompt, never sent), open the folder in VS Code or Cursor, its page, fork, hand back to your terminal, repaint. Stop** is last, in red, and stops only on a second click.
  • How far along. Its plan as a bar — the one the agent keeps, like Claude Code's todo list, else the branch page's — with the next item.
  • What it changed and how full it is. The branch's files and lines, how full its context is, and its checkpoints; each opens its own pane.
  • What memory did. How many of Slate's memories the session was handed, how many it used and how many it wrote — "Memory 59 handed · 6 used · 16 written". Click it to open Memory with exactly those memories lit on the graph.
  • The last three steps, with All steps opening the Steps pane.
  • At the foot, its tool, its branch, and how many other agents are on that branch.

Focus mode — ⌘⇧M. The top bar, the rail and the sidebar go, and the window is one agent and its rail. An Exit focus button stays in the corner, and the same chord brings everything back. It is not remembered between launches.

What else the terminal does:

  • It follows your theme, including any retint from Settings → Appearance, while the session keeps running.
  • ⌘F searches the session, scrollback included.
  • ⌘C copies the selection, ⌘V pastes, ⌘+/− zooms and ⌘0 resets the size, which is remembered. Ctrl-C still interrupts the process: on macOS the app's shortcuts live on ⌘, which no terminal uses. Every other app chord (⌘K, ⌘P, ⌘W) reaches the app rather than the CLI.
  • Shift+Enter adds a line instead of sending one, which a browser terminal does not do on its own.
  • Option is Meta. ⌥← and ⌥→ jump a word, ⌥⌫ deletes one.
  • The mouse behaves. Selecting text copies it (a switch in Settings → Terminal), the middle button pastes, and right-click opens Copy, Paste, Select all, Clear (⌥⌘K) and **Remember on page**. ⌘K stays the command palette.
  • Scrolling up is safe. Output keeps arriving, and a Newest output pill brings you back. Past the scrollback limit the terminal prints earlier output is no longer kept rather than looking like a session that began there.
  • Links look like links. A local server's address (http://localhost:5173) opens in Slate's own browser, as a tab beside the session; any other URL opens in your browser; a printed slate://page/<id> opens that page as a tab beside the session; a printed path such as src/x.ts:42 opens that file at that line, resolved against where the session is running.
  • It is your terminal. Settings → Terminal sets the font, its size and line height, the cursor's shape and blink, copy-on-select, and how much scrollback to keep (5,000 lines by default). Changes reach a session already on screen. Colours are not there — the terminal follows the app's theme.
  • A selection can be remembered. Select the sentence worth keeping and Remember files it as an atom under the page this session belongs to. Nothing is captured automatically.

The timeline. The Steps pane shows what the session did, in order: each prompt you typed, what the agent said, and every tool it ran, with its target on one line — the file, the command, the search. Click a step to see what it printed; an edit opens onto the lines it changed, drawn the same way as the branch review. A failed step says failed. When the agent keeps a plan — Claude Code's todo list, Codex's plan — it sits at the top, with how many items are done. The last 60 turns are shown, and a step's output is cut at 4,000 characters; the terminal has the rest.

Claude Code and Codex record every tool call in their transcripts. Gemini, Cursor and OpenCode record only what was said, so their timelines show the conversation and say that the tool calls are in the terminal.

What the session recorded. The About pane carries what the branch is for — its page, its goal and the documents under it — and Recorded: the memory atoms this session filed, and whether it wrote them on its own or after Slate asked. It carries no commits, because joining commits to a session means intersecting a time window with a repo, which counts a concurrent agent's work as this one's. A session nobody has judged yet stays silent rather than reporting "nothing recorded".

What the session was given. Above it, Given lists the memories Slate handed the session, each once: At start for the ones the session brief carried, On your prompts for the ones that arrived with a prompt. A green dot means the session used the memory (its replies repeated the memory's rare words), an outline means it did not, and a dashed outline means the session has not been judged yet, which happens after it ends. Five rows show per group, then a count. Click a row to open Memory. A session that was given nothing shows no Given section.

Several sessions at once

A session you open is a tab, in the same strip as your pages, in every world. Its status sits where a page's icon would be, and beside its name are the lines its checkout changed and how full its context is. A file you opened, a branch's changes and a preview are tabs in the same strip, with the file's own icon, a branch glyph or a terminal glyph. Every open tab stays mounted, so switching between sessions tears no terminal down.

While a session's tab is showing, the rail stays on Sessions and the list stays in the pane beside it. Clicking a row opens its session as a temporary tab in italics, which the next click replaces; a session you launch always gets a kept tab. The tab gestures and keys are the ones every tab has — see Tabs.

Closing a session's tab ends the session, after asking — the way an editor asks before closing a terminal tab whose process is still running. The ×, a middle-click and ⌘W all ask End qa?, naming the tool still running in it. End session stops the tool and closes its terminal, and the session leaves the rail; Cancel keeps the tab. Close others, Close to the right and Close all ask once, listing every session they would end. If a stop is refused, the dialog stays open with the reason. A session in your own terminal is not Slate's to end: closing its view leaves it running there. A session replaced in a temporary tab keeps running too, labelled In Slate · no window — clicking that row brings its tab back. When you close one, the session tab beside it takes its place. With none left, you land on the map. Escape, or the back arrow on a transcript, also returns to the map without closing anything. Clicking Sessions in the rail brings back the session tab you were last on.

A session beside its plan. ⌘-click any tab to open it in a second pane: two sessions, or a session and the page it is working from. Two panes, never a grid.

Two sessions side by side

Open beside in a session row's ⋯, or ⌘-click on the row, shows that session next to the one you are in. From one pane it splits the stage in two. From a split it adds a tab to the half you are not working in, so there are never more than two.

  • The half you are working in has a blue line on top. Click anywhere in the other half to work there. The session list marks the two sessions on screen left and right, and highlights the one in the focused half.
  • A session opened in a split starts with its inspector closed, so each terminal keeps half the window. Open it from the session's rail as usual; once you go back to one pane, the inspector is as you last left it there.
  • Back to one pane: Unsplit at the top of the right half, or ⇧⌘\. The session in the focused half stays on screen, and every tab is kept. Closing the last tab of a half also ends the split.

Opening a pull request

Open PR — in a session row's ⋯, in the Session pane, and above the Changes tree — opens one sheet:

  • From and to: the branch, the trunk it goes into, and the repository on its site (github.com/acme/nimbus).
  • Title: the first commit's subject. Edit it freely.
  • Description: the commits, oldest first, then the size of the change (31 files changed, +469 −108). Edit it freely.

Push and open GitHub runs git push -u origin <branch> in the checkout, with your own git and SSH key. Slate never uses gh and needs no token. Then it opens the site's compare page in your browser with the title and description filled in, and you press Create pull request there. GitHub, GitLab and Bitbucket are recognised from the origin remote; any other host is treated as GitHub (GitHub Enterprise). Bitbucket's form takes no title or description from the link. If the push is refused, the sheet stays open with git's own lines. If the browser cannot be opened after the push, the sheet stays open with the compare link to click or copy.

The PR number appears on its own. Slate reads refs/pull/* on origin — GitHub publishes one for every pull request — and puts #118 on the session's row once one points at the branch's tip. It asks once a minute, and every 30 seconds for five minutes after a push, while you are creating it. The trunk never shows one.

The sheet refuses, with the reason, on the trunk, with no commits ahead of it, on a detached HEAD, or with no origin remote. Uncommitted work is not pushed: commit it first.

Naming a session

A session has one name, and its tab, its row in the list and its memory page all show it. Right-click a session's tab and choose Rename…: the name becomes a field in the tab. Enter or clicking away keeps it, and Escape leaves the old one. A name is one line of up to 80 characters.

A session with no name of its own, or one that reads as none — blank, "session", "untitled", or a raw id — shows "\<Tool> session in \<project>" instead, never the id itself. The same rule holds in the list, the tabs, the map, ⌘K and the notification.

A name taken from the opening prompt leaves out what the tool wrapped around it: <pasted_content …> around a paste, [Image] and <user_query> from Cursor, a Codex preamble. A tag you typed yourself, like <div>, stays. An AI run's session is named for its run, not for the instruction line Slate opens each step with.

Renaming the tab renames the session in its own tool, so the tool's own resume list shows the new name too:

ToolHow Slate renames it
Claude Code, Codex, CursorTypes /rename <name> into the session
OpenCodeAsks OpenCode's own server
GeminiGemini keeps no session names, so Slate keeps it

Slate types the command only when it cannot land in your words: the session's last turn has ended — so no permission prompt can be showing — and nothing is half-typed in its prompt. Claude Code and Codex say when a turn ends; Cursor does not, so a running Cursor session gets its new name when you next open it in Slate. Until then the tab shows the new name dimmed. If you started typing and deleted it, Slate waits for your next Enter or Ctrl+U. A session running in your own terminal cannot be typed into; its new name reaches the tool when you next open it in Slate.

It works the other way too. Type /rename in any of the four CLIs and the tab, the row and the memory page follow.

Agents that know about each other

When two or more sessions are running in one project, Slate tells each of them the others are there — once, at the start of a turn, in the same message that carries the branch brief. The rail says so under the group: each told the other is here.

What each agent is given is the other one's own words: which tool, which branch, how it is, what that session was asked to do, and the last thing it said. Not the branch's goal — two agents on one branch share that, so it cannot tell them apart. The page id comes too, for an agent that wants the rest.

Two things it will not say. It never claims a session is running — Slate reads transcript timestamps, which know a file was touched, so it says last active six minutes ago and gives you the time. And it asks for nothing: no wait for, no check with. Slate reports; what the agents do about each other is theirs to decide.

An agent can leave one note for the others, or send one to a particular agent. Each is shown it once on their next turn. A reply is another note addressed back — that is the whole of a conversation between two agents, with no inbox to poll and no channel to open. Notes that only narrate work in progress are refused, so what gets left behind is the half worth having.

There is no scheduler and no queue. Slate says who is here and what they know; it never assigns anybody anything.

Reading a file beside the session

A session changes files; this is where you read them without leaving. The Changed list in the About pane names every file the session's own tool calls wrote, read off its transcript rather than guessed from a time window — so an agent working in the same folder at the same time can never appear on another's list.

Each file opens as a tab, in the same strip as the session, with its own icon for its kind and language. The rail stays on Sessions. A printed path in the terminal opens the same view, at the line printed; Open file… in ⌘K opens one through the system dialog.

⌘P finds a file by name in every checkout. Type two or more letters and, beside the matching pages, it lists files from every repository Slate tracks and every worktree of each one, grouped under the checkout and branch they are in — FILES · acme · main, then FILES · acme-feat-x · feat/x — because the same file exists in each and the name alone cannot say which copy you mean. A file's name outranks a folder that merely matches, new files an agent has not committed yet are included, and whatever the repository ignores (node_modules, build output) is not. ⌘K shows the same files among its other results, and ⌘⇧F finds text inside them — see Search. A group, whose folder holds its projects rather than being one, is searched too: the projects directly inside it are found, with their worktrees. A worktree outside every folder Slate tracks is not searched, because the file view could not open it.

Code opens as itself: syntax-highlighted, numbered, searchable with ⌘F, and editable. A markdown file opens rendered, with Read one click away. An image is drawn. An SVG is both the picture and the text that draws it. Any view re-reads itself when a session moves, and an updated pill says the text under you changed.

Comment on the changes, then send them to the agent. In Diff, put the cursor on a line — or select several — and click Comment on line 88 (or on lines 90-93). Write the note and press Add, or ⌘Enter. Notes collect under the header in line order. Send to the session pastes them as one message — Review comments on <file>: followed by each note against its lines — at the prompt of the session running in that file's folder, the deepest one when several are. Nothing is submitted: you read it there and press Enter. When no session in Slate is working in that folder, the message is copied instead, and the bar says so. Comments never change the file.

Rewinding a turn

Every prompt you send a session takes a checkpoint first. The moment a new prompt appears in a live session's transcript — before the agent acts on it — Slate snapshots that session's folder: every tracked and untracked file, not what the repository ignores. It works the same for all five tools, because it reads the transcript rather than asking the tool. Nothing you own moves: not the branch, not HEAD, not the staged changes, not the stash. Checkpoints live under refs/slate/checkpoints/<branch>/, which git log and git push do not show, and the newest 100 per branch are kept. A turn that changed nothing takes none. A repository with no commit yet is checkpointed too; a folder that is not in a repository has nothing to snapshot, so its session takes none.

The Turns pane lists them, newest first, each named by its prompt. Restore asks for a second click, then puts the folder's files back to how that checkpoint had them and removes files created since. It takes a checkpoint of the present first — Before restoring: … — so a restore can itself be restored.

Reading a file three ways

Read | Diff | Blame are three ways to look at the same file:

  • Read is the file itself. Marks down the margin show what the branch changed: green for an added line, blue for a changed one, a red notch where lines were removed. Click a mark to open that change in Diff.
  • Diff shows what changed, with long unchanged stretches folded. against picks the comparison: where the branch began (the default), or the last commit.
  • Blame puts the commit each line came from down the left: its age as the strength of one blue, and its time and subject once per run of lines. Pointing at a line lights every line from the same commit. Clicking it shows what that commit changed.

The Now pill opens the file's history: this branch's commits, a line where the branch left its base, and the commits before. Pick one and every lens shows the file at that commit, read-only; the pill turns amber, and Back to now or Esc returns. [ and ] step through changes. ⌥1, ⌥2 and ⌥3 switch lens, and ⌥H opens the history.

Editing

At Now, Read is editable. There is no edit mode: type, as in VS Code. The lines you change are marked amber in the margin, the tab wears a dot, and the bar says how many lines are not saved, with Revert and Save (⌘S).

The file has a second writer, the agent, so saving follows three rules:

  • While an agent is working in that folder, Save waits. The button says Waiting for Claude Code and you can keep typing. When its turn ends, Save works.
  • Every save takes a checkpoint first, so Turns can undo it. The line that says Saved also offers Undo.
  • If the file changes on disk while you have unsaved lines, the two are merged. Changes to different lines are all kept, and a line says so. Where you and the agent changed the same lines, each place is shown as Yours beside theirs, and you choose Keep yours, Keep theirs or Keep both. Nothing is written until you press Save, and nothing is ever overwritten without that choice.

The editor works as VS Code does, on the same keys:

  • Undo ⌘Z, redo ⌘⇧Z (Ctrl+Z and Ctrl+Y on Windows and Linux).
  • Multiple cursors: ⌥-click adds one, ⌘D adds the next match of the selection, ⌘⇧L selects every match, and ⌥⇧-drag selects a column.
  • Brackets and quotes close themselves, and typing one over a selection wraps it. The bracket under the cursor is matched with its partner.
  • Other matches of the selected word are lit, and words already in the file are offered as you type: Enter or Tab takes one, Escape closes the list.
  • Fold a block with the arrow in the margin. A closing brace fixes its own indentation as you type it.
  • Find and replace ⌘F, go to line Ctrl+G, comment ⌘/, move a line ⌥↑/↓, copy it ⇧⌥↑/↓, delete it ⇧⌘K.

A file is saved the way it was written. Its line endings (LF or Windows CRLF, even a mix), its indentation (tabs, or the width of spaces it already uses; four spaces when it has none) and a leading byte-order mark are all kept, so a one-line edit is a one-line change on disk. Slate does not autosave, format, trim trailing spaces or add a final newline: each would turn a small edit into a large diff.

In Diff, each change offers Revert. It puts that change back as an ordinary edit, which you then save like any other.

The agent reads the disk, not your screen. When an agent is in the folder and you have unsaved lines, a line says it cannot see them yet. Anything Slate sends to it — review comments, Commit…, Push, Open PR — saves your unsaved files in that folder first, and says so if one could not be saved.

Unsaved text survives closing the tab and quitting Slate, as VS Code's hot exit does. It is kept on this Mac, in the app's own storage, never in the file, and is forgotten once saved or reverted. It comes back through the same merge as an agent's write, so a file that changed meanwhile is merged with it, never overwritten. A past commit is never editable, and neither is Diff or Blame. There is no rename, new file or delete. Slate reads and writes only inside a folder it already has business in: a group, project or branch folder, or a folder a live session is running in. Up to 1 MB of text or 8 MB of image; anything larger, a binary that is not an image, or a file outside those folders is handed to the system with Open in Finder and a sentence saying why.

What the branch changed

The Changed list is one session's own work. Changed on branch is the other half: everything this branch holds that its base does not, whoever put it there. It is the question asked before a merge, and no session can answer it about itself: a night of unattended work is two sessions and a rebase.

It is measured from the point the branch left its base, so a commit that landed on the base afterwards is never counted as this branch's work. It includes what has not been committed yet, because that is the state an agent's branch is actually read in.

It is the Changes pane of the session rail, drawn as a tree of the repository with two views:

  • Changes shows only the changed files, inside their folders. Each file says how many lines moved, new for a file git has never seen or a binary one, and gone for a deletion. Each folder counts the changed files under it.
  • All files shows every file in the checkout, except what the repository ignores. Changed files are coloured and lettered: A added, M modified, D deleted, R renamed. A folder holding a change wears a dot and starts unfolded; the rest start folded.

In both, an uncommitted file wears a dot, and a folder holding only one folder is drawn as one row (packages/server/src). Clicking a changed file opens it already measured against that same point; an unchanged file opens as it is. The tree unfolds to the file open in the tab strip. Filter files narrows the tree to paths containing what you type. The keyboard works as in VS Code: ↑ and ↓ move, → unfolds, ← folds, Enter opens. Slate remembers which view you picked.

Commit…, Push and Open PR sit above the tree when there is something to commit or push. Commit… and Push each paste one request at the prompt of the session working in that folder — Commit the changes on this branch… — and do not press Enter. The agent does the git work, and writes the commit message when you leave it empty. With no session there, the request is copied, and the pane says so. Slate itself never stages or commits. Open PR opens the pull-request sheet, which is the one place Slate pushes.

On a branch with no changes, such as a session on main, Changes says so and All files still shows the whole checkout.

Nothing in the tree writes: there is no rename, new file, delete or drag.

The session's own list is in its About pane.

Reviewing the whole branch

Review all, beside Changed on branch, opens the branch as one page: every changed file's lines, one file under the next, measured from the same point. It is also what pointing at a row in the rail opens. The header counts the files and the lines added and removed.

  • The file tree on the left holds every changed file in its folders, the same tree as the Changes pane. Clicking a file scrolls to it and unfolds it if it was folded. Viewed files are drawn quieter.
  • Fold a file with its arrow, or all of them with Fold all.
  • Viewed folds a file and counts it. If the agent changes that file again, it comes back unviewed, because what you read is no longer what is there.
  • Click a line number to comment on that line. Notes collect across files, and Send to the session pastes them as one message at the prompt of the session working in that folder. Nothing is submitted; you press Enter there. A note on a removed line says removed line, so the agent knows which version you mean.
  • A file's name opens the whole file, against the same point.

Revert hunk undoes one hunk, and Revert file puts a file back to how the branch found it; a file the branch created is removed. Before either, Slate takes a checkpoint, so Turns can undo the revert. A revert is refused while an agent is working in that folder, because its next write would collide with it, and when the file changed after the page was drawn; the page says so in a line at the top. Only the files change: nothing is staged, and nothing you staged is touched.

Revert is the one thing the review itself writes. It does not stage or commit; the terminal is where you act. A branch waiting for review also carries Merge, Keep and Discard above its review.

A plain shell

Not every terminal is a session with an AI tool in it. ⌃` opens a plain login shell — your own shell, your own environment — in the folder the page you are on stands for, or your home directory when nothing on screen names a folder.

It is hosted exactly like a session: it survives navigating away, it opens in the Sessions tab beside everything else, and everything above applies to it. What it does not carry is a tool account or a hand-back.

Taking over a session from your terminal

A session running in your own terminal can be continued here. Clicking its row only shows it: its conversation, live — every message and tool step as it lands, read from the transcript the tool is writing — where a hosted session's terminal would be, with the same rail down the right edge (Session, Changes, Turns, About; no Steps, because the conversation is already the stage). One button above it says exactly what continuing it would do. Nothing on that screen types into your terminal: the Session pane shows its whole latest message, not an input. The one case that needs no button is a Claude Code background job: the row opens it in Slate as itself, because joining it copies nothing and interrupts nothing.

Whatever a row offers runs under the same account the session was already using. A tool's sessions live inside its config directory, so continuing one under a different account finds nothing and quietly starts a new conversation.

Moving a session back to your terminal

My terminal on a hosted session detaches it from Slate, leaves it running, and hands you the command that picks it up again, with a button to copy it. For a backgrounded Claude session that is claude attach <handle>, prefixed with the account it runs under where there is one. The window closes; the conversation does not. Claude Code is the tool that can do this today, so the button appears only there.

Stopping a session

Every row whose session can be ended carries a Stop button. Two clicks: the second confirms, and the armed state forgets itself after four seconds.

A backgrounded Claude session is ended through the tool itself, with claude stop <handle>, which keeps the conversation so you can attach to it again later. Everything else is signalled with SIGTERM, so the CLI can shut its own MCP subprocesses down rather than orphaning them, and that ends the conversation with it. A signal is refused when the process is no longer the tool it was reported as: pids are recycled, and a stale report must never kill something else.

This works for sessions Slate never started, which is the point — a forgotten CLI in a terminal three desktops away is exactly the one you want to end.

Quitting Slate ends the sessions it is hosting, because an interactive CLI holds its own MCP subprocesses and orphaning that tree helps nobody. What it does first is hand back whatever can be handed back: a Claude session that is not already a background job is sent its own detach input and given 1.2 seconds to act on it, so it goes on living as a job you can pick up later.

How status is worked out

Status comes from the transcript, from who spoke last, and from whether a running CLI process vouches for the session. A quiet transcript with no live process is a closed conversation: it is dropped from the tab, never shown as Needs you. A process vouches for a session of its tool in the folder it works in — which, for a CLI told to work somewhere else (codex --cd <folder>, cursor-agent --workspace <folder>), is that folder, not the one its terminal was in. A session that moved on — its shell changed folder, or it entered a worktree — is still found beside the process in the folder it began in, and two spellings of one folder (/tmp and /private/tmp, a symlink and its target) count as one. For a tool that lists its own sessions, an unlisted session is gone — but a listing is not enough to call one alive, because a CLI remembers a background job long after it stopped. A job the tool reports as done, stopped or failed is finished, and that outranks everything else.

Recency alone cannot see the end of a turn: the write that ends a turn is what touches the transcript. So a session that just asked you something would read as Working for the rest of a 45-second window. Three signals correct that. None of them is consulted for a session nothing vouches for, so a stale title or a stale row cannot strand a closed conversation on the tab:

  • The window title of a session Slate hosts. Slate owns that pty, so it can contradict the file: a session whose title has stopped moving becomes Needs you in about ten seconds. Only a title that has been seen to move counts, and of the five CLIs only Codex animates its title.
  • The tool's own listing, when it reports a session as busy.
  • A sub-agent that is still writing. This is the one that reaches a session running in somebody else's terminal, where Slate hosts no pty.

For Claude Code, and no other tool, the transcript's own records settle it: a record carrying a tool call is mid-turn, one carrying only text has finished. A call with no result, once the transcript has been quiet for the window, is Needs you — never Idle — because the tool is either running it silently or asking you to allow it.

Three blind spots remain, stated rather than papered over. A long-running tool in a session Slate neither hosts nor can ask about reads as Needs you for Claude Code, since a silent tool and a permission prompt look the same in its transcript, and as idle for the other tools. "Waiting for permission" and "answered, waiting for your next prompt" are indistinguishable, and both surface as Needs you. And a tool whose title does not move and whose transcript Slate cannot read that way is judged on timing alone, so the end of its turn can take up to the window plus a tick to show.

How it stays current

Pushed, not polled. The server holds the live set in memory and streams changes over server-sent events (GET /sessions/live/stream); an idle machine sends nothing at all. The same report is available as a one-shot at GET /sessions/live.

Keeping that set current is event-driven. One fs.watch covers the transcript roots — auto-capture subscribes to the same one — and only the file that changed is re-read, coalesced over 150ms because one turn is many writes. Two more watches cover what a transcript root cannot: HEAD in each live checkout, so a git checkout shows at once, and the directory holding OpenCode's database, whose sessions are rows rather than files.

Three things a file event cannot report, so three timers remain: time passing (5s, pure CPU — this is what flips a session to Needs you), a process exiting on its own (15s), and an event the OS dropped (60s, a full re-walk). A tool's own session listing is reused for 30s, and refreshed by a lifecycle change rather than by the clock. A session killed outside the app leaves the tab on the next 5s tick, because every projection asks the OS directly whether the process is still there.

What you do yourself does not wait for a timer. A stop, a hosted terminal closing, a hand-back and a hosted child exiting all force a refresh (POST /sessions/live/refresh) that reaches every surface at once. A stop is a request rather than a fact — SIGTERM returns long before a CLI has shut its MCP subprocesses down — so the picture is re-observed at 250ms, 700ms, 1.5s and 3s until those processes have actually left the process table.

Git is asked once per repository rather than once per branch, and once for the whole window rather than once per surface. Branch counts refresh at most every thirty seconds while sessions are reporting, and at once when the window is focused — which is how a commit you just made in a terminal outside Slate shows up.

The tracker is read-only throughout: it never signals the CLIs and starts no AI tool.
