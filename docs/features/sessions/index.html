The Sessions tab shows every AI-CLI session on this machine, live: Claude Code, Codex, Gemini, Cursor, OpenCode — every transcript store the auto-capture watcher knows about, including non-default config dirs and auto-discovered tools. Nothing to install or register: if the watcher can capture it, the tracker can see it.

Where a tool can answer for itself, Slate asks it rather than guessing. Claude Code lists its own sessions (claude agents --json), so those rows carry the real session id, the name you gave the session, the process behind it, and — for a background job — whether it has finished. Asked once per connected account, because that listing is scoped to a config directory. Tools with no such listing are still tracked exactly as before, from their transcripts and the process table.

A session Slate starts is named before it exists. Three of the five tools let the caller choose the conversation's id, so Slate mints one and passes it at launch — Claude Code and Gemini take it directly, and Cursor makes one on request. Slate then knows where that session's transcript will be written before the file exists, instead of recognising it afterwards by its filename. Codex and OpenCode offer no way to be told, and their sessions are recognised exactly as before.

Claude Code is the exception worth knowing: Slate starts a Claude session in the background so it survives the app, and a backgrounded session's id belongs to Claude rather than to Slate. Those sessions are joined by the background handle instead, which is the stronger key anyway. What they do carry is the page's own title — it appears in Claude's prompt box, its /resume picker and the terminal title, so a session started from Slate is recognisable from outside Slate.

A session's helpers are not sessions. A CLI running subagents writes a transcript per helper — Claude Code puts them under the session's own subagents/ directory, alongside a workflow's bookkeeping journal; other tools write one beside the session and say what it is only on the inside. Every one of those is a transcript file in a watched root, and none of them is a conversation you are having. They are filtered out of the tab and out of auto-capture by the same rule, so one workflow does not become seven rows that share a title.

But they are shown, as children of the session running them. A session that fans out does the great majority of its work inside sub-agents, and for a long time the tab could see none of it — one row reading working while seven agents were mid-flight, and the worktrees they were editing reading nothing running. Both statements were true of what Slate measured and neither described the machine. The same files are now read a second time, through a different door: a session's row says how many sub-agents are live beneath it and expands to name them, and each one is a pip in a corona around its session on the map.

What it lists is news, not history. These transcripts are never deleted, so a session open all day holds every sub-agent it ever ran — 21 of them, for one conversation, on the machine this was measured on. A count like that presented as current state is the same defect pointing the other way, so the list is bounded by the window the rail's Just finished group already uses: an agent appears while it is working and for a short while after, and then it is history. A session whose fan-out ended an hour ago shows no children at all.

A sub-agent is never a session, and the difference is enforced by what a descriptor can hold rather than by care: it carries no pid, no handoff and no attach id, so nothing can offer to stop it. There is nothing to stop — a sub-agent runs inside its parent's process, whose working directory is the main checkout. That is measured, not assumed: during a seven-agent run, no claude process on the machine had any of the seven worktrees as its cwd.

What you see

Two views of one list, side by side: a graph that shows the shape of the machine, and a rail that reads it out. Hovering either one lights up the other, so a dot out there and a line in here are legibly the same session — and pointing at a repo or a branch lights every row under it, because a place is a thing you can point at, not only a session.

Live sessions only — a closed conversation simply disappears from the tab. Each session is a dot at the end of its own limb, on a ring of its own outside the branch ring, and its state is the halo around it:

  • Needs you — ⌘⇧J takes you to the one that has waited longest, and again to the next; the count sits in this tab's header. Nothing outside the tab announces it — no toast, no badge — on purpose: it is a state you come here to read, not news. The brain finished a turn (an answer, a question, or a permission-gated tool call) and is blocked on you. This is what saves you from a session silently idling in a forgotten terminal.
  • Working — the transcript is being written right now (the CLI appends every few seconds while generating or running tools).
  • Idle — quiet, and the human spoke last: left mid-thought or finished.

The graph is a radial tree of place. There is exactly ONE brain — the machine's — at the centre, and the tree grows from it along the spine the workspace declares everywhere else: project → repo → branch → session. Each level is a ring — the agents included, so three limbs off main is three agents at a glance — the rings are evenly spaced, and a limb from one ring to the next is the link between a place and what is inside it. A session with no repo and no branch to stand under hangs from an Unplaced limb rather than being dropped. When more than one workspace has work running, a workspace ring sits inside the project ring, since which store a project lives in is what tells two same-named projects apart; with one workspace that ring would name the same thing above everything and is not drawn.

The tree is laid out by session count, not by child count: every level divides its parent's angle in proportion to the sessions beneath it, so a wedge means the same thing at every depth and a project running six sessions is visibly wider than one running one. A small machine does not draw a ruler: a lone child bends off its parent's ray, alternating sides with depth, so two sessions read as the same species of tree as twenty-four. Agents on one branch fan out to either side of the branch's own ray, never on it, so the branch's name — written outward along that ray from beyond the agent ring — keeps its lane.

Colour answers whose is this, and that answer does not change one level down. Every limb, node and name is in its project's hue — hashed from the project's name so it is stable across polls — and Unplaced stays colourless. Status never colours identity: urgency lives in the halo around each dot and in the node's tint, so a session blocked on you three levels down still shows at the top of its limb. The most urgent state anywhere beneath a node is the one it wears.

Names are written horizontally, beside the node, on a small chip — a card on the ground colour, so a name reads as a thing attached to its node rather than as text floating over the ring guides. A branch keeps the start of its name, cut at fifteen characters (fix/sessions-gr…): the kind and the first words are what tell a branch from its siblings, and the rail beside the graph always has the whole thing. Point at a node and it says its full name. The chip is pushed along its own ring — never toward the next one, so a name can never read as belonging to the ring beyond — by its own size, and a branch's name goes to the side away from its own session dots. A ring too crowded to hold a name sideways (a couple of dozen branches) writes it along the ray instead, running outward into empty space beyond the agents; a ring too crowded even for that drops the name, and the rail still lists it. Nothing may leave the panel: a name that would run off the edge pulls the rings in a little rather than being cut.

You can move around it. Two-finger scroll or drag the background to pan; pinch, ⌘-scroll or the + / − buttons to zoom, about the pointer where there is one; the reset button beside the percentage, or a double-click, puts it back. Click a node to focus it: its subtree takes the whole circle and everything else leaves, the rail narrows to the sessions inside it, and a crumb trail above the graph names where you are — any crumb jumps to that level, All returns to the machine, and Escape does what Escape does everywhere. Drag a node to re-order it among its siblings: only the ORDER is kept, never a position, so a node's radius is still its level and its parent is still where it lives, and any arrangement you make is one the layout can draw. Arrangements survive a restart; Reset layout puts the tree back in the order it would have chosen — busiest first, then by name, so the limb you are watching does not jump when a sibling changes state.

The rail in the left pane is the readable half. It nests the sessions down the same spine the graph draws — project → repo → branch — and answers what is running where; the dot on each row still says what needs you. Until 2026-08-24 a [ Status | Place ] toggle offered a second reading, triage order (Needs you, Working, Idle), and the toggle was the cost: two readings of one list is a mode to remember and a setting to keep, for a question the row's dot already answers. Place is the one shape now.

Every row says what its session is asking. Under the title: the question when a session is blocked on one, the current step while it is working, and nothing when the human spoke last — reading your own words back to you is noise in a column this narrow. When a turn ends with a question the question is lifted out of the paragraph around it (the last one, since a turn that asks two things is asking for the second most recently); when it ends without one, the last thing said stands, because Needs you covers a turn that simply finished as well as one that asked. A blocked row also says how long it has waited, which is a different fact from when it last did anything and is the one the queue is ordered by.

A branch heading says what its checkout holds. Beside the branch's name: how many commits it has that its base does not (↑3), how far the base has moved on without it (↓1), an amber dot when there is uncommitted work in it, and the word missing for a worktree git lists but cannot read — which is never shown as "clean", because clean is what a person reads as "safe to throw away" and that is the one case git worktree remove refuses. A branch that is clean and level with its base says nothing, because there is nothing to say.

A checkout with nothing running in it is listed too, under its repo like any other branch, saying checked out, nothing running. That is the case the tab could not show at all: you made a worktree, it sat on disk, and a surface that lists live sessions had no reason to mention a folder. It wears the same badge, so a branch you finished with last week still says it holds three commits and uncommitted work — and it costs nothing extra to find out, because the one git worktree list the repo is already asked returns every checkout of it.

Pointing at the heading offers to open what the branch changed, beside the "+" that starts a session there, in the strip beside the rail, and it needs no session running on it — which is the point: a branch outlives every session that worked on it, and four hours of an overnight run is two sessions and a rebase. The list is measured against the merge-base and includes the working tree, so a file already committed and a file still sitting dirty appear once each, told apart by a dot; a row opens the file against that same merge-base. Read-only, like every git surface here — nothing stages, commits, merges or reverts. Acting is the terminal's.

The graph says the same thing on the same branches. A branch node holding uncommitted work wears an amber pip, and its own chip offers the same control the rail's heading does — the two draw one tree from one report, so a branch that was dirty in one and silent in the other would be the app disagreeing with itself. The node has no room for ↑3 ↓1, so the counts stay on the rail and on the chip's own title.

Git is asked once per repository rather than once per branch, when the tab opens, when the window is focused, and at most every thirty seconds while sessions are reporting — and once for the whole window, not once per surface, so the rail and the graph asking together costs what one of them costs. Focusing the window is the way to see a commit you just made in a terminal outside Slate.

Blocked sessions lead the rail, in their own Needs you group, longest-waiting first — the same order ⌘⇧J walks, so the key and the list cannot disagree about what is next. A session appears once: there while it waits, in its place otherwise. That is the one exception to place being the rail's only shape, and it is the point of the tab.

What just finished sits at the foot for ten minutes, dim. A closed session otherwise simply vanishes, which leaves the commonest question after a long run — what did the one that just ended leave behind — with nowhere to be asked. Each row opens the page the work belongs to — the same branch-else-repo-else-project answer its live row opened a moment earlier. A session that ran where no page tracks it has nowhere to go and reads as text rather than as a control that would refuse.

With nothing selected, the pane opens on the queue — the same blocked sessions the rail leads with, at the width the pane has, each showing the whole of what was said rather than the question lifted out of it. The sentence before a question is usually what makes it answerable, and at 264px the row cannot afford both. A Queue | Map control in the header switches, and the choice is remembered: the map is a good map, it was simply the wrong thing to open on, because the question a person brings to this tab is "what needs me" and the map answers "here is the shape of the machine". With nothing blocked, the map is what you get.

The rail answers to the keyboard. Tab reaches the rows and Enter opens one; ↑/↓ or j/k move between them, Home and End jump to either end, and Escape hands focus back so the terminal can have it. On the focused row, f starts a second agent in its folder and s stops it — s twice, with the arm expiring on its own and clearing the moment the cursor moves, because a destructive single letter against a list is one key away from the hand that meant j. Movement stops at the ends rather than wrapping. The order walked is the order drawn, across every place group. ⌘K's Focus the sessions list is the way in from anywhere.

Those keys belong to the list, not to the app, and that is a safety rule rather than a preference: j and k are letters, and a global binding would fire while a terminal has focus — which in this tab is most of the time — so the session you were watching would lose the keystroke to the list moving behind it. Held by the rail, they can only act once focus is already inside it, and any modified chord (⌘⇧J, ⌘K) passes straight through.

Place is not a filter. Every live session appears — a session with no repo and no branch to stand under lands in a trailing Unplaced group rather than being dropped, because a list whose whole job is completeness may not quietly shed a row. The repo heading is skipped in exactly one case, when the repo is the project, since a single-repo project would otherwise say the same word twice; a project running four repos shows all four. Every level — projects, repos, branches — is ordered by urgency before name, so the group holding something blocked on you sorts above the alphabet, and inside a branch the rows keep triage order.

The rail reaches the sessions no project governs, which is most of a real machine. Those used to be a name and nothing else, pooled by their folder. A session in a git repo the workspace does not describe now names its actual repo and the branch it is on — read from the page tree where a page covers the folder, and straight from git where none does — so the ungoverned half of the machine groups exactly like the governed half. What that does not change is governance itself: those sessions are still ungoverned, still attributed to no project, and still hang from the graph's Unplaced limb.

Each row carries the session's opening prompt (the same title the memory layer uses), its tool logo and name, its project, and how long ago it was active; Claude Code rows have a copy button for the claude --resume <id> command. In Place mode the heading directly above the row already names the project, the repo and the branch, so the row stops repeating them: the project dot and the project/branch chips go, and the width they were competing for goes back to the title, which is what a person actually reads.

A row is one line, and the tall ones are the answer. A session title is a whole prompt, so it is cut to a single line and the rest is in the row's tooltip. Under it sits one quiet line: the tool's mark, how long ago it moved, and how far its plan has got (0/4). That is the whole row — about 44px — and the rail shows a dozen sessions instead of two.

The exception is the one that matters. A session waiting on you shows what it is asking, on its own line above the tool line. A session merely working shows nothing there: what it is doing at this second is a status you glance at, and it used to take five lines to say something nobody reads — which made every row look exactly like the one that genuinely needed answering. Now a taller row means someone is blocked, before you have read a word of it.

The plan's count stays on that quiet line; the next open item, the goal, and "all planned work is done" are in the tooltip with the full prompt. That mission is read from the page the session belongs to — the same facts the AI tool was handed at the start of it — so the row and the session agree instead of paraphrasing separately. A session no page covers simply has no count. Ticking an item off a plan shows up on the next tick: the mission is re-read every projection, unlike the page lookup itself, which is memoized.

A prompt written in Hebrew or Arabic is laid out right to left, in the rail as well as in the open-sessions strip.

Several at once. Every session you open stays open in the pane — a strip above it holds one chip per open session, the status where its icon would be, and clicking a chip or its row in the rail switches to it instantly: the others stay mounted, so no terminal is torn down and replayed when you come back. A file you opened and a branch's changes get chips in the same strip, wearing the file's own icon and a branch glyph, because they live where the session lives — one home, never a second bar in another world. Closing a chip closes the view; the session keeps running and the rail still lists it, marked with a small terminal glyph while it has a view. Which sessions you had open is remembered on this machine, so leaving the tab for a page and coming back finds them where they were. Escape returns to the graph without closing anything.

Two at once, side by side. ⌘-click a chip and it moves to a second pane beside the first — the same gesture as the main tab bar, so a session and the plan it is working from, or two agents on one change, are on screen together. The chip on the right wears a columns glyph, and Unsplit appears at the end of the strip. It is layout and nothing else: every view was already mounted, so splitting attaches nothing and tears nothing down. Two panes and never a grid. A split never has an empty half — closing or losing the left one hands the whole pane to the survivor, and going back to the graph closes the split rather than showing a map next to a terminal.

The rail is the app's own pane, so it resizes and hides like every other world's: drag the pane's edge, or ⌘\ to hide it altogether when a terminal wants the whole width. Its width is remembered on this machine.

Clicking a row takes the session into Slate, as a tab:

  • one that can be attached to — Slate's own, or any backgrounded session — opens as the live terminal, attached by the click itself. There is no second button for it: an extra step for something the click could do is the app asking permission to do the obvious thing.
  • one running interactively in your own terminal is branched: Slate resumes the conversation with --fork-session, which carries the whole history into a new transcript of its own. Your terminal keeps its session, running and untouched, and the two can never interleave because they never write to the same file. The cost is the honest one — from that click they are two conversations.
  • one whose tool offers no way in at all opens as its conversation, read from the transcript that tool is writing and tailing as it grows. Read-only, and the last resort rather than the doorway.

The one takeover a click never performs is the one that ENDS the original first (a tool with neither attach nor fork — Cursor and Gemini today, see the table below): that stays behind a button that asks twice.

A chip that has no terminal yet — freshly opened by key, or restored from a previous visit after its terminal was reaped — is taken over by the tab itself, once, and only after the host has answered what it is already hosting. An unread list is not an empty one: deciding off it took every open session over again on every mount, and a takeover is a new CLI process, not a stale row.

Driving a mission from its page

The page is where work starts, and it now knows what is happening on it:

  • Sessions running here appear in the page's own header — needs you, working, idle, in the tracker's own words — and clicking one opens that session rather than the tab that lists it. Starting a second session on a branch that already has one working is the mistake this removes.
  • Start session seeds the CLI's prompt with the goal and the next unchecked item of the page's plan (Continue on feat/x: … — next: …), read from the same definition the rail and the AI tool's brief use. A goal says what the branch is for and is often months old; the next item is what to do now. The line is typed, never sent — and it is always one line, because a newline in a terminal prompt is a send.

What a session recorded

Beside a running session, under Recorded, is the half no terminal can show: not what the CLI said, but what survived it — the atoms it filed, and whether it wrote them on its own or after Slate had to ask. A session that owes memory and has written none says so there, while the work is still open.

It carries no commits or touched files on purpose. Joining those to a session means intersecting a time window with a repo, which counts a concurrent agent's work as this one's — the defect that made contract_emission unable to answer the gating question. A receipt that is sometimes somebody else's work is worse than one that says less.

A session nobody has judged yet stays silent rather than reporting "nothing recorded": no verdict means its first turn has not ended, or that Slate is not installed in the config it runs under, and reporting Slate's own absence as the model's failure is the mistake the coverage notice exists to prevent.

The remaining limit, stated rather than papered over. The write path now carries a session id, and every caller that has one passes it: an atom is pinned to its session's page, and the session is credited with having written it. An MCP tool call still has no session to carry — a tool call is not an episode — so an atom written that way is attributed to nobody rather than to whoever asked last. A session whose transcript proves it complied but whose atoms cannot all be enumerated says exactly that ("this session wrote memory — filed under the pages it belongs to") instead of claiming it wrote nothing.

Whether a session owes memory, on its row

Each session on the rail carries what it still owes: Memory owed when it did real work and recorded none of it, Recorded when it wrote memory of its own. A session that owed nothing shows nothing — most of the rail owes nothing at any moment, and a chip on every row would bury the one that matters.

Work done inside the app is judged by the same ledger and appears the same way, which it could not before: session_compliance held 245 sessions and every one of them came from a CLI's Stop hook.

A session the ledger has never seen owes nothing, not everything. Every session predating the ledger is one of those, and lighting them all would train you to stop reading the signal on the day it shipped.

When the app asks you for memory

When a stretch of your own work in the app has changed things and recorded none of it, a bar appears above the composer: "14 changes here, and nothing recorded — what you learned dies with this window." Write it puts the ask in the composer; Dismiss answers it for this session.

It is deliberately the quietest thing that still works. Never a modal, never focus-stealing, never in the way of a keystroke — a gate you have to clear to save your own work is the feature that gets switched off, and then enforcement is zero rather than partial. It appears only when something is owed, so it is absent almost all of the time rather than being chrome you stop seeing, and it asks once: dismissing is an answer, and the ledger records the miss either way.

The judgement is the same one the Stop hook makes for a CLI (owesMemory) — enough produced to be worth losing, and nothing written down — so the app and the hook cannot come to enforce two different rules. The thresholds it borrows were measured on CLI sessions, not on app use, because the ledger held no in-app sessions when this shipped. They are an assumption until there are enough in-app sessions to re-read them from, and the bar for interrupting a person should end up higher than the one for interrupting a model, not equal to it.

Closing the tab: a window is not a lifetime

What ⌘W means depends on who owns the session, not on what is on screen:

Anything left running without a window is labelled In Slate · no window in the rail, and clicking that row brings its window back rather than starting anything. A live CLI nobody can see is the one thing this tab exists to prevent.

Quitting Slate is unchanged: every session that can be handed back to no terminal is given its tool's own detach input first, and what cannot be handed back is ended rather than orphaned.

The page the work belongs to is one click from there (Its page), resolved the same way as before: the branch page when your workspace has one, else the repo folder, else the project. Which branch a session is on comes from the transcript itself when the tool records one (Claude Code stamps every line) and from the folder's HEAD otherwise, so a checkout since the session started never sends you to the wrong branch.

Below about 1024px wide the graph is dropped rather than squeezed, and the rail leads — it needs roughly 380px before three rings and their names have room, and it shows nothing the rail doesn't.

Starting a session

Where you are looking is where it starts. Point at a project, repo or branch node in the graph, or at one of those headings in the rail grouped by place, and a small + appears beside it — New session here. Pressing it starts a session at that place at once, on the tool the project names as its default, under that project's account, and opens it in Slate; there is no picker, because the place was already chosen by being pointed at. The control is a real button, so it is reachable by Tab as well as by the pointer, and pressing it neither zooms the graph nor starts a drag. A repo node or heading carries a second control, New worktree, which goes straight to the worktree form with that repo already chosen. A branch git named but Slate has no page for starts in its repo's checkout; a project whose only repo shares its name (the graph draws that repo nameless) starts in that repo's folder. A place with nothing to run in — a project with no linked folder, a page from a workspace other than the one this window is showing — shows no control at all rather than one that refuses. A refusal from the launch itself (no tool connected, no CLI to start) is shown on the tab, in the project's own words.

New session, at the head of the list in the left pane, is for the place you have not looked at yet, and for choosing a different tool. It sits with the list rather than in the tab's header, because it is the one control here that does not act on an existing session — the header says what the machine is doing. It shows where a session can run the way the workspace is shaped — project → repo → branch, as a tree — and clicking a row starts one there. A row that carries its own folder shows it, because a name alone hides a wrong checkout; a branch with a worktree is a row of its own, and a repo's last row is New worktree…, which makes one (branch, base, folder, and what to carry over) and starts the session inside it. A repo with a folder always opens, even with no branch rows yet — that row is what it opens onto.

A new worktree gets the ignored files the checkout it came from has. git worktree add copies tracked files only, so a fresh worktree has no dependency tree, no .env, and none of the build output a compile needs — which is why one made outside a terminal used to be a folder you could not build. The form asks once, with the answer already filled in: it reads what the repository actually ignores at its top level and offers those as chips, so you tick node_modules and skip .DS_Store rather than typing paths. They are hard-linked, so the copy costs an inode and no disk, and nothing carried is tracked — so nothing carried is what the branches differ about.

The pick is remembered on the project, and every later worktree of every repo in it is provisioned without asking. Under the chips is Then run — one command, run inside the new folder once the files are there, for the part that is a command rather than a copy: a build step, a codegen pass, a submodule fetch. It is remembered on the project the same way, and empty is the normal answer, because most of what a fresh worktree needs is files. What is in the field is what runs, so a command typed here takes effect on the worktree being made rather than the next one.

A branch with a worktree says what its checkout is holding, on the row itself: how many commits it has that the trunk does not (↑), how far the trunk has moved on without it (↓), and a dot when it still has uncommitted work — hover it and it says how many files, and that removing the worktree would discard them. Removing already refused a checkout with work in it; this is the same fact before the click rather than after, so "which of these five is safe to throw away" is a glance instead of five terminals. A worktree git lists but cannot read — its folder deleted by hand, or on a volume that is not mounted — says missing, never nothing: an undecorated row reads as clean, and clean reads as safe to remove.

Which tool is asked on the project row, because that is whose question it is: a workspace connects its tools and names a default in Connect, and a project may override it, and every branch under it inherits the answer. The control is the same one the Console shows beside its scope — the tool, and the account it runs under here — preset to the project's default, so an unpicked start runs exactly as the project says. A project on one tool shows that tool; a project on two lets you start this session on the other without changing the default.

Projects with no linked folder are not offered, in the picker or on a node: there is nothing to run in. The header button is available while the tab is still scanning — waiting to learn what other sessions exist is not a reason to be unable to start one.

Starting a session from a page

A branch, repo or project page carries a Start session button in its header. It runs the tool that project connected, in the folder the page stands for, under the account that project assigns to that tool — the three things a terminal makes you set up again by hand — and opens it inside Slate.

If the branch page has a Goal, that line is typed into the CLI's prompt and left there, unsent: you read it, edit it, and press Enter yourself. Nothing is submitted on your behalf, and the deeper context (decisions, prior sessions, the plan) still arrives the way it always has — through the memory layer's own recall at session start.

Whether it arrived is checked, not assumed. A terminal echoes what is typed into it, so Slate watches the session's own output for the line it sent: when it is there, the terminal says so; when a CLI's startup repaint swallowed it — which is what used to leave an empty prompt and no explanation — it says that instead, and offers the line back to insert or copy.

When it can't, it says why in the project's own words: "Acme does not use gemini. Sessions under /code/acme use: claude. Add it in Connect → AI tools to allow it here." A page with no folder, and a tool with no CLI to start (Cursor is an editor), are refused the same way.

Sessions that run inside Slate

A session's CLI is also told where it is: TERM_PROGRAM=Slate, the app's version, and SLATE_TERMINAL_ID — the terminal it is running in — so a tool that adapts to its host can, and so a session can state which window it belongs to rather than being matched to one by process id. It is opened at the size the pane will actually give it, too, instead of the 80×24 every pty defaults to and then being resized a frame later, which made each CLI lay its interface out twice.

A session started this way is a background job from birth. Slate starts it with claude --bg — which begins idle, spending no turn — reads back the handle it prints, and opens a view onto it. The consequence is the one that matters: that session belongs to no terminal, so you can pick it up in Slate, in any terminal (claude attach <id>), or after Slate has quit. A tool with no such mode is started the ordinary way; a session that runs beats one that is portable.

It runs on a real pseudo-terminal the app owns, so the CLI behaves exactly as it does in Terminal.app — colours, spinners, the full TUI — and you type into it normally. It is the same CLI running its own tool loop under its own limits; Slate supplies the folder, the account and the context, and stays out of the conversation.

Because the process belongs to the app and not to the view, navigating away does not end it: the session keeps running, and coming back replays what it said while you were gone. A session drawing a full-screen interface is not replayed but asked to paint itself again — its history is every screen it ever had, one on top of another, and the current screen is the only useful answer. Stop on the terminal ends it.

What the terminal does that a terminal doesn't

It is Slate's window, not a generic one embedded in it, and it is the same window wherever you open it — every session Slate hosts renders through one body and one status bar inside the Sessions tab.

The terminal gets the window. With a session on screen the tab draws no page chrome at all: no title strip saying "Sessions", no margin down either side. The tab strip is the top edge, the status bar is the bottom edge, and everything between them is the agent's screen. This matters more than it sounds: a terminal measures its screen in whole character cells, so a 59px title strip and 32px of margin above and below are not framing, they are rows the CLI never gets to draw on. On a 1440×900 window the change is 93×20 characters to 156×54 — four and a half times the screen, and the same terminal. Close the last view and the title strip comes back, because then there is a page to name again.

The status bar under the terminal is 24px, and it is in two halves that behave differently: the facts on the left take what width is left and truncate, the actions on the right never move. That is not a detail — a bar where Stop scrolls off the edge on a narrow window still claims to offer a Stop. It carries what the old 52px header carried: what the session is called, where it runs (tool · project · branch · folder), what it is doing in the CLI's own words (the window title the session sets for itself), and the things you can do — Its page, Fork (a second agent in the same folder), My terminal, Stop (one Stop, through the tool when it has one so the conversation stays resumable) and Context. A session drawing a full-screen interface gets a Repaint as well, for a screen that looks stale.

Focus mode — ⌘⇧M. The top bar, the rail and the sidebar go too, and the window is one agent and its status bar. An Exit focus button stays in the corner the whole time, and the same chord brings everything back. It is not remembered between launches, deliberately: a window with no chrome is something you turn on for an hour, not a shape to be relaunched into.

  • It follows your theme. Light or dark, and any retint you choose in Settings → Appearance, applied while the session keeps running.
  • ⌘F searches the session — the same find bar as a page, over everything the session has said, scrollback included.
  • ⌘C copies the selection, ⌘V pastes, ⌘+/− zooms and the size is remembered. Ctrl-C still interrupts the process — on macOS the app's shortcuts live on ⌘, which no terminal has ever used, so nothing has to be given up. Every other app shortcut (⌘K, ⌘P, ⌘W) reaches the app instead of also being typed at the CLI. A tool's own copy key works too, through the sequence terminals use for it.
  • Shift+Enter adds a line instead of sending one. An AI prompt is a paragraph, and Enter submits it — so the key every one of these CLIs documents for a second line has to actually arrive. It does now: measured against the CLI itself rather than assumed, since a browser terminal sends a plain carriage return for Enter whatever else you are holding, and a carriage return is a send.
  • Option is Meta. ⌥← and ⌥→ jump a word, ⌥⌫ deletes one — what a CLI's own keybindings assume — rather than inserting the accented character macOS would otherwise compose.
  • The mouse does what a terminal's mouse does. Selecting text puts it on the clipboard (a switch in Settings → Terminal, for people who select text to read it), right-click opens the menu — Copy, Paste, Select all, Clear, and Remember this line — and the middle button pastes. ⌥⌘K clears the screen; ⌘K stays the command palette, as everywhere else in the app.
  • Scrolling up is safe. Output keeps arriving without yanking you back down, and a Newest output pill appears while you are reading the past. Scrollback the host can no longer back says so — "earlier output is no longer kept" — rather than looking like a session that began there.
  • Links look like links. A printed URL or path underlines under the pointer and says what it will actually open, which for a compiler's relative path is a different file depending on where the session is running. A URL opens in your browser; a printed slate://page/<id> — what an AI tool writes when it records where it filed something — opens that page, as a tab beside the session; a printed path such as src/x.ts:42 opens that file, read-only, beside the session at that line (see below) — resolved against where the session IS, so a path printed after a cd names the file that exists.
  • It is your terminal. Settings → Terminal sets the font, its size and line height, the cursor's shape and blink, copy-on-select and how much scrollback to keep. Changes reach a session already on screen; nothing has to be relaunched. Colours are not there on purpose — the terminal follows the app's theme, so Appearance is the one place that decides them.
  • A selection can be remembered. Select the sentence worth keeping — why the build failed, the command that finally worked — and Remember files it as an atom under the page this session belongs to, deduped like any other memory. Nothing is captured automatically: what is worth remembering is a judgement.

Reloading the app does not lose any of it. The sessions live in the host process, so Slate asks what is still running and gives each one its tab back without moving you off what you were looking at.

It is also captured like any other session — the CLI writes its own transcript, so the watcher, your memory and this tab treat a hosted session and a terminal session identically. Hosting is an option, never a requirement.

A file beside the session

A session changes files; this is where you read them without leaving. The Changed list in the session's context column names every file the session's own tool calls wrote — read off its transcript, never guessed from a time window, so an agent working in the same folder at the same time can never appear on another's list. Each opens right here — a view in this tab's own strip, beside the session that wrote it, with the same chip, the same click to raise it and the same × to close it. It does not take you to another part of the app: the session stays one click away, which is the whole point of reading the file at all.

Every file wears its own icon in the strip and in the list — a glyph for the kind of thing it is and a colour for its language, so four sessions and the files they changed are told apart before anything is read. A printed path in the terminal opens the same view, at the line printed; Open file… in ⌘K opens one through the system dialog.

A file is shown the way its type deserves. Code opens as source — syntax-highlighted by file type, numbered, searchable with ⌘F. A markdown file opens rendered, with its source one click away. A screenshot or any other image is drawn. An SVG is both the picture and the text that draws it. Whatever the type, the view re-reads itself when a session moves — an updated pill says the text under you changed.

Source | Changes switches between the file as it is and the file against what HEAD holds, so "what did it change" is one click and never a guess. A file new since HEAD says so.

It is read-only, on purpose and for good: sessions write files, Slate shows them. There is no save, no rename, no file tree — this is the review gate that makes running four agents at once safe, not an editor. Slate shows only files inside a folder it already has business in — a project, repo or branch folder, or the folder a live session is running in — and up to 1 MB of text or 8 MB of image; a file outside that, a binary that is not an image, or a bigger one is handed to the system with Open in Finder and a sentence saying why.

What the branch changed

The Changed list above is one session's own work. Changed on branch beside it is the other half: everything this branch holds that main does not, whoever put it there — the session in front of you, the one that ran before it, or you, in a terminal. It is the question asked before a merge, and no session can answer it about itself: a branch outlives its sessions, and a night of unattended work is two of them and a rebase.

It is measured against the point the branch left its base, so a commit that landed on main afterwards is never counted as this branch's work. And it includes what has not been committed yet, because that is the state an agent's branch is actually read in — a session commits when it is finished, and you look long before that. A file still sitting uncommitted wears a dot; the rest have landed. Each row says how many lines moved, or says new where there is nothing to count against — a file git has never seen, or a binary one.

Clicking a row opens the file the same way the Changed list does, with Changes already measuring against the same point the count came from — so a change that was committed hours ago still shows as a change, rather than as an unchanged file.

Nothing here stages, commits, merges or reverts. Reading is the gate; the terminal is where you act.

It is a rail on the right, and it is open when you get there. Context — the branch page and its goal, what the session has recorded, and the two Changed lists — sits down the right edge, scrolling inside itself, and the Context button on the status bar hides it.

It used to sit UNDER the terminal. Same content, same default; what changed is which axis it is paid for on. A third of a 900px window is 297px, which a terminal spends as 19 rows it never draws on — and rows are what a terminal runs out of. On the right it costs width, of which there is plenty, so the agent's screen still grows several times over. Hiding it is remembered, and an answer anybody had already given the old drawer carries across unchanged.

Opening a terminal for its own sake

Not every terminal is a session with a brain in it. ⌘` opens a plain login shell — your own shell, with your own environment — in the folder the page you are on stands for, and any page with a folder carries a button for it beside Start session. Nothing on screen naming a folder is not a refusal: it opens in your home directory.

It is hosted exactly like a session: it survives navigating away, it opens in the Sessions tab beside everything else running, it follows the theme, and everything in the list above applies to it. What it does not carry is a tool account or a handoff — a shell has no login to run under and no conversation to hand back.

Working across sessions

Sessions have one home: the Sessions tab. The top tab bar holds pages; opening a session — from the rail, ⌘K, ⌘⇧J, or a page's Start button — brings you here and opens it in the tab's own strip, one chip per session, and clicking a chip switches to it. (Until 2026-08-24 a session could be a top-bar tab too, and appeared in two strips at once — ADR 0015 is amended: a top-bar tab is a page.)

The strip's panes stay mounted. A session you switch away from keeps running with its scroll position, its attachment and its output exactly as you left it — nothing re-attaches and nothing replays. Which sessions are open is remembered on this machine, so leaving the tab for a page and coming back finds them where they were.

A hosted session also shows what it is for beside the conversation: the branch page it belongs to, its Goal, and its knowledge pages, one click each. That is the half a terminal cannot have — you are not switching between the work and what the work is about.

Carrying a session into Slate

A session running in a terminal can be continued here — that is what the tab is for, more than starting new ones. What is on offer depends on what the tool itself supports, and Slate uses each tool's own lifecycle rather than inventing one:

Whatever a row offers, it runs under the same account the session was already using. A tool's sessions live inside its config directory, so continuing one under a different account finds nothing and quietly starts a new conversation.

Moving a session back to your terminal

The other direction, and the reason hosting is safe to try: Move to my terminal on a hosted session detaches it from Slate, leaves it running, and hands you the command that picks it up anywhere (claude attach <id>). The window closes; the conversation doesn't. A session that can't leave the app is one you shouldn't agree to run in it.

Stopping a session

Every row whose session can be ended carries a Stop button: two clicks (the second confirms; the armed state forgets itself after a moment).

Where the tool has its own stop, Slate uses it — claude stop <id> ends the session but keeps the conversation, so you can attach to it again later. Where it doesn't, Slate signals the process with SIGTERM so its CLI can shut its own MCP subprocesses down rather than orphaning them, and that ends the conversation with it.

This works for sessions Slate never started — that is the point, since a forgotten CLI in a terminal three desktops away is exactly the one you want to end. A signal-based stop is refused if the process is no longer the tool it was reported as: pids are recycled, and a stale report must never kill something else.

Quitting Slate ends the sessions it is hosting, because an interactive CLI holds its own MCP subprocesses and orphaning that tree helps nobody. What it does first is hand back whatever can be handed back: a session that is not already a background job is sent its tool's own detach input and given a moment to act on it, so quitting the app is not a way to lose a conversation that could have gone on living in your terminal.

How status is derived (and its limits)

Status comes from three signals: transcript recency, who spoke last, and whether a running CLI process vouches for the session (one ps + one lsof -d cwd). Tool and working directory narrow the candidates; when the process names a session id on its own command line that id decides it, and otherwise the process goes to the session that began nearest after the process did. Matching on tool and cwd alone gave the newest transcript the process regardless of which session it belonged to, so with two sessions of one tool in one folder a killed session could render alive holding a live session's pid — and Stop would then signal the survivor. A quiet transcript with no live process is a closed conversation — it is dropped from the tab, never shown as Needs you. On a platform where processes can't be enumerated, every recent session is assumed alive: over-reporting beats hiding a session that needs you.

For a tool that lists its own sessions, that listing decides membership in both directions — unlisted means gone, because ps cannot tell a session from the CLI's own helpers (bg-pty-host, bg-spare, a daemon) and each of those would otherwise vouch for a long-dead transcript. It does not on its own decide liveness: a CLI remembers a background job for as long as it feels like it, and a row for a job that stopped days ago read as Needs you for as long as its transcript stayed inside the recency window. So a listed session is corroborated before it counts as alive — the process it names has to exist, and a background job that names no process falls back to the ps scan. Neither source is trusted alone: the registry over-reports by remembering, ps over-reports by seeing helpers, and the answer is where they agree.

A row that says it is finished is finished, and that outranks both of them. claude agents --json reports a background job's lifecycle in its own field — done, stopped, failed, or blocked for one waiting on a human — and a finished job stays in the list: measured here, 3 of the 8 rows the CLI called active carried done. Its pid does not save the check either, because a background job runs on a prewarmed helper from the CLI's own pool and the row keeps naming that process after the job ends, so asking the OS whether the pid exists asks about a spare waiting for the next job. Both readers of the registry — the tab, and the check that verifies a Stop actually stopped something — read the state rather than the membership. Before they did, three finished jobs sat on the tab as Needs you for the whole 24-hour window, and pressing Stop on one signalled a helper another session was about to claim.

A fourth signal answers for the session when its transcript cannot. A long-running tool records its result as a user record and writes nothing while it runs; so does a session driving subagents, which appends nothing of its own until they are done. Three sources answer it: the window title the CLI sets on a pty Slate hosts, the tool's own listing when it reports the session as busy, and a sub-agent that is still writing. Any of the three promotes a quiet session to Working, and none is consulted for a session nothing vouches for, so a title or a row outliving its session cannot strand a closed conversation on the tab.

The third is the subagent case measured directly rather than inferred, and it is the one that reaches a Claude Code session running in somebody else's terminal — where Slate hosts no pty and has no title to read. It only ever promotes: every session that has ever spawned a sub-agent keeps those files forever, so a quiet one says nothing about its parent.

The hosted title — and only the hosted title — can also say the opposite, which matters more than it sounds. Recency means the file was touched, and the write that ends a turn is what touches it: the assistant's answer, its question, its permission prompt. So a session that has just asked you something reads as Working for the rest of the window, which is exactly the moment somebody is waiting on it. Slate owns the pty for a session it hosts, so it can contradict the file — and a session whose title has stopped moving becomes Needs you in about ten seconds rather than fifty.

The tool's listing is not allowed to do that. It is a report arriving from outside the process with no freshness of its own, and an idle that has not caught up would demote a session that is demonstrably writing. The title is a measurement Slate takes itself, off a pty it owns, and it is held long enough that a spinner cannot flicker a row.

Which sessions the title reaches, and which it does not. Only a title that has been seen to move is allowed to report a stop. Of the five CLIs only codex animates its title; Claude Code sets one fixed string, Gemini one, OpenCode names the task without motion, and Cursor sets none. For those a settled title is what the title always looks like, not evidence of anything — so a session whose title has never moved says nothing.

The transcript answers for the rest, from its own record shapes. An assistant record carrying a tool call is mid-turn; one carrying only text has finished; a result just back means the model owes the next thing. That distinction is what recency was standing in for all along, and it needed no new source — only the block types the message parser discards, because it keeps records with text and a bare tool call has none. That is why "the assistant spoke last" is as true in the middle of a turn as at the end of one, and why the window had to exist.

Measured 2026-08-29 across the transcripts on this machine: Claude Code carries tool_use, tool_result, thinking and text blocks in quantity; codex writes turn lifecycle events and no content blocks, and is the one CLI already served by its title; Gemini's logs.json is a list rather than a chat and Cursor's is a single JSON document, neither measurable from what is on disk here. So the reader is written generically and claimed only for Claude Code. A shape it does not recognise says nothing, and the window stands.

This too can only say STOPPED. A session waiting on a permission prompt has a tool call as its newest record and is indistinguishable from one running a long tool, so reading "a call is out" as definitely working would pin a session that is blocked on you to Working forever — worse than the window it replaced. A fix must not make the worst case unbounded.

Which tools this reaches was measured, not assumed — each CLI spawned on a real pty and its escape sequences captured through a working turn (2026-08-23):

Codex flips between a spinner frame and a plain one about ten times a second, so a verdict is held briefly rather than read from whichever frame a sample happened to catch — otherwise a busy session would flicker once a second.

Three accepted blind spots remain. A long-running tool in a session that Slate neither hosts nor can ask about still reads as idle — the transcript is all there is out there. "Waiting for permission" vs "answered, waiting for your next prompt" are indistinguishable; both surface as Needs you, and the second is why neither external signal is allowed to say a session is working. And a tool whose title does not move and whose transcript shape is not recognised — Gemini, Cursor, OpenCode on the evidence available here — is still read on the transcript's timing alone, so the end of its turn can take up to the window plus a projection tick to show.

How it stays current

Pushed, not polled. The server holds the live set in memory and streams changes over server-sent events (GET /sessions/live/stream); a change reaches the tab in about 300ms, and an idle machine sends nothing at all.

Keeping that set current is event-driven: one fs.watch over the transcript roots — auto-capture subscribes to the same one, so the machine opens one watch tree rather than two — and only the file that changed is re-read. Parsed transcripts are cached against their stat (mtime + size), and reads are bounded head/tail, so even a multi-hundred-MB session costs a few KB to judge.

OpenCode writes no transcript files — its sessions live in a SQLite database — so a fourth watch covers it: fs.watch on the directory holding opencode.db, debounced 150 ms like the rest. The directory rather than the file, because OpenCode runs in WAL mode and the .db file's own mtime can sit days behind writes that are landing in -wal/-shm right now.

Three things a file event cannot report, so three timers remain:

time passing5spure CPU — status is a function of the clock, so the working→Needs you flip touches no files. This tick is the floor on how fast the flip can show, whichever signal produced it
a process exiting on its own15sone ps+lsof, forced rather than served from the cache, so the interval really is the cadence. Only that — the CLI's own session registry (claude agents --json, ~0.3 s per config dir) used to ride this tick unconditionally and now sits behind its own 30 s TTL, forced only by a lifecycle change
an event the OS dropped60sthe full walk, kept as a reconciler (macOS drops events under load; Linux has no recursive watch)

The 15s tick is a discovery cadence, not the latency of noticing a death. Every projection asks the OS directly whether the process a session names is still there — a signal-0 probe, one syscall, no subprocess — and a session whose process has gone is ended at once, before recency is even considered. So a session killed outside the app leaves the tab on the next 5s tick rather than waiting out the working window. That window still governs a session with no process to name at all, which is what a one-shot claude -p run looks like between two scans.

User-triggered lifecycle changes do not wait for that timer. Stop, hosted terminal close, hand-back, and a hosted child exiting all force a live-session refresh (POST /sessions/live/refresh): the server re-reads the process list and each tool's own session registry, then publishes the full report to every subscriber. That is what keeps the rail, graph, open-session strip, sidebar badge, command palette and terminal chrome on the same picture immediately.

A stop is a request, though, not a fact. SIGTERM returns long before a CLI has shut its MCP subprocesses down and closing a pty returns before the child is reaped, so the observation taken the instant the button was pressed still finds the process in ps. The refresh therefore does not stop at one look: the caller gets that first one straight away — nothing waits three seconds to answer a button — and the registry keeps re-observing at 250ms, 700ms, 1.5s and 3s, pushing each report, until the processes the mutation ended have actually left the process table. It stops the moment they have, so an ordinary stop costs one extra look. Two mutations in a row — a hosted Stop signals the CLI and then closes its pty — each get their own observation rather than sharing the first one's answer, and a burst of them costs one extra look between them all.

The tracker is read-only throughout: it never signals the CLIs and spawns no brain. The same report is available as a plain one-shot at GET /sessions/live for anything that would rather not hold a connection open.
