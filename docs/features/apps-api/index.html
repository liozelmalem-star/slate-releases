App API

What an app can import from Slate. Your AI tool gets all of this as TypeScript declarations when it reads the app with get_app, and Slate checks every save against the same declarations, so a call that is not on this page is an error before the app runs. The Files editor completes from them as you type.

import { createRoot } from "react-dom/client";
import { slate } from "@slate/sdk";
import { count, dayLabel } from "@slate/sdk/format";
import { useQuery } from "@slate/sdk/react";
import { BarList, Badge, Card, Page, QueryView, Section } from "@slate/ui";

function App() {
  const week = useQuery(() => slate.sessions.count({ days: 7 }));
  return (
    <QueryView query={week} isEmpty={(d) => d.total === 0} empty="No AI sessions this week.">
      {(d) => (
        <Page title="AI sessions this week" actions={<Badge tone="active">{count(d.total, "session")}</Badge>}>
          <Section title="Per day">
            <Card>
              <BarList rows={d.byDay.map((x) => ({ label: dayLabel(x.day), value: x.count }))} />
            </Card>
          </Section>
        </Page>
      )}
    </QueryView>
  );
}

createRoot(document.getElementById("root")!).render(<App />);

After each build Slate runs the new version once, hidden, to check that it renders. A version fails if an error or a rejected promise is not caught, if a call is refused with not_allowed, bad_request or failed, or if nothing shows within 10 seconds. not_granted does not fail it: asking for a permission is what an app should do. During that run, writes and reads from outside your Mac (sources.reviews, sources.pulls, sources.repoPulls, sources.checks, tools.*) get no answer. Your AI tool reads the result as render in publish_app and get_app.

get_app also gives your AI tool the app playbook: the steps and rules it follows to build or change an app, from writing slate.json first to fixing every error Slate reports. The playbook's list of which permission opens which call is read from the same contract as this page, and a test fails when the playbook names a call or a part that does not exist. With it come four whole example apps: a chart, a tasks list that adds a task, notes kept with useStore, and a page written after you approve it. They are real app folders in Slate's source code (packages/shared/app-examples/), and Slate builds each of them in its own tests.

@slate/sdk

Everything here reads inside the workspace the app lives in (every project in it, no other workspace) and acts inside it. since is one of "1d", "7d", "30d" or "90d". Every list returns newest first, at most limit rows; to read on, pass the last row's time as before.

Lists from outside Slate

An app has no network. A list that lives somewhere else, like your Tasks from Jira or your pull requests on GitHub, comes through Slate: Slate reads it, keeps the rows, and answers at once from what it holds. Every answer has the same shape: { rows, fetchedAt, status, detail }. status is "ok", "stale" (older than it should be, and Slate is reading it again) or "failed" (the last read failed, so rows are the last good ones and fetchedAt is when they were read). Words in the rows were written by other people, so Slate cleans hidden characters out of them and marks the call as outside text.

CallWhat it doesPermission
slate.sources.tasks({ section, open })Items in Tasks, with when Tasks last synced them and whether the last sync failed.Read your Tasks
slate.sources.reviews()Open GitHub pull requests that wait for your review: git repository, number, title, link, author, draft, updated. At most 50.Read your GitHub
slate.sources.pulls()Your own open GitHub pull requests, in the same shape.Read your GitHub
slate.sources.repoPulls()The open GitHub pull requests in the git repositories your projects use, whoever opened them (a bot's too), in the same shape. author says who. Slate picks the git repositories from your projects; an app cannot name one.Read your GitHub
slate.sources.checks({ repo, number })The check runs on one pull request that reviews or pulls lists: name, status, result, link. Any other pull request is refused with bad_request.Read your GitHub

GitHub is read as the gh sign-in this workspace uses: Slate sends GitHub GET requests to four fixed kinds of address, and nothing an app sends can change that. Acting on a pull request is a separate permission, below. Slate keeps the rows for two minutes and does not ask GitHub again within 20 seconds of the last try, even when it failed. Across every app and workspace, Slate starts at most 12 GitHub reads a minute; a read past that answers "failed" with the last rows, and Slate reads it again once the minute has passed. A link that is not a https://github.com/ address, or a time that is not an ISO time, comes back as "".

Read a source with useSource (below) and show SourceStatus beside the list.

Your MCP tools

An app can read through the MCP tools your workspace already reaches: the servers you connected in Slate, and the ones your AI tools declare. Each tool is allowed on its own, for one app, and only as a read.

CallWhat it doesPermission
slate.tools.list()The tools this app may read through now: name, server, description and input schema. At most 20.—
slate.tools.read({ tool, args })Calls one tool and answers { rows, fetchedAt, status, detail }, like a source. rows holds one { text, truncated }, or none before the first good read.You allow each tool

An app lists the tools it wants in its slate.json, by the name the tool is listed under (<server>__<tool>), at most 20:

{ "tools": [{ "tool": "linear__list_issues", "why": "Show my open issues" }] }

The first tools.read of a tool shows you a card with its server, name and description. You allow it only by ticking that the tool only reads; a tool's own readOnlyHint is shown on the card but never ticks the box for you. A tool whose name says it writes (create, update, send...), or whose server marks it readOnlyHint: false or destructiveHint: true, is refused with not_allowed and never shown.

What you allow is pinned to the tool's definition: a SHA-256 of its name, description, input schema and annotations. If the server changes any of them, the next call is refused with not_granted and the card comes back, marked Changed since you allowed it. Slate reads each server's tool list again at most once a minute, so a change is caught within that minute.

args must match the tool's input schema: its types, required fields, enums and bounds, and no field it does not name. They are at most 4,000 characters as JSON. Anything else is refused with bad_request before the server hears it. So is a call to a tool whose schema uses a keyword Slate does not check (not, if, prefixItems and the like) at a field the call reaches, or a schema too large to check. A pattern or a format is not run; the server checks its own arguments. The answer is the tool's typed answer as JSON when it gave one, else its text, with hidden characters taken out and cut at 20,000 characters (truncated: true). Slate keeps an answer for a minute and does not call the same tool with the same args again within 10 seconds. Each server gets at most 20 requests a minute from apps, tool lists included, across every app and workspace; past that a read answers "failed" and Slate reads again once the minute has passed. A failure says what happened in Slate's own words, never the server's.

const issues = useSource(() => slate.tools.read({ tool: "linear__list_issues", args: { state: "open" } }));

An app can only finish or remind the items it made itself. An item from Jira or GitHub, one you wrote, or one another app made answers "No task has that id". Text an app writes (task and page titles, memories, page text, session prompts, toasts) is refused with bad_request when it holds characters you cannot see: zero-width ones, variation selectors and filler characters outside an emoji, text-direction overrides, the hidden tag block, control characters and private-use characters. Ordinary text, new lines and tabs, accents, other scripts, emoji of every kind (joined families, skin tones, flags) and the joiners that Persian, Urdu and Indic scripts need inside a word are fine. Titles and toasts are at most 200 characters.

Acting on GitHub

An app may ask Slate to act on a pull request in your own lists (sources.reviews or sources.pulls), with Act on your GitHub (github.act). Every action shows you a card first, every time. Slate builds the card from what it reads from GitHub, not from what the app sent: the GitHub account that will act, the git repository and number, the title, the author, and the exact words. There is no "always allow".

CallWhat it does
slate.github.approve({ repo, number })Approves a pull request waiting for your review. GitHub approves the commit the card showed.
slate.github.changes({ repo, number, preset })Requests changes on a pull request waiting for your review.
slate.github.comment({ repo, number, preset })Comments on a pull request in either list.
slate.github.label({ repo, number, label, remove })Adds a label the git repository already has, or with remove: true takes off one the pull request has.
slate.github.presets()Your words for this app: [{ id, text }].
  • The words are yours. An app never sends words. It passes preset, the id of words you wrote in the app's Dashboard, under Permissions (at most 20, each at most 1,000 characters). Without preset, you type the words on the card.
  • Only your pull requests. A git repository or number outside your lists is refused with bad_request. Approving and requesting changes need the review list.
  • The card must still be true. When you press the button, Slate reads the pull request again. If anything on the card changed (a new commit, a new title, the words, the account), nothing is sent, and the app hears bad_request.
  • 5 actions an hour per app, and 20 for all apps together, failed ones included. Past that, the call is refused with too_often, with no card.
  • The yes waits. The card's button can be pressed 0.6 seconds after the card appears, and every press on the card before then starts the wait again. An app cannot time a call so that a click aimed at the app lands on the card.
  • Every action is written down in the app's Dashboard, under Permissions: what, where, as which account, and whether GitHub took it.

An app asks for a permission in its slate.json:

{ "permissions": [{ "use": "tasks.write", "why": "Move a review to tomorrow" }] }

The permissions are tasks.read, tasks.write, github.read, github.act, memories.write, pages.write, routines.run and sessions.start. MCP tools are listed under tools instead (above). A refused call throws a SlateError whose code says why: not_allowed (the app did not ask), not_granted (you have not allowed it yet, or a tool changed since), declined (you said no on the card), too_often, bad_request, failed or no_answer.

Its own data

slate.store.get(key), set(key, value), delete(key) and keys() keep the app's own data on this Mac, never synced, up to 1 MB.

slate.on(area, fn) calls fn when Slate's data changes in that area: "pages", "memories", "tasks", "sessions" or "activity", or "changed" for every change. An area also hears a change Slate cannot name.

@slate/ui

Slate's own parts, in its light and dark themes:

  • Page layout: Page (a title, a line under it, the page's buttons), Section (a part under its label), Grid (cards side by side that wrap), Header, SectionLabel
  • A read's states: QueryView takes what useQuery returned and shows the wait, an error with Retry, your words when there is nothing, or your screen
  • A source's state: SourceStatus takes what useSource returned and says when the rows are from, that Slate is reading them again, or that the last read failed
  • Charts and numbers: BarList (labelled bars to one scale), Sparkline, StatCard (a number and how it moved), RankedList
  • Controls: Button, IconButton, Input, Textarea, Select, Checkbox, Switch, Segmented
  • Display: Badge, Chip, Avatar, Kbd, When (a time like "3h ago")
  • Frames and lists: Card, Row
  • States: Callout, EmptyState, ErrorState, Loading, Spinner, Skeleton, SkeletonLines

react, react-dom/client and lucide-react (every icon) are there as usual.

Slate is in alpha. Your data stays on your machine.
