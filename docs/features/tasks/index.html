Features

Tasks

Tasks lists what you owe: an issue assigned to you, a pull request to review, a message to answer, and lines you write yourself. Any of them can carry a reminder. Tasks sits in the rail after Home and belongs to the workspace the switcher picked.

Today's meetings

If a work gateway you connected carries a Google Calendar (or Outlook), one Today row sits above the Overview. It shows:

  • The next meeting: "in 25 min" within the hour, "in 8h 12m" after, "now" while one runs. Then its name, and Join when it has a video link.
  • The day as a thin line, 08 to 19, wider if a meeting falls outside. Each meeting is a mark; a dashed mark is one you have not answered or said maybe to. A red tick marks now.
  • The day's sums: meetings, all-day events, and free time left (only gaps of 45 minutes or more count).

Point at a meeting for its card: title, times, length, how far off it is, your answer, Join and Open in your calendar. Click to keep it open (✕, Escape or a click elsewhere closes it). If the title names one of your tasks by key ("Sync on PROJ-123") or a pull request by number ("Review #412", when only one task has that number), the card lists it under About; click to open that task.

Declined and cancelled meetings are left out. A meeting has no Done and adds to no count. Slate reads the calendar with every Tasks sync, through the gateway that reads your Jira, Slack and Gmail, at no token cost. If the calendar needs a new sign-in, the row shows Sign in (when the gateway gave a link), checks every few seconds, and gives up after three minutes. A workspace with no calendar shows no row.

Reviews is grouped by where each pull request stands:

  1. To review — asked of you, or assigned to you. Only a review asked of you counts as needing you.
  2. Changes asked — your pull request; a reviewer asked for changes.
  3. Checks failing — your pull request; its checks fail.
  4. Ready to merge — your pull request; checks pass, no conflicts, and no review owed (approved, or the project requires none). If Slate never read the review state, the group is No review asked for and offers no merge run.
  5. Checks running — your pull request; checks not finished.
  6. Waiting on review — your pull request, waiting for reviewers. Also where a pull request of unknown state goes (only GitHub is read for it today).
  7. On your projects — pull requests nobody took, on projects your account owns.

Issues is grouped by each tool's status names. "In Progress" (Jira) and "in progress" (ClickUp) share one group.

Each task shows its tool's logo (a tile with initials for Outlook and Azure DevOps).

Tasks reads GitHub, apps you connect in Connect → Integrations (sign-in from Slate, or a pasted token), and Jira, Slack and Gmail through a gateway set up in your agent. Slate learns to read other apps. An app Slate recognises but cannot read says Not read yet.

To-dos

The + in the side panel's title row adds a to-do: "call the accountant". Type it, press Enter. The box stays open, so three things go in as three lines. Set a reminder first if it needs one. The list then switches to To-dos with the new line selected.

To-dos stay in their own section: nothing you write lands in Issues, Reviews or Messages, and no tool writes to To-dos. They never sync and never vanish.

The list is grouped by when: Overdue, Today, Tomorrow, This week, Later, No time. Done today sits at the bottom, struck through, until tomorrow.

  • Tick the box to finish one. Tick again to undo.
  • Double-click the title to rename. Only to-dos can be renamed; a ticket's title belongs to its tool.
  • Run with AI… offers Feature (default), Bug and Investigate only. With no ticket, the agent reads the title and your note, and ships a pull request with no ticket update.

On the Overview, To-dos has Slate as its source.

Reminders

Any task can carry a time. Remind me… (beside Done on a to-do, and in the ⋯ menu of a tool's task) offers in an hour, this evening, tomorrow morning, next week, or a time you pick. The row shows when it is due.

At that time Slate rings a notification with the title, and the task moves to Needs you until you mark it done. Set a new time to snooze; Clear the reminder removes it.

  • Slate has to be running. A reminder that came due while Slate was shut rings once on next open, and says what time it was for. One due while the computer slept rings within five minutes of waking.
  • Reminders in Automations turns it off. Times already set stay.

Your agents can set one with remind\_me (Slate's MCP tools). A reminder is one moment; for something every day or week, use an automation.

The side panel

Tasks opens on the Overview. The title row has the +. Under it:

  • Overview: its number is what needs you now (a review asked of you, a direct message, a reminder that rang).
  • To-dos, Issues, Reviews, Messages, each with a count. A count includes only tools that answered. A section with nothing waiting is dimmed.
  • Agent runs: runs started from Tasks in the last 14 days, each with its session's receipt (see agent runs). Its number is flagged receipts you have not looked at. A session you ran yourself is not here; see Details in Sessions.

In a section, list and item sit side by side. Drag the line between them to widen the list (320 to 640 px; the item keeps at least 420 px). The width is remembered; double-click resets it. Above the list, one chip per tool with items, most first; extra chips fold into +N. With one tool there is no row.

Sync at the top reads your tools now. Its label says when the last read finished, which tool failed, or which needs sign-in ("Jira needs sign-in"). It is greyed while a read runs.

Chips filter the list to one tool; a ⋯ beside them acts on it. Disconnect (apps connected from Slate) forgets Slate's sign-in. Hide from Tasks (any app) removes its count and tasks without touching the tool; hidden integrations are listed on Connect → Integrations, each with Show. A tool Slate cannot reach keeps its old tasks, last, under Can't reach GitHub, outside the count.

With nothing connected, the panel offers Connect an integration; a tool your agents already reach is offered above the list with Use from your agents. On a first day the Overview gives way to the six most used apps as Connect tiles and a link, See all {count} integrations in Connect →.

Sign in opens the tool's sign-in page in your browser. Tasks then shows "Waiting for you to sign in…", checks every 4 seconds, and says Signed in to Jira when done. After 3 minutes it asks you to try again. For GitHub it tells you to run gh auth login. A sign-in link brought back by Teach Slate opens directly.

The Overview

The Overview draws the day left to right: your tools, the four kinds of work, Slate, the agents at work. Your tools (left) are each a logo and name, with You wrote feeding To-dos; a number on a logo is what waits from it; Sign in under a name means it needs a new sign-in; Connect an integration is the last node. The four kinds of work are coloured dots with counts or "nothing waiting". Slate (middle, drawn with its Hub mark) is the one memory every tool feeds and every agent shares, with how much needs you under it. The agents at work (right) are those running now in this workspace; past two, the second becomes a count. Click any logo, dot or name to open its list.

A task

Click a row to open the task beside the list:

  • Where it came from ("GitHub assigned this to you"), comment count and project.
  • Slate remembers: up to three memories that name the task by key (ECL-18747) or, for a pull request, number (#140). To-dos and Messages tasks show no card.
  • Run with AI… is the lead button (a to-do also keeps Done). The ⋯ holds the rest: Open in GitHub (when the tool gave a link), Remind me…, and Hide from Tasks, which removes a tool's task from this list only and offers Undo. A hidden task returns if the tool reports a newer change. Each section keeps a folded Hidden (N) line where Unhide brings one back.
  • The run button says what would run: Slate's mark, the skill (fix-bug) and the agent (Claude Code). Its chevron picks the agent for this run only, and the skill, which changes the project's rule for that kind (Workflow). Once a run starts, the button says Running and opens it. When there is nothing to run yet (your pull request waits on review or checks), one line says so.
  • The start dialog, top to bottom:
  • Where: project and agent. Filled in from the task's project, else the last one you used, else your only project.
  • What it is: Bug or Feature (something to solve or a to-do), Someone else's PR, My PR, My PR, checks failing, My PR, ready to merge. Beside those: Investigate only (to solve), Draft a reply or Find the answer, then draft (a message), and Just open a session everywhere.
  • The kind's rule: the skill, its steps on one line with the two stops for you as an amber hand (Stops for you after the plan, and before it ships), and Saved for every bug in <project> under the skill picker.
  • What the agent run gets: The task; What Slate knows, the memories the brief carries, each with × to leave it out (nothing is a valid answer); Your note, closed until you add one.
  • Just open a session shows What to type in instead: the task's name and link (or a to-do's words), typed into the tool and not sent until you send. /, @ and Cmd+Enter work as on Home.
  • What it can use, one line (GitHub · yarn test · Autopilot off), opening to each tool and whether the agent reaches it, the check command, Autopilot and the agent run rules, under Saved for every run in <project>. Allow Autopilot is the project setting; This run: Step by step / Autopilot is for this run.
  • The button says Run it or Open a session. If something blocks the start (a folder that is not a git repository), the reason is written in the footer.

The task's description and comments are read in the tool. A terminal and changes belong to the task's session in Sessions.

Agent runs (beta)

An agent run carries a task through a fixed process in a session you can see. agent runs (beta) is on in Automations; off, the card offers only Just open a session. Only your click starts a run. The list and every run's controls belong to the open workspace.

Workflow

Six kinds of work, each running one skill per project:

KindHow Slate knowsIts steps
BugThe ticket's type is Bug or Defect (Jira), or a GitHub issue has a bug labelRead it, Plan, you approve, Build, Check, Draft, you approve, Ship
FeatureAny other ticketSame as a bug
Someone else's PRYou were asked to review itRead it, Review, you approve, Post
My PRYou opened it; a reviewer asked for changesRead the comments, Plan, you approve, Build, Check, Draft, you approve, Push and comment. Then it is done; the next review round is a new run
My PR, checks failingYou opened it; checks failRead the checks, then as My PR
My PR, ready to mergeApproved, checks pass, no conflictsRead it, then as My PR: the run updates the branch and pushes. The merge is yours; an agent run never merges

Your pull request waiting on reviewers or running checks has no kind yet, but you can pick one. A pull request you opened counts as yours even if you assigned it to yourself.

A skill is one the project keeps (fix-bug, dev-flow, code-review) or Slate's own steps. Slate reads skills from .claude/skills, .agents/skills, .cursor/skills, .gemini/skills and .opencode/skills, also inside sub-packages. A folder with no SKILL.md is not a skill.

Slate suggests by skill name, best first (for bugs fix-bug, bugfix, fix; for features dev-flow, development; for reviews code-review, review; for your pull request address-review, fix-pr; for failing checks fix-checks, fix-ci; for ready to merge git-merge, merge, land). A description is never used to guess. With no name match, Slate's own steps run until you pick.

You change a rule by picking. Workflow, a folded box at the top of Issues and Reviews, shows that section's rules for one project (Bugs → fix-bug), with a project picker. The run button's menu and the start dialog change the same rule. A pick is saved at once for every task of that kind in that project; a changed rule says Changed and resets in one click. If a picked skill leaves the project, the rule says so and Slate's own steps run. Open shows the skill in Toolkit, and the rule says how often it ran in the last 30 days (ran 4× · 1 stopped by you).

A kind with no skill shows Slate's own steps and New review skill (or New bug skill). It opens Toolkit's New skill form on that project with a name and description filled in. Create writes the skill, makes it the rule and returns to Tasks; Cancel writes nothing. Both are offered for a project, not a group.

Slate keeps the steps and the approvals. A skill that is a whole process still runs inside them: each step opens the skill's SKILL.md and follows it for that step only. The plan still waits for approval and nothing ships before it. The skill lives in the run's own folder (a committed one already does; an uncommitted one is copied in with its files), so the agent does not ask permission for each step. Skill text is never copied into a prompt. A run keeps the skill it started with; a rule change affects the next run.

What the dialog offers:

  • Task to solve: Bug, Feature, or Investigate only (reports cause and options, changes no file).
  • Your pull request: My PR, My PR, checks failing, My PR, ready to merge. Its branch is fetched from origin into a folder of its own and is the only branch the run may push. You approve the plan, then the changes and one comment, word for word. A pull request from someone else's copy of the project is refused: its branch cannot be pushed from your project.
  • Someone else's PR: you approve the comments as Post comments, Request changes or Approve, and the run posts exactly that. Slate never picks. The head is fetched from your origin (no remote is added) into a folder of its own. A review never pushes.
  • A message: Draft a reply in a folder under Slate's data, or Find the answer, then draft, which reads the project you pick first. The dialog says whether Slate can send it or hands it to you.
  • Check: the command for the check step, from the project's files (package.json scripts, Makefile targets, pyproject.toml, Cargo.toml, go.mod), or Let the AI run find the tests. Slate opens on the one it detects; a pick is saved.
  • Tracker and code host, and whether your agent reaches each (command line gh or glab, an MCP server, or a claude.ai connector). An unreachable tool never blocks the run: the row says what happens instead (a link to open, a ticket update to copy), and Connect goes to Connect → Integrations. If the agent reported the server as needing sign-in in the last day, the row says Needs sign-in and offers Sign in to Jira in Claude Code.

On Run it, Slate:

  1. Makes a branch named after the task (fix/proj-12-short-title) and a folder for it, then runs the project's setup command there in the background. If the start fails, the folder and branch are removed. If setup fails, the run blocks and says so.
  2. Starts your agent in that folder with one line naming the run. Codex, Cursor and Gemini CLI are told to trust the folder.
  3. Closes the dialog and keeps you in Tasks, where the task shows the run: steps, the agent's last report, status. Open session shows the terminal. A tool that cannot take its first line at launch opens the session with the line typed in. The run also appears at the top of Agent runs.

The brief, the first step, hands the agent Slate's notes on the task, the project's memory index and any earlier run for it. The agent does one step at a time (Read it, Plan, Build, Check, Draft) and reports each. After each step the run waits for Next, which appears once the agent finishes its turn. After the plan it waits for Approve plan or Send back; Save as Plan doc keeps the plan as the branch's Plan doc. Before anything leaves your machine it waits for Approve to ship, which shows the commits, changed files, and the pull request title and body, ticket update, review comments or reply, word for word, each with Copy. Approving lets the push through, plus writes to the task's own tracker or chat and the code host. Every other server still asks; merging and removing are always refused. After shipping, Slate reads the pull request back and says whether it matches what you approved.

When a run stops for you (a step done, a plan or ship to approve, a held call, a block), it counts in Needs you and ⌘⇧J. Claude Code also sends one system notification.

Autopilot runs the steps back to back without Next. It still stops at the two approvals, at a held call, and after a long run of steps. A failed check returns to Build up to twice, then the run stops. Autopilot is off for every project until you turn it on in the start box or the project's Settings; then the panel switches a run between Step by step and Autopilot. On Autopilot, Claude Code does not ask for a call the agent run rules allow.

Claude Code, Cursor (interactive sessions), OpenCode (through Slate's plugin) and Codex support Autopilot and the agent run rules, and Slate types and sends the next step. Gemini CLI is step by step only: its rules can refuse a call but never ask, and Slate types the next step for you to send with Enter.

After shipping, the run waits for its merge. Every two minutes Slate reads the pull request's state with gh or glab; when it is merged or the task is done, the run is done. Mark done finishes it by hand. A pull request closed without a merge blocks the run: Mark done or Watch for the merge again. For a reply or review you posted yourself, I sent it myself finishes it. A finished run writes one line to its branch doc's progress log, keeps a lesson if the agent reported one, and records its session's tokens and estimated cost (all but Cursor report usage). It also shows on its pull request's task under Reviews.

Inside a section, that section's runs sit at the top under Agent runs; Needs you shows runs waiting on an answer. Agent runs in the side list shows the last 14 days, newest first: status, steps, approvals, and the session's receipt. One line above adds up runs started, done, pull requests and estimated cost. A done run offers Remove folder. The folder goes; the branch goes too when every commit is also on another branch or a remote. A branch holding work stays, as does your own pull request's.

If you type in the run's session, the run pauses until Resume. If the session ended, Reopen session opens it in the run's folder (a still-running background Claude Code job is reattached; otherwise the conversation continues where the tool allows). A session that never picks the run up within five minutes blocks it; Resume starts it again. Cancel agent run stops the session and removes the folder; the branch follows the same rule as Remove folder.

The agent keeps everything your tool normally does (shell, web, your MCP servers) inside agent run rules:

  • Git: only the run's branch. A push is refused until you approve shipping. Force pushes, tags and branch removal are always refused.
  • MCP: a tool that writes elsewhere asks first. Merging and removing are refused.
  • Shell: a command that sends data out asks first.
  • Files: writes stay in the run's folder. While reading and planning, it writes nothing.

The rules read each tool call and shell command, including those wrapped in env, $( ), scripts and heredocs. They are a guard, not a sandbox: an unknown program can still reach the network. The push rule has a second lock, a git hook in the run's folder.

A held call is refused for now and shows in the run. Answer there: Allow for this step, Always allow in this project, or Deny. An allowance names that one call (the MCP tool or exact command) and only lets through what a rule would have asked about.

agent run rules in the start box lists built-in rules and the project's own. Add one as Allow, Ask first or Deny, naming a call as the held-call card does: an MCP tool (mcp__jira__add_comment, or mcp__jira__*), shell: and a command (shell:npm publish), or file: and a path. Allow covers one exact call. Ask first and Deny also cover a command's first words and everything under a folder. Deny always wins.

Receipts

A receipt is what an AI session ran, checked against what it said. When a session's turn ends, in any agent Slate captures, Slate reads the session's own transcript and writes one. No model reads it and nothing leaves this computer. A session that only talked (no check, no changed file, no commit) gets none. The Agent runs count is flagged receipts not yet marked reviewed.

A receipt shows:

  • It said: the first paragraph of the last reply.
  • Checked against the transcript: where what it said and what it ran disagree, each with its evidence. What it said matches what it ran when nothing disagrees.
  • What it ran: every test, gate, lint, typecheck and build, in order, with passed and failed counts or exit code.
  • What changed: the files it edited.
  • Outcome: the commits its own git commit reported, and whether they are on the default branch or were reverted there within 30 days. Checked when you open agent runs, at most every 10 minutes per receipt.

Red Flagged:

  • A test failed, then passed on a re-run with no change in between.
  • The last run failed, and nothing passed after it.
  • It said the checks pass, but no test or gate run passed: the last reply says tests, a gate or a build passed, and no such run passed.

Amber Worth a look:

  • A run ended without a result: killed or stopped before it said how it went.
  • It edited a file outside the project (temporary folders and agents' own folders do not count).
  • A test's expected value was changed: an edit to a test file changed what an assertion expects.

A project's checks count by the name it gives them. Slate reads them from package.json scripts, make and just targets, and the pre-push hook (always a gate). A script that runs a file in a gate, ci, check or verify folder is a gate whatever its name.

Cursor records commands but not what they printed, so its runs show not recorded. Mark reviewed clears a receipt from the count; new runs, edits or commits in that session ask for review again. Open session opens its tab.

Copy as Markdown copies the whole receipt for a pull request. Share as artifact publishes the same text as an artifact. Both come from the stored receipt, with no model. Apps can read receipts too, and a Home widget can show the last day's (Apps API).

Where the tasks come from

A normal read involves no agent and spends no tokens.

GitHub is read through your GitHub CLI (gh), once you press Connect on its card in Connect → Integrations or setup; a signed-in gh alone reads nothing. When gh has several accounts, each workspace reads as the account that owns its git repositories (for an organisation's, the one that can see them). A workspace no account reaches shows no GitHub; switching accounts drops the old one's tasks. Every AI session Slate starts in a project runs gh as the sign-in that reaches that project, whatever gh's default is. An agent run shows GitHub as connected only when one of your sign-ins reaches the project.

  • Tasks reads when you open it, and when you return to the window after a minute.
  • Each read first asks GitHub whether anything changed. A full read happens on a change, when the last is over ten minutes old, or on Sync.
  • Six lists: reviews asked of you, pull requests assigned to you, your own open pull requests, issues assigned to you, and on git repositories your account owns, pull requests nobody reviewed or took (On your projects) and unassigned issues. A task on several lists shows once.
  • One more read gets where your open pull requests stand: review decision, checks, can it merge. If it fails, they show under Waiting on review.
  • No gh shows Unavailable. Signed out, or no sign-in sees this workspace's git repositories, shows Sign in: run gh auth login. A workspace whose docs name no GitHub git repository shows no GitHub row.

Apps you connected from Slate (GitLab, Jira, Linear, ClickUp, monday.com, Notion, Trello, Plane, Mattermost, Shortcut, Basecamp, Todoist, or any server added by address) are read through the app's own official server, signed in as Slate. Once Slate has signed in to one, it is read first and an agent's server for the same app is left alone; until then that server keeps reading, so connecting a personal Jira never stops a company Jira syncing. Other tracker apps are learned on first read; a chat app such as Mattermost by Teach Slate.

Jira, Slack and Gmail are read through the MCP servers your agents already use, after you press Use from your agents once. Slate looks in the settings of Claude Code, Cursor, Gemini CLI, Codex and OpenCode, only for accounts this workspace runs under, and keeps two kinds of server: a tool gateway carrying many tools (one declared in several tools, or as both a local server and a web address, counts once), and a server for one integration (a linear or atlassian server), skipped if a gateway or Slate already reads that tool. Either is a local server, which Slate starts and keeps running (turning integrations off stops it, unless another workspace still has them on), or a web address (streamable HTTP or SSE). A web address uses the key in its settings; with none, Slate signs in as itself: Sign in opens the server's sign-in page and returns to Slate. That sign-in stays on this machine, one per workspace; your agent's is never read.

Slate only calls tools that read (the rule). If a gateway cannot be reached (an expired sign-in), its tools say Unavailable or Sign in and their last tasks stay until the next good read. Tasks from a tool no gateway of this workspace reads any more are removed.

  • Jira: issues assigned to you, not done, grouped by Jira's status names.
  • Slack: direct messages and mentions from the last 7 days you have not answered.
  • Gmail: unread emails from the last 7 days, up to 30, by subject and sender. At most 15 new emails are opened per read; the rest come later. Outlook is not read this way.

Messages shows only what belongs to this workspace. A message stays when it names something the workspace works on: a group or project in your tree (thunderbolt, acme/api), or a project key, project name or git remote from your Issues and Reviews tasks.

  • Gmail applies this in its own search, on the subject only.
  • A Slack message is checked on its text as it is read (a link or channel name alone does not count; the text is not kept). It also stays when it comes from someone in your Issues or Reviews tasks.
  • Messages from a tool Slate learned, those Claude reads for you, and Zulip and Rocket.Chat messages read with a token are checked on title, channel and sender.

A workspace with no groups, projects, Issues or Reviews shows everything.

Apps read through a read card

Some official servers have no command that lists what is assigned to you (monday.com's commands include none). Their entry in Slate's app list carries a read card: one read-only call, where the items sit in the answer, and how to keep only yours that are not done. monday.com reads your 25 most recently used boards, 100 items each, with the board's name under each title. If an app's answer changes shape, its row says so.

Apps read with a pasted token

Six apps have no sign-in Slate can use, so you connect them with a token (Connect → Integrations). Slate reads each one's web API read-only, leaving finished items out:

  • Bitbucket: open pull requests where you are a reviewer and have not approved or asked for changes. Bitbucket has no such list, so Slate asks each git repository you are a member of, up to 200.
  • Gitea and Forgejo: open pull requests whose review was asked of you.
  • Gerrit: open changes whose attention set holds you. Someone else's change is a review; your own change back in your attention is yours to act on.
  • YouTrack: unresolved issues assigned to you, with state and priority.
  • Zulip: unread direct messages and mentions, one row per conversation.
  • Rocket.Chat: rooms with unread direct messages or mentions, one row per room.

A read that worked is not repeated for three minutes unless you press Sync. Two servers of one app are read together; one failing never hides the other's tasks.

Tools Slate learns on its own

During a sync, a tracker app with no reader gets one try a day per workspace. No model is used. Slate:

  1. Picks the app's tools that could list your tasks: the name says tasks, issues, items, tickets, cards or stories, and either says they are yours (get_my_issues) or takes an assignee. A tool that writes, or needs something Slate cannot fill in, is never tried.
  2. Asks who you are, when a tool needs it, through the app's "who am I" tool (atlassianUserInfo, Todoist's user-info, Shortcut's users-get-current). An app with none, such as ClickUp, is asked to resolve "me" like any name.
  3. Calls the best tools, at most 6 calls: first with your id as assignee, then with me.
  4. Keeps the first read that returns a list with a title and a status for at least one task (a status can be a done flag such as completed: true). A plain list beats one narrowed to a slice, such as tasks by date.

From then on the tool is read like Jira, for free, with your id kept as a placeholder. Finished tasks (Done, Closed, Resolved) are left out. If an app reads fine but nothing is yours yet (a new account), Slate keeps no read, because empty answers cannot show which filter works, and tries again the next day. Sync, connecting or disconnecting an app learns again at once. If an app renames or removes a kept read's tool, Slate removes the read and learns again in the same sync. A gateway tool that read fine in the last 3 minutes is not asked again until Sync; one waiting on sign-in is always asked.

Teach Slate

When you connect an app in Connect → Integrations that Slate has no reader for, Slate teaches itself once, with nothing to press. Its tile says Learning how to read your tasks in GitLab… for about a minute. Apps go one at a time. Slate asks Claude (Sonnet) about that one app, through Slate's own connected_tools and read_connected tools, so it works whatever MCP servers your agent has. Claude may not run a shell command or browse the web. Slate then tries the answer itself and keeps it only if it returned a list; after that it reads the tool with no agent and no tokens. If Claude finds nothing, the tile says Couldn't find your tasks in Notion. with Try again, and Slate never teaches that app by itself again. A read kept later clears it.

Slate checks every tool before calling it: when it picks, when it keeps an answer, and on every read. A tool is refused when any word in its name is a write word: send, create, update, remove, add, move, post, reply, comment, merge, close, assign, set, mark, upload, write and about fifty more. A word used as a filter is fine, so get_assigned_issues passes and assign_issue does not. A tool belonging to a different app is refused too. While Claude looks, it is kept away from the most common write words.

A tool only your Claude account reaches (a claude.ai connector such as monday.com) is read by Claude (Haiku) when you open Tasks and the last read is over 30 minutes old, or on Sync (at most every 2 minutes). It never reads a tool Slate reads itself, and there is no background timer.

What is stored

Per task, one line: tool, key (acme/api#412), title, state, person, link, a few counts, the tracker's type (Bug, Story), and the reminder time. Never a description, comment or message text. A line you wrote is the same row with no tool. Tasks live in the workspace's local file and are never shared, even in a shared workspace. Today's meetings are never written to disk: title, times, link and your answer stay in memory until the day ends or Slate quits.

Per project, only the skills you picked (a name per kind of work), in the file of the workspace that holds the project's doc. Skill text is never copied. Per learned tool: its name, arguments, your id in that app, and where each field sits in the answer, never the answer; for an app Teach Slate found nothing in, when that happened.

Slate keeps its own sign-in for a gateway at a web address or an app you connected from Slate (the token the server issued to Slate) in work-gateway-auth.json, a private file on this machine readable only by your user. Each sign-in is sent only to the server that issued it; if a gateway names a different sign-in server, Slate asks you to sign in again. The address of each connected app is in the workspace's file; it is not secret and never shared. A token you pasted is kept the same way in work-token-auth.json with the account name, never logged, sent only to the server you pasted it for; Disconnect removes it. An unfinished sign-in is kept in oauth-pending.json for fifteen minutes, so a restart during the browser step does not lose it. Slate holds one fixed address for the browser to return to; if another program holds it, the sign-in returns to the app's own port.

Receipt data

Per AI session that ran a check, changed a file or made a commit, one receipt in the workspace that holds the project's folder: session id and tool, title and branch, the first paragraph of the last reply, each run's command and result, edited paths, flags, commit ids and subjects, and when you marked it reviewed. Never what a run printed beyond counts, or the text of an edit. Local to the workspace and never shared.
