Agents & Workflows

Most of Slate is something you drive. Agents are the part that runs on its own. You describe what you want done and when, and Slate wakes on schedule, pulls together your recent context, and hands it to a brain along with your tools.

Workflows are the multi-step routines those agents, or event watchers, kick off.

Agents

An agent is a scheduled job with a prompt. You define it on the Agents page: a cadence, a prompt, and optional scoping. From then on it runs in the background without you opening the Console.

Which workspace a routine belongs to

Routines belong to the workspace you created them in, and only that workspace lists them. An agent is scoped to a project page, so it lives in the same store as the project it reads, and switching workspace genuinely changes which routines exist.

A routine therefore runs while you are in its workspace. The tick only fires routines from the workspace the window is showing, because the run's report is filed by the same window that produced it. Moving a project to another workspace takes its routines with it.

How scheduling works

Agents run on a cron-like cadence — daily, weekly, monthly, or at a specific hour. The executor lives in the Tauri host (src-tauri/src/agents/) and ticks every 60 seconds. On each tick it finds the agents that are due in the active workspace's store.

Rust gathers the context and emits agent_due; the webview runs the model and reports back with agents_report_run. Because the model call runs in the webview, an agent reaches the same brains and tools the Console does. Which brain, and under which account, is the agent's own: it names a tool, and its project supplies the account.

Context an agent sees

Before it runs, the executor assembles the material the prompt can reference:

SourceWhat it brings in
SessionsRecently captured AI sessions, each with its full one-line summary
FactsActive facts, tagged by kind (decision / preference / state / fact) with the reasoning (why) attached
PagesRelevant workspace pages
Prior runsThe agent's own earlier output, so it can build on what it already said

Each session is tagged with its top-level project (Acme, Private, …), so a run over all projects can group its output by project. The agent also runs with the same workspace tools as the Console, so a prompt can tell it to recall and search for the real decisions behind those summaries rather than reason over titles alone.

Grounding on your live tools

Everything above is Slate's own record — what was true when it was written. A ticket that has since moved is invisible to it. So before a routine writes anything, it also checks the world.

Each captured session records the directory it ran in and the CLI config it ran under. The runner derives the distinct working contexts from the period's sessions, ranks them (real git checkouts first, then by how much work happened in them), and takes the top three. For each it runs one short pass with the brain started in that directory under that config, which is what makes your project-scoped MCP servers (Jira, GitHub, Slack) load. Each pass asks only for identifiers and states: ticket keys and statuses, PR numbers and states. Ticket bodies, comments, and message contents are never requested or stored.

A source that failed because it needs signing in gets a button rather than a sentence. The running card offers Log in next to it, signs in against the same account and directory the pass used, and re-runs the routine. If the sign-in fails, the card says why in the CLI's own words. A local (stdio) server has no sign-in flow, so no button is offered for one.

What comes back reaches the report as two lists: what was verified this run, and which sources could not be reached. A routine may state a ticket or PR status as current fact only if a tool returned it this run; anything else is written as last-known and marked unverified. The Standup and the Shutdown both end with a Not verified section naming every source they could not reach and every context they did not check. If a routine reached everything, it says so outright, because a missing section would read as "all verified".

Prompt template variables

Inside an agent's prompt you can drop template variables that expand to that gathered context when the agent runs:

VariableExpands to
@sessionsRecent captured sessions
@factsActive facts
@pagesRelevant pages
@dateToday's date
@prior_outputsOutput from the agent's recent runs

Scoping and chaining

An agent can be narrowed to a single project with scope_project_id, so a brief for one project only reasons over that project's sessions, facts, and pages. It can also chain into a workflow after it finishes, via post_workflow_id — useful when the "think" step and the "act" steps are cleaner as separate pieces.

The report finds you

When a run finishes it files a dated report, and you do not have to go looking for it. A native OS notification fires on completion, carrying the report's opening line so you can read the gist without opening the app. On the Console home a Today card shows your latest ceremony — the Standup in the morning, the Shutdown from 17:00 — with a button to run a fresh one when the last is not from today.

Wherever you open it from — the Today card, the "report ready" toast, a routine's Last report — the report opens in Loop, beside the runs that came before it. It is never a page.

The ceremonies

Slate seeds six routines that mirror the operating rhythm of an engineering org, run from your own memory and organized by project. All six arrive switched off: run one from the Console card when you want it, and turn on its schedule from the Agents page.

RoutineCadenceWhat it produces
Standupdaily, 07:00Where each project stands and today's focus
Shutdowndaily, 18:00What moved today, loose ends, and tomorrow's first move
Planningweekly, MonWhat to commit to for the week ahead, per project
Reviewweekly, FriWhat shipped, what's in flight, what's blocked
Retroweekly, FriWhat went well, what dragged, one concrete change
Monthly ReviewmonthlyTrajectory, the decisions that mattered, one thing to change

Each is an ordinary routine with a prompt — edit the cadence, scope it to one project, or add your own. Their output lands in Loop.

Workflows

Workflows live on the Workflows page. A workflow is an ordered list of steps, each with its own prompt and its own tool. You can write the steps yourself or describe what you want and have a brain generate them.

Workflows do not have to be triggered by hand. They can be started by:

  • an agent, via its post_workflow_id, or
  • a watcher that fires on an event.

Watchers listen for things happening rather than a clock:

TriggerFires when
session_endedA captured AI session finishes
Daily at hour XA chosen hour of day arrives

Where a step runs

A workflow runs in its project's directory — the checkout Slate is watching for it, or the project folder if there is no checkout. That is what makes your project-scoped MCP servers load for a step, exactly as they do when you work in that directory yourself, and it is the same rule a routine's grounding pass follows. So a step can be written to check something rather than recall it.

A project with no folder configured is the exception: its steps run where nothing is scoped, so they have no connected tools to reach and can only work from what you put in the prompt. The directory is resolved once for the whole run, so editing a project mid-run cannot split one workflow across two places.

An agent belongs to a project, and a workflow runs in one. Each step names a TOOL; the project supplies the account it runs under. A background run costs the same model calls as running the prompt yourself in the Console.

Loop

Routine reports and workflow results are machine-generated, so they are not pages. They live in their own store and are collected in Loop, the surface that keeps you in the loop.

Loop is an operating picture. The Latest row shows the newest report from each routine — today's standup, this week's review, the last retro — plus a live card for any run in progress. History below holds every report, grouped by routine with a count, newest first inside each group. Every entry is labelled with the routine's current name and icon, so a renamed routine keeps its whole history under one heading, and with the project scope it ran on. Selecting one opens the full report.

A report is deleted rather than trashed — the delete button asks once before it does it, and the routine can always run again.

⌘K searches reports too. They have an index of their own over title and body, so a phrase you remember reading in last Tuesday's standup finds the standup — listed under REPORTS, separately from your pages, because it opens in Loop rather than in the tree.
