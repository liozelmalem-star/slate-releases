Agents & Workflows

Most of Slate is something you drive. Agents are the part that runs on its own. You describe what you want done and when, and Slate wakes on schedule, pulls together your recent context, and hands it to a brain along with your tools.

Workflows are the multi-step routines those agents (or event watchers) kick off.

Agents

An agent is a scheduled job with a prompt. You define it on the Agents page: a cadence, a prompt, and optional scoping. From then on it runs in the background without you opening the Console.

Which workspace a routine belongs to

Routines belong to the workspace you created them in, and only that workspace lists them. This is not a filter over a shared set — an agent is scoped to a project page, so it lives in the same store as the project it reads, and switching workspace genuinely changes which routines exist.

It follows that a routine runs while you are in its workspace. The tick only fires routines from the workspace the window is showing, because a run's report is filed by the same window that produced it: claiming one from anywhere else would write a team's report into your personal store, which is the kind of mistake a workspace boundary exists to make impossible.

Moving a project to another workspace takes its routines with it.

How scheduling works

Agents run on a cron-like cadence — daily, weekly, monthly, or at a specific hour. The executor lives in the Tauri host (src-tauri/src/agents/) and ticks every 60 seconds. On each tick it finds the agents that are due in the active workspace's store.

The split of work is deliberate: Rust gathers context, the webview runs the model.

every 60s tick (Rust)
  └─ find due agents
       └─ gather context: sessions, facts, pages, prior runs
            └─ emit `agent_due` → webview
                 └─ run LLM + tools
                      └─ report back → `agents_report_run`

Because the model call runs in the webview over the AI bridge, an agent reaches the same brains and tools the Console does — nothing is proxied to a separate service. WHICH brain, and under which account, is the agent's own: it names a tool, and its project supplies the account.

Context an agent sees

Before it runs, the executor assembles the material the prompt can reference:

SourceWhat it brings in
SessionsRecently captured AI sessions, each with its full one-line summary
FactsActive facts, tagged by kind (decision / preference / state / fact) with the reasoning (why) attached, so the brain can weigh a claim rather than take it on faith
PagesRelevant workspace pages
Prior runsThe agent's own earlier output (its opening lines), so it can build on what it already said instead of repeating itself

Each session is tagged with its top-level project (Acme, Private, …), so a brief run over all projects can group its output by project rather than blending unrelated work into one report.

Grounding doesn't stop at this pre-gathered dump. The agent runs with the same workspace tools as the Console — so a well-written prompt tells it to recall and search for the real decisions and threads behind those summaries, rather than reasoning over titles alone. The seeded Morning Brief prompt does exactly this, per project.

Grounding on your live tools

Everything above is Slate's own record — what was true when it was written. A ticket that has since moved, or a PR that has since opened, is invisible to it. So before a routine writes anything, it also checks the world.

Each captured session records the directory it ran in and the CLI config it ran under. From the period's sessions the runner derives the distinct working contexts, ranks them (real git checkouts first, then by activity), and takes the top three. For each, it runs one short pass with the brain started in that directory under that config — which is what makes your own project-scoped MCP servers (Jira, GitHub, Slack) load, exactly as they do when you work there. Each pass asks only for identifiers and states: ticket keys and statuses, PR numbers and states. Ticket bodies, comments, and message contents are never requested or stored.

One kind of failure gets a button rather than a sentence: a source that failed because it needs signing in. That is the only one you can fix on the spot, so the running card offers Log in next to it, signs in against the same account and directory the pass used — a server can be declared in a project's folder or in one CLI account's config, and asking the wrong one reports it missing — and then re-runs the routine, because a fresh token against a stale report still shows an empty card.

If the sign-in fails, the card says why in the CLI's own words. And if the reason is that the server has no sign-in to complete at all — a local (stdio) server, where the flow only exists for HTTP and SSE ones — the button goes away rather than inviting a click that can never work.

What comes back is handed to the report as two explicit lists: what was verified this run, and which sources could not be reached. That split is the point. A routine may state a ticket or PR status as current fact only if a tool returned it this run — anything else is written as last-known and marked unverified. The Standup and Shutdown both end with a Not verified section naming every source they couldn't reach and every context they didn't check; if a routine reached everything, it says so outright. A missing section would read as "all verified", which is the failure this exists to prevent.

Prompt template variables

Inside an agent's prompt you can drop template variables that expand to that gathered context when the agent runs:

VariableExpands to
@sessionsRecent captured sessions
@factsActive facts
@pagesRelevant pages
@dateToday's date
@prior_outputsOutput from the agent's recent runs

Scoping and chaining

An agent can be narrowed to a single project with scope_project_id, so a morning brief for one project only reasons over that project's sessions, facts, and pages.

An agent can also chain into a workflow after it finishes, via post_workflow_id — useful when the "think" step and the "act" steps are cleaner as separate pieces.

The report finds you

When a run finishes it files a dated report — but you don't have to go looking for it. A native OS notification fires on completion, carrying the report's opening line so you can read the gist without opening the app. And on the Console home, a Today card surfaces your latest Morning Brief, so it greets you when you open Slate.

Wherever you open it from — the Today card, the "report ready" toast, a routine's Last report — the report opens in Loop, on the stage beside the runs that came before it. It is never a page: what a run produced is not a document you filed, and Slate stores it as neither.

The ceremonies

The seeded routines mirror the operating rhythm of a high-functioning engineering org, run for you from your own memory and organized by project:

RoutineCadenceWhat it produces
StandupdailyWhere each project stands and today's focus
Planningweekly (Mon)What to commit to for the week ahead, prioritized per project
Reviewweekly (Fri)What shipped, what's in flight, what's blocked
Retroweekly (Fri)What went well, what dragged, one concrete change
Monthly ReviewmonthlyTrajectory, the decisions that mattered, one thing to change

Each is just a scheduled routine with a prompt — edit the cadence, scope it to one project, or add your own. Their output lands in Loop, the latest of each on top.

Workflows

Workflows live on the Workflows page. A workflow is a multi-step routine — either prompt-based (the model works through the steps) or manually defined.

Workflows don't have to be triggered by hand. They can be started by:

  • an agent, via its post_workflow_id, or
  • a watcher that fires on an event.

Watchers listen for things happening rather than a clock:

TriggerFires when
session_endedA captured AI session finishes
Daily at hour XA chosen hour of day arrives

Where a step runs

A workflow runs in its project's directory — the checkout Slate is watching for it, or the project folder if there is no checkout. That is what makes your project-scoped MCP servers (Jira, GitHub, Slack) load for a step, exactly as they do when you work in that directory yourself, and it is the same rule a routine's grounding pass follows.

So a step can be written to check something rather than recall it. A project with no folder configured is the one exception: its steps run where nothing is scoped, so they have no connected tools to reach and can only work from what you put in the prompt.

The directory is resolved once for the whole run, not per step, so editing a project mid-run cannot split one workflow across two places.

An agent belongs to a project, and a workflow runs in one. Each names a TOOL; the project supplies the account it runs under, so the same workflow is one account in one project and another elsewhere. A background run costs the same model calls as running the prompt yourself in the Console.

Loop

Routine reports and workflow results are machine-generated — a different kind of thing than the pages you write by hand. So they are not pages at all: they live in their own store and are collected in Loop, the surface that keeps you in the loop. Nothing to hide from the sidebar, because nothing puts them there.

Loop is an operating picture, not an archive. The Latest row shows the newest report from each routine — today's standup, this week's review, the last retro — so you see where everything stands at a glance. Earlier is the full history below, newest first. Every entry is labelled with the routine's current name and icon (so a renamed routine keeps its whole history under one heading) and the project scope it ran on. Selecting one opens the full report.

Under the hood each run writes one output row: what produced it (a routine or a workflow, by id), the run it belongs to, its title and body, and the scope_project_id the grouping above reads. It stopped being a page on purpose — a report is something a run produced, not something you wrote. One thing changed with it: a report is deleted rather than trashed — it asks first, and the routine can always run again.

⌘K searches reports too. They have an index of their own over title and body, so a phrase you remember reading in last Tuesday's standup finds the standup — listed under REPORTS, separately from your pages, because it opens in Loop rather than in the tree.
