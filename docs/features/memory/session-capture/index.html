Session Capture

Memory is only useful if it fills itself. Slate captures your AI sessions automatically: a filesystem watcher observes the conversation files that coding tools already write to disk, detects completed sessions by pattern, and stores each one as a page in your workspace.

How capture works per tool

ToolCapture method
ClaudeWatcher — pattern detection on conversation files. No hooks needed.
CodexWatcher — pattern detection on conversation files. No hooks needed.
GeminiWatcher — pattern detection on conversation files. No hooks needed.
CursorWatcher — cursor-agent writes JSONL under ~/.cursor/projects/<project>/agent-transcripts/. No hooks needed.
OpenCodeDatabase reader — OpenCode keeps its sessions in SQLite, not in files, so Slate reads the rows instead of polling a directory. Nothing to configure.

There is nothing to configure for any of them. Four tools write JSONL transcripts and the watcher recognizes them on its own; OpenCode writes no transcript at all, so Slate reads its database (~/.local/share/opencode/opencode.db) read-only and renders each session into the same shape the other four produce. That means one set of rules — the same digest, the same noise filtering, the same branch attribution — applies to every tool rather than the best-supported one.

Cursor used to be listed here as needing an opt-in sessionEnd hook. It doesn't: its CLI writes ordinary transcripts that the watcher already read. If you enabled that hook on an earlier version you can turn it off — capture continues without it.

Auto-discovery — new tools and non-default configs

The four rows above are a seed, not a fixed list. The watcher also auto-discovers any AI tool that writes JSONL transcripts under your home directory: it looks for a hidden config folder holding a subdirectory (projects, sessions, tmp, …) whose files parse as a role-tagged transcript, and captures it automatically. Two things fall out for free:

  • A brand-new tool you install is captured with no registration.
  • A non-default config directory — e.g. running Claude under ~/.claude-personal — is picked up automatically, not just the default ~/.claude.

Nothing is registered by hand; if it writes transcripts under ~, it's captured. (XDG ~/.config trees are skipped for precision.) Assigning an account to a project is what starts capturing it — there is no separate watch list to keep in step.

What a captured session looks like

Each session becomes a page (icon MessageSquare / 💬) with structured JSON properties:

PropertyMeaning
promptThe originating request for the session.
summaryA one-line summary of what happened.
toolWhich AI tool produced the session.
tokensToken count for the session.
sessionIdStable id linking the session back to its conversation.
kindsession when a sessionId is present, note when it is not — derived, never asserted beside it.
modelThe model that ran.
branchThe git branch the work happened on.

The page body carries the session's digest — every real human turn (the asks and mid-session course-corrections, where decisions live) plus the final outcome. This is deliberate: a session's important decisions are usually made in the middle, so recall's content search needs more than the opening prompt to find them. For a session on a git branch, the digest page is filed under the branch and linked from its session log.

The branch is taken from the transcript's own record when the tool writes one (Claude Code does); for tools that don't (Codex, Gemini, Cursor, OpenCode), a freshly captured session falls back to the repository's current branch, so it no longer collapses to the repo level. Historical back-fill stays repo-level rather than mis-stamp an old session onto today's checkout.

remember writes each atom's human-readable window through this same writer, and such a page has no conversation behind it — no sessionId, no tool. Deriving kind from the sessionId is what keeps the two apart: until 2026-08-29 the writer stamped session on everything, so remembered atoms surfaced in the Console's conversation history offering rows there was nothing to resume. A startup pass retypes the pages already written; it retypes rather than archives, because the page is where a human reads the atom back.

Captured sessions appear in the Memory page and are shown read-only — they are a record of what happened, not a document to edit.

Keeping the watcher running

Capture runs inside Slate itself and stops when you quit. Sessions you run while it is closed are picked up the next time you open it — the historical scan catches what the live watchers missed. Turn it on and off in Settings → Machine & AI; it is one switch per computer, unlike the tools and sources on the other tabs, which belong to the open workspace.

The watcher reads files already on your machine and writes only to your local workspace. Session capture sends nothing to the network.
