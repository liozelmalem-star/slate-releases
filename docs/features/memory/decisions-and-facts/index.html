Decisions & Facts

Slate's long-term memory holds two kinds of knowledge. A decision is a choice you made, kept with its reasoning. A fact is a durable statement that stays true across tasks. You recall facts to know what is so; you read decisions to know why you chose what you did.

Decisions

Record one with record_decision. It takes title (what was decided), reasoning (why), alternatives (what was rejected and considered), confidence and outcome, and writes both a decision atom and a decision page carrying the full reasoning. Your AI tools read them back with recall, which ranks a decision first when a question asks why; Slate's in-app agent can also list them with list_decisions.

remember also produces a decision when it detects one in the text. A remember call that names kind: "decision" must carry its reason, either as reason or in the sentence itself. Without one it is refused, because a decision without its reason can't be weighed later.

Facts

Each fact carries:

AttributeMeaning
textThe knowledge itself.
kinddecision, preference, state, fact, or lesson.
triggerFor a lesson: when it is handed to a session, a command pattern or a file glob — see Lessons.
confidenceHow strongly it's held; strengthened by near-duplicates.
statusactive or superseded.
subjectThe slot it asserts about, when it has one — see Slots.
origin, origin_toolWho wrote it: person (you, in the app) or agent, and which tool. Empty on facts written before this was recorded.
pinnedYou pinned it, so every session in its project starts with it.
last_used_atWhen a session last cited it by its ref.
source_hashA fingerprint of the cited file when the fact was written, so a later change can be flagged.

Facts are ranked lexically when recall runs — keyword coverage between your query and the fact, weighted by recency (a 30-day half-life) and confidence, and re-ordered by word statistics fitted on your own memories. Nothing is stored for it and no model is called. Knowledge that no longer holds is superseded by whatever replaced it rather than deleted, so the record survives.

Shelf life — when a fact stops being offered

A state fact says where a thread stands right now, so it goes stale in a way the other kinds do not. Fourteen days after its last confirmation it leaves the recall pool: nothing will offer it to an AI again.

Nothing is deleted. The row stays in the store, stays searchable, and stays visible in Memory — it is retired, not dropped. And the clock runs from the last time the fact was confirmed, not when it was written, so a state that keeps proving true keeps being restated and keeps living.

Only state has a shelf life. A decision and its reasoning stay worth knowing, a fact stays true, and a preference you have not restated in a year is one you still hold.

Resting — when a fact leaves the index

A fact, decision or state that no session has cited or restated for 30 days rests. It leaves the index that sessions start with, and stays stored and searchable with recall. Citing it, restating it or pinning it wakes it. Pinned facts and preferences never rest.

Nothing is deleted this way. Facts that an earlier version of Slate evicted for never being used keep that mark, and writing the same fact again brings one back.

Slots — how a fact replaces another

A preference and a state are single-valued: you hold one preference per axis, and a thread is in one state. When a new one arrives, the old one should be retired. Similarity cannot decide that — "dark theme" and "light theme" share no words, and a contradiction often looks more similar than a restatement.

A slot settles it. It is a stable dotted key naming the axis — ui.theme, deps.db-boundary, branch.slate.main.state — and a later fact on the same slot retires the earlier one.

Slate works the key out for you; there is nothing to pass. A subject that is not a well-formed dotted key — a branch name, a dated snapshot, a title with spaces — is discarded rather than stored, and the fact is deduped by similarity instead. Decisions and plain facts never take a slot: they accumulate, because superseding them would throw away knowledge that is still true.

Facts Slate writes for itself

Almost every fact is written by an AI tool calling remember. One is not. Slate derives a state fact for each branch carrying uncommitted work, from the same data behind Parked work — one per branch, on a slot named branch.<repo>.<branch>.state, refreshed when the server starts.

Only that case. A branch whose work has all landed would produce what git log -1 already answers. Work sitting in your index or working tree is the opposite: no commit records it.

Because the slot is named, each new reading supersedes the last, and a branch you come back to and commit simply stops producing a fact. state facts also leave the recall pool after 14 days (Shelf life), so an abandoned branch fades on its own.

Is the corpus still worth trusting?

Facts accumulate for as long as you use Slate, and two ways of going bad are invisible from the outside. Corpus health measures both and can repair them. It is an Activity widget, hidden until you add it from Edit.

An atom filed under a page you deleted. A fact's scope is a page, and recall reaches facts by walking the page tree. Delete the page and the fact is not wrong, it is unreachable, and nothing says so. The repair moves it to a scope recall does reach.

A fact filed under the folder project instead of its repo. Facts used to be filed under the broadest folder project, so every repo in that folder shared one pool. New facts go to their repo. The repair moves an old one when the file it cites exists in exactly one repo below the project, or the session that taught it belongs to one. A fact with neither stays where it is, still reachable from every repo below.

A citation that stopped resolving. A fact can carry a source_ref like path/to/file.ts:98, and the point of it is that your AI tool checks the code before trusting the claim. Once the file moves or goes, that check costs a lookup and teaches nothing; worse, paths get reused, so an old ref eventually resolves against an unrelated file. The repair drops the citation and keeps the claim.

A citation whose project folder is not on this machine is reported as not judged, never as stale — that is a fact about this computer. Press Show what would change before repairing; it lists the files it could not find and each fact it would move, with the repo it would move to.

The panel also reports what it will not touch, because each is a judgement rather than a fault: facts recall has never returned, facts longer than a sentence, facts with no tags, and exact duplicates. That last one watches the write path — dedup runs on every write, so a duplicate count that climbs means something stopped working.

Nothing here runs on its own. Whether a citation resolves depends on what is checked out right now, so a repair that swept at startup would strip good citations the first time you worked from a different checkout.

Recall does not wait for the repair. A fact whose cited file is gone is left out of what sessions receive, and Memory marks it cited file gone. See Recall & Remember.

Repairing memory by hand

The list in Memory has two repairs the store cannot make for itself:

  • Needs review. A claim that contradicts a fact Slate holds more firmly is held here, never written over it. Choose Keep existing, Replace it or Keep both.
  • Retire session. On any fact a session taught, this retires everything that session wrote, after showing each fact. Retired facts stay stored and appear under Show retired.
  • Tidy proposals. Merges and retirements a session proposed during a tidy wait under Needs review too, each with what it would change and why.
  • Pin. The pin on a row puts that fact at the top of its project's index for every session.

In a shared workspace, pulling a teammate's unchanged fact again doesn't count as confirming it. Only its author confirms a fact.
