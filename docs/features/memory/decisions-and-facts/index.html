Decisions & Memories

Slate's long-term memory holds two kinds of knowledge. A decision is a choice you made, kept with its reasoning. A fact is a durable statement that stays true across tasks. Recall memories to know what is so. Read decisions to know why you chose what you did.

Decisions

record_decision needs title (what was decided), reasoning (why) and confidence (high, medium or low). It also takes alternatives, outcome and source_ref. It writes a decision memory and a decision doc with the full reasoning. The memory's confidence is 0.95, 0.8 or 0.6 for high, medium and low. recall ranks a decision first when a question asks why.

remember also stores a memory as a decision when the text reads like one and no kind is given. A remember call with kind: "decision" must carry its reason, as reason or in the sentence. Without one it is refused, because a decision without its reason cannot be weighed later.

A decision learns what came of it

When an agent run relied on a decision, the decision gets its outcome by itself. "Relied on" means the decision was in the run's brief and the run's session cited it. A decision only in the brief, and not cited, is left alone.

  • Pull request merged. The decision's doc gets a line under Outcome, such as Shipped in "Fix the invoice rounding" (link), 2026-10-14. Its memory carries the same line.
  • Closed without merging. The line says Not shipped. Mark done on that run afterwards adds no Shipped: only a merge says the work went out.
  • Reverted within 30 days. For a merged GitHub pull request, Slate adds Reverted: "…" was undone in (link). It counts a revert only on exact evidence: a merged pull request that names this one as reverted (GitHub's Revert button writes that), or a commit saying "This reverts commit" with the merge's commit id (git revert writes that).

Slate checks once an hour, through your own gh. GitLab merge requests are not checked. The first line replaces "To be determined."; later ones are added beside it, so the doc keeps the history. The same line is never written twice.

Memories

Each memory carries:

AttributeMeaning
textThe knowledge.
kinddecision, preference, state, fact or lesson.
triggerFor a lesson: when it is given to a session, a command pattern or file glob. See Lessons.
confidenceHow strongly it is held. Near-duplicates strengthen it.
statusactive or superseded.
subjectThe slot it asserts about, when it has one. See Slots.
origin, origin_toolWho wrote it: person (you, in the app) or agent, and which tool. Empty on memories written before this was recorded.
pinnedYou pinned it, so every session in its project starts with it.
last_used_atWhen a session last cited it by ref.
source_hashA fingerprint of the cited lines (or the whole file, for a bare file) when written, so a later change to that code can be flagged.

recall ranks memories lexically: BM25 between your query and the memory's sentence, tags, citation and reason, lifted a little for recency, scaled by confidence, and re-ordered by word statistics fitted on your own memories. When nothing covers enough of the query, recall returns no memories. Nothing is stored for it and no model is called. Knowledge that no longer holds is superseded by what replaced it, not removed, so the record survives.

What a project keeps

Each project says what Slate keeps from the agents, automations and apps working in it. Open the project's settings and find Memory:

  • Keep: a preset. The workspace default, Decisions and lessons only, or Every kind, from every writer.
  • Advanced: which kinds are kept, which writers may save (agents, Slate's automations and tasks, apps, the agents' own memory files), words a memory may never mention, and whether this project's sessions are captured at all.

Each setting says where it comes from: set here, from a group above, from the workspace, or the default. A word banned higher up stays banned here. A refused memory is not saved, and the agent is told why. What you save yourself in the app, and a proposal you accept, is never filtered. A new policy changes what is saved from now on. Memories already kept stay.

Shelf life: when a memory stops being offered

A state memory says where a thread stands now, so it goes stale. Fourteen days after its last confirmation it leaves the recall pool: no session, automation or recall offers it. Only recall with as_of still reads it.

Nothing is retired or removed. The memory stays active in the store and in the Memory list, and does not appear under the retired chip. Restating or confirming it restarts the 14 days. The clock runs from the last confirmation, not from when it was written, so a state that keeps proving true keeps living.

Only state has a shelf life. A decision and its reasoning stay worth knowing, a fact stays true, and a preference you have not restated in a year is one you still hold.

Resting: when a memory leaves the index

A memory no session has used or restated for 30 days rests. It leaves the index that sessions start with, and stays stored and searchable with recall. Citing it, restating it or pinning it wakes it. Pinned memories and preferences never rest.

Memories an earlier version evicted for never being used keep that mark. Writing the same memory again brings one back.

Slots: how a memory replaces another

A preference and a state are single-valued: you hold one preference per axis, and a thread is in one state. A new one should retire the old. Similarity cannot decide that. "Dark theme" and "light theme" share no words, and a contradiction often looks more similar than a restatement.

A slot settles it. It is a stable dotted key naming the axis, such as ui.theme, deps.db-boundary or branch.slate.main.state. A later memory on the same slot retires the earlier one.

The writer passes the key as subject: two or more parts joined by dots, no spaces, no date. Slate keeps it as written. A subject that is not a key (a branch name, a dated snapshot, a title with spaces) is dropped, and the memory is deduplicated by similarity instead.

An agent must pass a key for a state, or the memory is refused. For a preference the key is optional. With none, Slate uses a slot the project already uses, but only when the text clearly names it. It never invents a key. Decisions, lessons and plain fact memories never take a slot. They accumulate, because replacing them would discard knowledge that is still true.

Memories Slate writes for itself

Almost every memory is written by an agent calling remember. One is not. Slate derives a state memory for each branch carrying uncommitted work, from the same data as Parked work: one per branch, on the slot branch.<repo>.<branch>.state, refreshed when the server starts.

A branch whose work has all landed produces nothing, because git log -1 already answers it. Work in your index or working tree is different: no commit records it. Each new reading supersedes the last. A branch you commit simply stops producing one, and an abandoned branch fades after 14 days (Shelf life).

Is the corpus still worth trusting?

Memories accumulate, and two ways of going bad are invisible from outside. Are memories reachable? measures both and can repair them. It is an Activity widget, hidden until you add it from Edit.

A memory filed under a doc you removed. A memory's scope is a doc, and recall reaches memories by walking the doc tree. Remove the doc and the memory is unreachable, and nothing says so. The repair moves it to a scope recall reaches.

A memory filed under the folder's group instead of its project. Memories used to be filed under the group, so every project in it shared one pool. New ones go to their project. The repair moves an old one when the file it cites exists in exactly one project below the group, or the session that taught it belongs to one. Otherwise it stays, still reachable from every project below.

A citation that stopped resolving. A memory can carry a source_ref like path/to/file.ts:42, so your agent can read the code before trusting the claim. Once the file moves or goes, the check teaches nothing. Paths also get reused, so an old ref can resolve against an unrelated file. The repair drops the citation and keeps the claim.

A citation whose project folder is not on this machine is reported as not judged, never as stale. Press Show what would change before repairing. It lists the files it could not find and each memory it would move, with the project it would move to.

The panel also reports what it will not touch, because each is a judgement: memories recall has never returned, memories longer than a sentence, memories with no tags, and exact duplicates. Dedup runs on every write, so a climbing duplicate count means something stopped working.

Nothing here runs on its own. Whether a citation resolves depends on what is checked out now, so a repair at startup would strip good citations the first time you worked from a different checkout.

Recall does not wait for the repair. A memory whose cited file is gone is left out of what sessions receive, and Memory marks it cited file gone. See Recall & Remember.

Repairing memory by hand

The list in Memory has repairs and controls the store cannot make itself:

  • Needs review. A claim that contradicts a memory Slate holds more firmly is held here, never written over it. Choose Keep existing, Replace it or Keep both.
  • Retire session. On any memory a session taught, this retires everything that session wrote, after showing each one. Retired memories stay stored, and the retired chip lists them for 30 days.
  • Tidy proposals. Merges and retirements a session proposed during a tidy wait under Needs review, each with what it would change and why. The to review row opens to say what waits and who proposed it. Accept all applies every proposal, with Undo. The Memory icon on the rail counts what waits.
  • Pin. The pin on a row puts that memory at the top of its project's index for every session.
  • Hide from sessions. A hidden memory stays stored and listed in Memory, but Slate does not give it out: not to a session, not to a teammate in a shared workspace (one already shared is withdrawn), not to AI memory care, not in an @-mention, not to an app. Its words were also copied into docs when it was saved (Preferences, a branch doc, a note or a decision doc). Those docs stay as you wrote them, and you still see the words. But wherever a doc leaves your hands, to an agent, an app or a teammate, the words become [held memory]. Give to sessions again gives the memory out again, and the copies in docs with it. A memory shared in a workspace is hidden on your other computers signed in to the same account too, from their next sync, and giving it back reaches them the same way. A memory in a workspace you never shared has no cloud copy, so its hide stays on this computer. A teammate sees a hidden memory as one you removed: gone, with no sign it was hidden.

In a shared workspace, pulling a teammate's unchanged memory again does not confirm it. Only its author confirms a memory.
