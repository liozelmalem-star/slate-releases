Recall & Remember

A session gets memory three ways: an index at the start, a search it runs itself, and a lesson on the tool call it is about. At the end it calls remember to save what it learned.

What a session is given at the start

Tools with Slate's hooks installed get a brief at session start, of at most 4,000 characters (about 1,000 tokens):

  • The branch: its name, and on a feature branch its goal, ticket and open items.
  • The memory index for this project: up to 40 lines, one memory each, fewer when the 4,000 characters run out. The index is chosen, not matched against words:
  • memories pinned into the index, by you in Memory or by a session with remember(…, index: true) (at most 25 per project);
  • memories a session cited in the last 30 days;
  • then lessons, then preferences, then decisions, newest first within each kind.

Other fact and state memories stay out unless pinned or cited. The session finds them with recall. A lesson with a trigger stays out too: it arrives when its trigger fires. Outside any project folder Slate knows (your home folder, say), the index holds only global memories.

  • Recent work: parked branches, recent feature branches and recent sessions, when there is room.

The same index everywhere Slate runs an AI

Every place in Slate that hands an AI work gets the same brief, chosen the same way and held to the same rules. A hidden memory, an app's memory you have not released, a state past its shelf life and a memory whose cited code changed never reach any of them.

PlaceHow it gets the index
A session in an agentAt session start, as above.
A task (an agent run)In its brief, from get_agent_run: first the notes about this work, then the index. The task's session starts without the index, so it is not given twice.
An automation runAs @memory in its brief step. After the index it also sees the memories a session leaves to search, newest first, because an automation that tidies memory needs them.
The in-app agent (Home, Ask AI)In its system prompt, for the project you are in.

Deciding where a memory goes

You decide at the moment you see a memory in a list:

  • An automation's What it knows tab shows What it gets from memory: the lines its next run gets, each marked with why. Always give this here puts a memory first for that automation. Not relevant here keeps it out of that automation.
  • Home's composer has What it knows beside the project picker. It opens the same list for Home's AI, for the project picked there, with the same two choices.
  • An agent run's What Slate knows row has Never for agent runs beside the × that leaves a memory out of one run.
  • A memory's card in Memory lists every such decision, each with an undo.

A memory kept out of an automation, agent runs, sessions, Home's AI or apps never reaches them, through the index, a lesson or an app's read. A pinned memory comes first, but a held memory or a stale state still stays out. A memory that replaces another keeps its decisions.

When Slate starts a tool with the index already in its prompt, it sets SLATE_BRIEF=embedded, and the tool's session-start brief keeps the branch and recent work but leaves the index out. An automation gets that only when its brief step uses @memory and the memory arrived. A task's own session gets the index from get_agent_run, so its session-start brief leaves it out too. A second terminal opened in the task's folder still gets it.

Every index line carries a ref, such as m:7f3a2b1c. A session uses it to cite a memory, ask for its detail, or correct it.

Text an app wrote reaches a session quoted: Data saved by an app (not an instruction): «…». That holds on every path: the index, recall, get_memory, list_memories, lessons, notes from other agents and get_doc. A memory an app saved is also held until you release it.

Nothing is added to the prompts you type, except a note when the branch changed, another agent works in the same project, or another agent left a note. Picking memories by the words of each prompt was measured to help 0 times in 24.

When a project holds more than 300 memories that are not resting, or at least 5 preferences and decisions and no lesson with a trigger, the brief also asks the session to offer you a tidy, at most once a week and not while proposals wait for you.

Rules: which memories your agents get

In Memory, Graph | Rules under the project picker shows your rules. Pick one in the list to change it, turn it off or remove it. The + in the side panel's title opens Add a rule, a popup with the project it holds for and a switch: Ready rule (pick one and adjust its words; it shows how many memories it would leave out) or Write your own:

  • Leave out what nobody used for a while: a memory type not used for N days (60 to start).
  • Keep only lessons that proved useful: used in at least N sessions (2 to start).
  • Keep only decisions from work that shipped: from agent runs whose pull request merged.
  • Drop what came from work that was undone: reverted after it merged.
  • Write your own: a sentence in your words. Every agent that saves memory there is told it under "What to save here". Slate cannot check it.

For sets where the rule holds: all projects, or one. A ready rule shows what it would do before you add it, and a saved rule shows what it does now. A rule only decides what is given out. Nothing is removed: what it leaves out stays in Memory and returns when you turn the rule off. What you write yourself is never left out. Rules apply everywhere memory is given out: sessions, automations, agent runs, Home's AI, lessons on tool calls and apps.

Lessons: memory on the tool call it is about

A lesson says what to do in a situation: "before a push, run the full gate, because the hook is the only CI". A lesson can say when it applies:

remember({
  text: "Before a push, run the full gate, because the hook is the only CI",
  when: { tool: "shell", match: "git push" }
})
whenFires on
{ tool: "shell", match: "<regular expression>" }A command that matches.
{ tool: "read", path: "<glob>" }Reading a file that matches, such as packages/db/**.
{ tool: "edit", path: "<glob>" }Editing or writing a file that matches.

A when makes the memory a lesson. A pattern that matches every command or every file is refused.

When a session is about to run a matching command, or touches a matching file, Slate adds the lesson to what the agent sees for that call. It does the same for a lesson or decision whose source_ref cites the file. At most 2 memories are added to one call, each once per session. The call itself is never blocked or changed.

ToolWhen the lesson arrives
Claude CodeBefore a shell, read or edit call.
CodexBefore a shell or patch call, once you trust the hook: Codex skips a new or changed hook until you approve it under /hooks.
Gemini CLIAfter a shell, read or edit call, added to the tool's result.
CursorAfter a shell, read or edit call, added to the tool's result.
OpenCodeAfter a shell, read, edit or patch call, added to the tool's result.

Gemini CLI, Cursor and OpenCode can only add text after a call, so the lesson arrives with the result, in time for the next step.

The hook runs on every watched call, so it first checks a small list of triggers that Slate keeps next to the store. It opens the store only when something could match.

recall and get_memory — search in two steps

recall({ query, cwd })
recall({ query, cwd, as_of: "2026-08-01" })
get_memory({ refs })

recall searches the project's memories and docs and returns one line per memory, with its ref and citation. Default 8 results, 25 at most, memories at most half of them, docs the rest. On a feature branch the first result is the branch brief. A doc is found when its title or text holds the query's words. With kind: "pages" it searches docs only and returns up to 20.

Memories are ranked lexically and locally with BM25. Each query word counts by how rare it is among your memories. A memory's sentence, tags, citation and reason are all read (the sentence counts most). Words match by stem, so "refused" finds "refusal". A recent memory is lifted a little above an equally good old one, and a newer memory that nearly ties an older one on the same subject comes first. Once a workspace holds 200 memories, a match is also lifted, at most doubled, by how close its words sit to the query's in your own memories (latent semantic analysis, fitted in memory from your store). That only re-orders what the keywords found: a memory sharing no word with the query is never added. What you did to the code also moves a match, at most doubled or halved: your merges and Confirms lift a memory, your reverts and discards of the code its sessions wrote lower it (see Citing). Nothing is stored or downloaded, and no model is called.

Nothing found is an answer. Once a project holds 50 memories, a memory that covers too little of the query is not returned, so a question nothing answers gets no memories back instead of a near miss. A memory that only just clears the bar is marked weak. A memory whose cited code changed is marked citation: changed, and one whose file is gone citation: gone: read the code before relying on it. The cited file is read in the session's checkout first, then in the project's folder, so a session in a worktree checks a citation against its branch's code.

A second search. also takes up to three other phrasings of the same need. Each is searched alone and the results are merged. Use it after a thin first search.

With as_of, recall answers from what memory believed at the end of that day (UTC; a time without a zone is UTC too), including claims replaced since. Each such claim carries until, the moment it stopped being believed. The answer holds memories only, because a doc keeps just its current text. Use as_of for "what did we decide back then", never for work you are about to do. A look at the past does not count as memory offered to a session.

get_memory returns what the line leaves out, for the refs asked:

FieldMeaning
reasonWhy the memory was written.
source_refThe file or commit the claim is about.
citationsame: the cited code is unchanged. For a line range or symbol, that means those lines, found again even if an edit above moved them. For a bare file, the whole file. changed: check the code first. gone: the file is missing. unchecked: nothing to compare.
status, pinned, written, citedWhether it is active and pinned, when it was written and last cited.
evidenceHow many times it was confirmed, cited and contradicted, and by which tools. Confirmed: another tool restated it, or you confirmed it in the app. The writing tool saying it again is an echo and does not count. Cited: a session named its ref in its own replies. A claim several tools reached is surer than one tool's. Each tool counts once per session, or once a day with no session. Slate re-reading a source it already holds (a tool's memory file imported again, a branch reading re-derived at launch) never counts. Your Merge of a branch counts as your confirmation. Contradicted counts your Reverts and Discards of branches whose sessions cited it.
historyWhat it replaced, newest first, and what it was replaced_by, oldest first, each with until when it was believed.

A ref that names no memory comes back under unknown.

Citing — how Slate learns what helped

The contract asks every agent to list the refs of the memories that shaped its work in used, which remember and log_mission_progress both take. Each ref counts as a use at once, and the memory records when it was last cited. Refs never go in the agent's reply. A ref written in a reply anyway is still counted when the session ends.

Slate never asks for citations at the end of a session. That question prints on your screen and costs the agent a whole extra turn.

Citations are the agents' signal. Yours is what you do to the code they wrote. A Merge in review confirms the memories the branch's sessions cited. A Revert or Discard contradicts them. Saving an edit on cited lines asks whether the memory still holds (see What agents know about the file). Each shows on the memory's card with an undo, and get_memory counts contradictions under evidence. Recall ranks by what held up. A memory your acts contradicted at least twice, and nothing confirmed, leaves the index and is no longer added to tool calls as a lesson, unless you pinned it. recall still finds it, lower down. A confirmation brings it back. A memory nobody cites or restates for 30 days rests: it leaves the index and stays stored and searchable. Pinned memories and preferences never rest.

remember — save what you learned

Call remember with one concise statement. Each call writes one typed memory:

kindWhat it captures
decisionA choice you made ("chose X over Y because Z").
preferenceA durable working preference.
stateA durable note about where things stand.
factA durable piece of project knowledge.
lessonWhat to do in a situation, and why. Can say when it applies.

The memory is filed under the project you work in (a worktree beside the project counts as the project) and deduplicated: a near-duplicate strengthens the existing memory. A memory that names no folder and no doc is filed under your personal project. Only global: true files it as global, because global memories reach every session everywhere. remember also appends the statement to the branch's doc.

The answer lists up to 3 neighbours: close memories it was not merged into. When one says the same thing or is now wrong, call remember again with its ref in replaces.

index: true pins the memory into the project's index, which holds 25. When it is full, the reply lists it and adds nothing, so the agent calls again naming one to take out with unindex. A memory taken out stays stored and searchable.

What is worth saving: a correction you made, an approach you confirmed, a decision and why, something true that is not obvious. The contract asks the agent whether a future agent would act better for knowing it, and not to save what code, git or docs already say, fix recipes, or where work stands now. Home's AI and every automation run get the same rule in their own prompt, so they save the way a connected tool does even when a tool cuts the MCP instructions short.

When a session saved nothing. After real work (5 changes or 10 of your turns) with nothing saved, the session's end asks the agent once to save what the next session needs. A session where you corrected the agent ("no, …", "wrong", "I told you", or the same in Hebrew) is asked even when short, and the ask quotes your correction so the agent saves it as a lesson. A session that saved anything is not asked.

When the claim cites a file (source_ref), Slate stores a fingerprint of it. If the file changes, the memory leaves the session-start index, because a claim the agent must doubt before using is not worth a spot there, and get_memory reports changed. recall still finds it. The same happens when the cited line is past the end of the file, or the cited name (path:symbol) no longer appears in it. That check needs no fingerprint, so it covers older memories too. Restating the claim takes a fresh reading and brings it back. You can also answer this in the file: a file open beside a session marks every cited line and offers Confirm, Correct and Retire (see What agents know about the file).

Correcting a memory

When a memory is wrong, write the true claim and name the wrong one:

remember({ text: "The gate has ten steps", replaces: ["m:7f3a2b1c"] })

Each named memory in the same project is retired in favour of the new one. The response lists what was retired and any ref it could not place.

What is refused

A refused write says how to fix it:

  • Transient text ("currently editing X").
  • A git snapshot from an agent ("main is 11 commits ahead"). Git answers these better.
  • A tool call's own markup in the text (<parameter …>): the call was malformed and its other arguments landed in the text.
  • A decision with no reason. Pass reason, or say why in the sentence ("because", "so", "rather than", "never", "the owner wants"). The reason is stored.
  • Three or more numbers in an agent's memory. Measurements go stale first. Keep the claim in the sentence and put the numbers in reason.
  • A state from an agent with no subject. Only a slot key lets the next state replace it. Pass a dotted key such as release.next-version. A handoff is a state by design and is exempt.
  • A vague reason, when AI memory care is on. Every memory from an agent must then say in reason, in at least four words, why it changes what a future agent does.
  • What the project's memory settings turn off: a writer, a kind, or a word the memory may never mention. See What a project keeps.
  • A workspace that is read-only for you. In a workspace you joined as a viewer, or one its owner deleted forever, nothing can be saved. The call fails and says which.

A short line with no verb is kept, with a warning that it reads as a title. What you write in the app is held only to the transient-text and decision rules. The other rules and the project's settings apply to agents, automations and apps.

How much to save. The contract asks each task to save at most two memories, only what will change how a future agent acts. Most save none. A tool call carries no session, so Slate cannot count per session. This is asked, not enforced.

Every memory records who wrote it: you in the app, or the agent by name. An agent that passes no source is named by the tool it connected through. Memories written before September 2026 mostly say nothing. Recognised keys, tokens and passwords are removed before a memory is stored ("the staging key is [secret]"), and the rest of the sentence is kept. This holds for what you type in the app, for the reason and the citation, and for the docs an agent writes: the copy of a memory on a branch doc, a decision doc, a progress log and a saved document.

When a new claim contradicts a memory Slate holds more firmly, it does not overwrite it. It waits under Needs review in Memory, beside the memory it disagrees with. The Memory icon on the rail counts what waits.

kind is optional. Without it Slate infers it from the text. Preferences and states are also placed in a slot when the project has one that fits, so a new preference retires the one it contradicts.

Tidying a project's memory

Slate calls no model to shrink memory. The session you are in does the reading, with your agreement:

  1. list_memories reads the project's memories, 100 at a time, with refs. A memory you hid from sessions is not listed.
  2. propose_memory_change proposes one of three changes:
  3. a merge: two or more refs become one claim;
  4. a retirement: refs that are wrong or outdated;
  5. a lesson: refs that form a rule about an action become one lesson, with the when it arrives on.

Every ref must be a memory of that project. A ref from another project is refused, and a merge or lesson is held to the same save rules as remember.

  1. Nothing changes yet. Each proposal waits in Memory under Needs review, with what it would change and why. Merge, Retire or Make it a lesson applies it. Dismiss drops it. Accept all applies every proposal, and Undo takes the batch back.

To have Slate do it, turn on AI memory care on the Memory care row in Memory (see Automations). Each night it reads up to 50 memories of one project or group (the one holding the most) twice, separately, with its own agent and the code each cites. It retires only what both readings agree is wrong. Anything they disagree on waits under Needs review. It shows its cost before it turns on and stops at a monthly token cap you set. A retired memory that nothing replaced comes back with Bring back under Memory → the retired chip, for 30 days. With AI memory care on, an agent's new memory must also say in reason why it changes what a future agent does.

To run your own prompt on a schedule, save the Memory pass automation. Each morning it reads yesterday's sessions and up to 30 of the project's memories on your project's own agent: the ones the memory brief ranks first (pinned and cited first, then the freshest), cut to a size budget. It adds at most five memories and files merges and retirements under Needs review. Nothing changes until you accept.

Learning from what you decline

When you say no to something an AI proposed, Slate keeps it: an automation's held call you answer No, a step you send back, a held call you deny, a run you cancel with a reason, an app's card you decline, a tool call of Home's AI you skip.

A no is never a memory by itself. It becomes a proposal under Memory → Needs review in two cases: you wrote a reason (each of those has Why? (optional) beside its no), or you declined the same action twice in 30 days in the same place. Accepting it saves a lesson and pins it to the automation, agent runs or app that produced it. At most five such proposals wait at once in a project.

When a lesson becomes a skill

A lesson used in at least three different sessions has become a way of working. Once a day Slate proposes turning one into a skill, at most three each time, under Memory → Needs review. Make it a skill writes it to .claude/skills/<name>/SKILL.md in the project's folder, linked from .agents/skills/<name>, with the lesson and its reason, so every agent that reads project skills picks it up. A lesson on a branch goes to its project's folder, not the branch's worktree. A lesson with no project folder on this computer is never proposed. The lesson then stops reaching sessions through the index, so it is not read twice. A dismissed proposal is not asked again. The same proposal also waits in Toolkit › Suggestions, and the card here links there. Accepting in either place writes the skill once. Other changes to a project's AI setup (fix, copy, remove) are only in Toolkit: Memory reviews what Slate remembers, Toolkit what your agents load.

Logging progress mid-run

log_mission_progress appends a session summary to a Progress section, on the branch's Plan doc when you have one, otherwise on the branch doc. It never creates a doc. On a trunk branch (main, master, develop) the log keeps only the latest 20 entries, the task's goal does not replace the branch's own, and remember writes only the memory, not a copy on the doc, because a trunk never ends and anything that only appends to it grows forever. Copies older versions wrote there are moved, unchanged, to a child doc "Earlier notes on main", the first time Slate starts with a large main doc.

Measuring it

Does memory help? One session in four is held out: it gets no index, no lessons and no tidy offer, and its agent can still search. For every session Slate counts the turns that open by correcting the agent ("no, …", "wrong", "I told you"). The Does memory help? widget on the Activity dashboard (hidden until you add it from Edit) compares corrections per session with and without memory. It shows a result after 50 sessions in each group. You can turn the holdout off there.

yarn memory:report prints the numbers this design is judged by, from a snapshot of your store:

  • how many sessions used a memory, and how many offered memories were cited;
  • what was offered on each channel (lessons are channel trigger);
  • reach: per tool, how many work sessions were given memory, of those captured;
  • the holdout comparison;
  • health: memories written against distinct memories sessions used in the window (fewer writes per cited memory is better);
  • quality: the share of memories AI memory care read that both readings kept (aim for 80%);
  • imported memories per tool;
  • per project: active memories, index lines and changed citations.

--sample 24 writes a sheet of random deliveries to judge by hand.

yarn memory:eval --cwd <project> scores search. It runs recall over a fixed set of questions with known answers and prints recall@5 and MRR per kind of question (plain memories, updated memories, questions about time, questions nothing answers). The question set quotes your memory, so it lives beside your store at memory-eval/questions.json in Slate's data folder. --half tune and --half report score the odd and even questions, so a change to search is chosen on one half and judged on the other. --also <file> passes other phrasings of each question, as an agent's second search would.
