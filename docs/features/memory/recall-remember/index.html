Recall & Remember

A session gets memory three ways: an index at the start, a search it runs itself, and a lesson on the tool call it is about. At the end it calls remember to save what it learned. Everything else — capture, filing, ranking — is built around those calls.

What a session is handed at the start

Tools with Slate's hooks installed get a brief when a session starts, of at most 4,000 characters (about 1,000 tokens):

  • The branch: its name, and on a feature branch its goal, ticket and open items.
  • The memory index for this project: up to about 25 lines, one memory each. The index is chosen, not matched against words:
  • memories pinned into the index, by you in Memory or by a session with remember(…, index: true) — at most 25 per project;
  • memories a session cited in the last 30 days;
  • then lessons, preferences and decisions, newest first within each kind.

Other facts and state memories stay out unless pinned or cited; the session finds them with recall, and where a thread stands is the branch's to say. A lesson with a trigger stays out too: it arrives when its trigger fires. Outside any project folder Slate knows (your home folder, say), the index carries only global memories.

  • Recent work: parked branches, recent feature branches and recent sessions, when there is room.

Every index line carries a ref, such as m:7f3a2b1c. The ref is how a session cites a memory, asks for its detail, or corrects it.

Nothing is added to the prompts you type. A prompt still gets a note when the branch changed, another agent is working in the same project, or another agent left a note. It never gets memory: picking memories by the words of each prompt was measured to help 0 times in 24.

When a project holds more than 300 active memories, or at least 5 preferences and decisions and no lesson with a trigger, the brief also asks the session to offer you a tidy, at most once a week.

Lessons: memory on the tool call it is about

A lesson says what to do in a situation: "before a push, run the full gate, because the hook is the only CI". A lesson can say when it applies:

remember({
  text: "Before a push, run the full gate, because the hook is the only CI",
  when: { tool: "shell", match: "git push" }
})
whenFires on
{ tool: "shell", match: "<regular expression>" }A command that matches.
{ tool: "read", path: "<glob>" }Reading a file that matches, such as packages/db/**.
{ tool: "edit", path: "<glob>" }Editing or writing a file that matches.

A when makes the memory a lesson. A pattern that matches every command or every file is refused.

When a session is about to run a matching command, or touches a matching file, Slate adds the lesson to what the agent sees for that call. It does the same for a lesson or decision whose source_ref cites the file. At most 2 memories are added to one call, and each one only once per session. The call itself is never blocked or changed.

ToolWhen the lesson arrives
Claude CodeBefore a shell, read or edit call.
CodexBefore a shell or patch call, once you trust the hook: Codex skips a new or changed hook until you approve it under /hooks.
Gemini CLIAfter a shell, read or edit call, added to the tool's result.
CursorAfter a shell, read or edit call, added to the tool's result.
OpenCodeAfter a shell, read, edit or patch call, added to the tool's result.

Gemini CLI, Cursor and OpenCode can only add text after a call, so there the lesson arrives with the result, in time for the next step.

The hook runs on every watched call, so it first checks a small list of triggers that Slate keeps next to the store. It opens the store only when something could match.

recall and get_memory — search in two steps

recall({ query, cwd })
recall({ query, cwd, as_of: "2026-08-01" })
get_memory({ refs })

recall searches the project's memories and pages and returns one line per memory, with its ref and citation. On a feature branch the first result is the branch brief. Results are ranked lexically and locally: keyword coverage, recency and confidence. Once a workspace holds 200 memories, a match is also lifted, at most doubled, by how close its words sit to the query's in your own memories (latent semantic analysis, fitted in memory from your store). This only re-orders what the keywords found; a memory sharing no word with the query is never added. Nothing is stored, nothing is downloaded, and no model is called.

With as_of, recall answers from what the memory believed at the end of that day (UTC; a time without a zone is UTC too), including claims replaced since. Each claim replaced since carries until, the moment it stopped being believed. The answer holds memories only: a page keeps just its current text, so there is no past version of it to offer. Use as_of for "what did we decide back then", never for work you are about to do. A look at the past does not count as memory offered to a session.

get_memory returns what the line leaves out, for the refs the agent asks about:

FieldMeaning
reasonWhy the memory was written.
source_refThe file or commit the claim is about.
citationsame: the cited file is unchanged since the memory was written. changed: check the file before relying on the claim. gone: the file is missing. unchecked: nothing to compare.
status, pinned, written, citedWhether it is still active, pinned, when it was written and last cited.
evidenceHow many times it was confirmed and cited, and by which tools. Confirmed means another tool restated it, or you confirmed it in the app; the tool that wrote it saying it again is an echo and does not count. Cited means a session named its ref in its own replies. A claim several tools arrived at is surer than one only one tool wrote. Each tool counts once per session, or once a day when there is no session, and Slate re-reading a source it already holds (a tool's memory file imported again, a branch reading re-derived at launch) never counts.
historyWhat it replaced, newest first, and what it was replaced_by, oldest first, each with until when it was believed.

A ref that names no memory comes back under unknown.

Citing — how Slate learns what helped

The contract asks every agent to name the ref of any memory that shaped its work, for example "per m:7f3a2b1c". When the session ends, Slate reads the agent's own replies (not the text it was handed) and counts each ref it finds as a use. The memory records when it was last cited.

Agents rarely cite unasked, so the Stop hook asks once. When a session was given memory, has done some work (an edit, or three turns) and has named none of it, the hook asks which memories it relied on, answered with refs or memory: none. It asks at most once per session, after any nudge to save memory, in every tool whose end-of-turn hook can hold the turn — Claude Code, Codex and Gemini CLI, and Cursor as soon as its stop hook enforces. OpenCode's is record-only, so it is never asked.

That citation is the only use signal. A memory nobody cites or restates for 30 days rests: it leaves the index, and stays stored and searchable. Pinned memories and preferences never rest.

remember — save what you learned

Call remember with one concise statement. Each call writes one typed memory — the unit every AI tool shares:

kindWhat it captures
decisionA choice you made ("chose X over Y because Z").
preferenceA durable working preference.
stateA durable fact about where things stand.
factA durable piece of project knowledge.
lessonWhat to do in a situation, and why. Can say when it applies.

The memory is filed under the repo you are working in (a worktree beside the repo counts as the repo) and deduplicated against what is already known: a near-duplicate strengthens the existing memory. A memory that names no folder and no page is filed under your personal project; only global: true files it as global, because global memories reach every session everywhere. remember also appends the statement to the branch's page, so you can read it back by hand.

A new memory is answered with up to 3 neighbours: close memories it was not merged into. When one says the same thing or is now wrong, call remember again with its ref in replaces.

index: true pins the memory into the project's index. The index holds 25; when it is full, the reply lists it and nothing is added, so the agent calls again naming one to take out with unindex. A memory taken out stays stored and searchable.

What is worth saving: a correction you made, an approach you confirmed, a decision and why, a non-obvious fact. The contract asks the agent first whether a future agent would act better for knowing it, and not to save what the code, git or the docs already say, fix recipes, or where the work stands now.

When the claim cites a file (source_ref), Slate stores a fingerprint of that file. If the file changes later, the index line says cited code changed since; check it, and get_memory reports changed. The same happens when the cited line is past the end of the file, or the cited name (path:symbol) no longer appears in it; that check needs no fingerprint, so it covers older memories too. Restating the claim takes a fresh reading.

Correcting a memory

When a memory turns out to be wrong, write the true claim and name the wrong one:

remember({ text: "The gate has ten steps", replaces: ["m:7f3a2b1c"] })

Each named memory in the same project is retired in favour of the new one. The response lists what was retired and any ref it could not place.

What is refused

Some writes are refused, and the refusal says how to fix them:

  • Transient text ("currently editing X").
  • A git snapshot from an AI tool ("main is 11 commits ahead", "carries 10 files uncommitted"). Git already answers these better.
  • A decision with no reason. Pass reason, or say why in the sentence ("because", "so that", "rather than"). The reason is stored with the decision.

Every memory records who wrote it: you in the app, or the AI tool by name. An agent that does not pass source is named by the tool it connected through. Memories written before this was recorded, in September 2026, mostly say nothing, rather than guess. Keys and tokens are taken out before a memory is stored (for example "the staging key is [secret]"), and the rest of the sentence is kept.

When a new claim contradicts a memory Slate holds more firmly, it does not overwrite it. It waits under Needs review in Memory, beside the memory it disagrees with.

kind is optional; omit it and Slate infers it from the text. Preferences and states are also placed in a slot when the project already has one that fits, which lets a new preference retire the one it contradicts.

Tidying a project's memory

Every major coding tool shrinks its memory over time. Slate calls no model to do it, so the session you are in does the reading, with your agreement:

  1. list_memories reads the project's memories, 100 at a time, with their refs.
  2. propose_memory_change proposes one of three changes:
  3. a merge: several refs become one claim;
  4. a retirement: refs that are wrong or outdated;
  5. a lesson: refs that are a rule about an action become one lesson, with the when it is handed over on.
  6. Nothing changes yet. Each proposal waits in Memory under Needs review, with what it would change and why. Merge, Retire or Make it a lesson applies it; Dismiss drops it.

To have it done on a schedule instead, save the Memory pass routine. Each morning it reads yesterday's sessions and the project's 30 newest memories on your project's own AI tool. It adds at most five new memories, and files merges and retirements under Needs review, where nothing changes until you accept.

Logging progress mid-mission

Between the start and the end of a longer piece of work, log_mission_progress appends a session summary to a Progress section — on the branch's Plan page when you have one, otherwise on the branch page — so a mission accumulates a running record of what happened. It never creates a page.

Measuring it

Does memory help? One session in ten is held out: it gets no memory index, no lessons and no tidy offer, and its agent can still search. For every session, Slate counts the turns that open by correcting the agent ("no, …", "wrong", "I told you"). The Does memory help? widget on the Activity dashboard (hidden until you add it from Edit) compares corrections per session with memory and without it. It shows a result only after 50 sessions in each group. You can turn the holdout off there.

yarn memory:report prints the numbers this design is judged by, from a snapshot of your store: how many sessions cited a memory, and how many of the memories offered were cited; what was offered on each channel (including lessons, on channel trigger); reach, which is per tool how many work sessions were handed memory out of those captured; the holdout comparison; imported memories per tool; and per project the active memories, index lines and changed citations. --sample 24 writes a sheet of random deliveries to judge by hand.

yarn memory:eval --cwd <repo> scores search: it runs recall over a fixed set of questions with known answers and prints recall@5 and MRR, per kind of question (plain facts, updated facts, questions about time, and questions nothing answers). The question set quotes your memory, so it lives beside your store, at memory-eval/questions.json in Slate's data folder, and not in the repo.
