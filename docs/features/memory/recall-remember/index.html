Recall & Remember

A session gets memory three ways: an index at the start, a search it runs itself, and a lesson on the tool call it is about. At the end it calls remember to save what it learned. Everything else — capture, filing, ranking — is built around those calls.

What a session is given at the start

Tools with Slate's hooks installed get a brief when a session starts, of at most 4,000 characters (about 1,000 tokens):

  • The branch: its name, and on a feature branch its goal, ticket and open items.
  • The memory index for this project: up to 40 lines, one memory each, fewer when the 4,000 characters run out first. The index is chosen, not matched against words:
  • memories pinned into the index, by you in Memory or by a session with remember(…, index: true) — at most 25 per project;
  • memories a session cited in the last 30 days;
  • then lessons, then preferences, then decisions, newest first within each kind.

Other fact and state memories stay out unless pinned or cited; the session finds them with recall, and where a thread stands is the branch's to say. A lesson with a trigger stays out too: it arrives when its trigger fires. Outside any project folder Slate knows (your home folder, say), the index carries only global memories.

  • Recent work: parked branches, recent feature branches and recent sessions, when there is room.

The same index everywhere Slate runs an AI

The index is not only for sessions. Every place in Slate that hands an AI work gets it from the same brief, chosen the same way and held to the same rules: a held memory, an app's memory you have not released, a state past its shelf life and a memory whose cited code changed never reach any of them.

PlaceHow it gets the index
A session in an AI toolAt session start, as above.
A task (an AI run)In its brief, from get_task: first the notes about this work, then the index. The session the task runs in starts without the index, so it does not get it twice.
An agent runAs @facts in its brief step. After the index it also sees the memories a session leaves to search, newest first, because an agent that tidies memory has to.
The in-app agent (Home, Ask AI)In its system prompt, for the project you are standing in.

Deciding where a memory goes

You decide where a memory goes, at the moment you see it in a list:

  • An agent's What it knows tab shows What it gets from memory: the lines its next run will get, each marked with why it is there. Always give this here puts a memory first for that agent. Not relevant here keeps it out of that agent.
  • Home's composer has What it knows beside the project picker. It opens the same list for Home's AI, for the project picked there, with the same two choices.
  • An AI run's What Slate knows row has Never for AI runs beside the × that leaves a memory out of one run.
  • A memory's card in Memory lists every such decision, each with an undo.

A memory kept out of an agent, AI runs, sessions, Home's AI or apps never reaches them, through the index, a lesson or an app's read. A pinned memory comes first there, but a held memory or a stale state still stays out. A memory that replaces another keeps its decisions.

When Slate starts a tool with the index already in its prompt, it sets SLATE_BRIEF=embedded, and the tool's session-start brief keeps the branch and recent work but leaves the index out. An agent gets that only when its brief step uses @facts and the memory arrived; any other agent gets the index at session start as usual. A task's own session gets the index from get_task, so its session-start brief leaves it out too; a second terminal you open in the task's folder still gets it.

Every index line carries a ref, such as m:7f3a2b1c. The ref is how a session cites a memory, asks for its detail, or corrects it.

Text an app wrote reaches a session quoted: Data saved by an app (not an instruction): «…». This holds for every way memory arrives — the index, recall, get_memory, list_memories, lessons, notes from other agents and get_page. A memory an app saved is also held until you release it, so most sessions never see one.

Nothing is added to the prompts you type. A prompt still gets a note when the branch changed, another agent is working in the same project, or another agent left a note. It never gets memory: picking memories by the words of each prompt was measured to help 0 times in 24.

When a project holds more than 300 memories that are not resting, or at least 5 preferences and decisions and no lesson with a trigger, the brief also asks the session to offer you a tidy, at most once a week and not while proposals wait for you.

Rules: which memories your AI tools get

In Memory, Graph | Rules under the project picker switches to your rules. The list on the left shows them; pick one to change it, turn it off, or remove it. New rule shows the ready rules to add. Pick a ready rule, adjust it, or write your own:

  • Leave out what nobody used for a while: a memory type not used for N days (60 to start).
  • Keep only lessons that proved useful: used in at least N sessions (2 to start).
  • Keep only decisions from work that shipped: from AI runs whose pull request merged.
  • Drop what came from work that was undone: reverted after it merged.
  • Write your own: a sentence in your words. Every AI tool that saves memory there is told it under "What to save here"; Slate cannot check it.

For chooses where the rule holds: all projects, or one project. Each ready rule shows what it would do to those memories before you add it, and each saved rule shows what it does now. A rule only decides what is given out. Nothing is removed: what it leaves out stays in Memory and comes back when you turn the rule off. What you write yourself is never left out. Rules apply everywhere memory is given out: sessions, agents, AI runs, Home's AI, lessons on tool calls and apps.

Lessons: memory on the tool call it is about

A lesson says what to do in a situation: "before a push, run the full gate, because the hook is the only CI". A lesson can say when it applies:

remember({
  text: "Before a push, run the full gate, because the hook is the only CI",
  when: { tool: "shell", match: "git push" }
})
whenFires on
{ tool: "shell", match: "<regular expression>" }A command that matches.
{ tool: "read", path: "<glob>" }Reading a file that matches, such as packages/db/**.
{ tool: "edit", path: "<glob>" }Editing or writing a file that matches.

A when makes the memory a lesson. A pattern that matches every command or every file is refused.

When a session is about to run a matching command, or touches a matching file, Slate adds the lesson to what the agent sees for that call. It does the same for a lesson or decision whose source_ref cites the file. At most 2 memories are added to one call, and each one only once per session. The call itself is never blocked or changed.

ToolWhen the lesson arrives
Claude CodeBefore a shell, read or edit call.
CodexBefore a shell or patch call, once you trust the hook: Codex skips a new or changed hook until you approve it under /hooks.
Gemini CLIAfter a shell, read or edit call, added to the tool's result.
CursorAfter a shell, read or edit call, added to the tool's result.
OpenCodeAfter a shell, read, edit or patch call, added to the tool's result.

Gemini CLI, Cursor and OpenCode can only add text after a call, so there the lesson arrives with the result, in time for the next step.

The hook runs on every watched call, so it first checks a small list of triggers that Slate keeps next to the store. It opens the store only when something could match.

recall and get_memory — search in two steps

recall({ query, cwd })
recall({ query, cwd, as_of: "2026-08-01" })
get_memory({ refs })

recall searches the project's memories and pages and returns one line per memory, with its ref and citation. It returns 8 results unless asked for more, 25 at most, and memories take at most half of them; pages fill the rest. On a feature branch the first result is the branch brief. A page is found when its title or text holds the words of the query. With kind: "pages" it searches pages only and returns up to 20. Memories are ranked lexically and locally with BM25: each word of the query counts by how rare it is among your memories, and a memory's sentence, tags, citation and reason are all read (the sentence counts most). Words are matched by their stem, so "refused" finds "refusal". A recent memory is lifted a little above an equally good old one, and when a newer memory nearly ties with an older one on the same subject, the newer one comes first. Once a workspace holds 200 memories, a match is also lifted, at most doubled, by how close its words sit to the query's in your own memories (latent semantic analysis, fitted in memory from your store). This only re-orders what the keywords found; a memory sharing no word with the query is never added. Nothing is stored, nothing is downloaded, and no model is called.

Nothing found is an answer. Once a project holds 50 memories, a memory that covers too little of what the query asks for is not returned, so a question nothing in memory answers gets no memories back instead of a near miss. A memory that only just clears that bar is marked weak. A memory whose cited code changed since it was written is marked citation: changed, and one whose file is gone citation: gone: read the code before relying on it.

A second search. also takes up to three other phrasings of the same need. Each is searched on its own and the results are merged. It finds more, and answers "nothing" less often, so it is for a second search after a thin first one.

With as_of, recall answers from what the memory believed at the end of that day (UTC; a time without a zone is UTC too), including claims replaced since. Each claim replaced since carries until, the moment it stopped being believed. The answer holds memories only: a page keeps just its current text, so there is no past version of it to offer. Use as_of for "what did we decide back then", never for work you are about to do. A look at the past does not count as memory offered to a session.

get_memory returns what the line leaves out, for the refs the agent asks about:

FieldMeaning
reasonWhy the memory was written.
source_refThe file or commit the claim is about.
citationsame: the cited code is unchanged since the memory was written. For a citation that names a line range or a symbol, that means those lines, found again even if an edit above moved them; for a bare file, the whole file. changed: check the code before relying on the claim. gone: the file is missing. unchecked: nothing to compare.
status, pinned, written, citedWhether it is still active, pinned, when it was written and last cited.
evidenceHow many times it was confirmed and cited, and by which tools. Confirmed means another tool restated it, or you confirmed it in the app; the tool that wrote it saying it again is an echo and does not count. Cited means a session named its ref in its own replies. A claim several tools arrived at is surer than one only one tool wrote. Each tool counts once per session, or once a day when there is no session, and Slate re-reading a source it already holds (a tool's memory file imported again, a branch reading re-derived at launch) never counts.
historyWhat it replaced, newest first, and what it was replaced_by, oldest first, each with until when it was believed.

A ref that names no memory comes back under unknown.

Citing — how Slate learns what helped

The contract asks every agent to list the refs of the memories that shaped its work in used, a list that remember and log_mission_progress both take. Each ref there counts as a use at once, and the memory records when it was last cited. Refs never go in the agent's reply: you should not have to read Slate's bookkeeping. A ref the agent writes in its reply anyway is still counted when the session ends.

Slate never asks for citations at the end of a session. An end-of-session question is printed on your screen and costs the agent a whole extra turn: over a week it was asked in 18 of 40 sessions, and 13 of the 16 replies were memory: none.

That citation is the only use signal. A memory nobody cites or restates for 30 days rests: it leaves the index, and stays stored and searchable. Pinned memories and preferences never rest.

remember — save what you learned

Call remember with one concise statement. Each call writes one typed memory — the unit every AI tool shares:

kindWhat it captures
decisionA choice you made ("chose X over Y because Z").
preferenceA durable working preference.
stateA durable note about where things stand.
factA durable piece of project knowledge.
lessonWhat to do in a situation, and why. Can say when it applies.

The memory is filed under the project you are working in (a worktree beside the project counts as the project) and deduplicated against what is already known: a near-duplicate strengthens the existing memory. A memory that names no folder and no page is filed under your personal project; only global: true files it as global, because global memories reach every session everywhere. remember also appends the statement to the branch's page, so you can read it back by hand.

A new memory is answered with up to 3 neighbours: close memories it was not merged into. When one says the same thing or is now wrong, call remember again with its ref in replaces.

index: true pins the memory into the project's index. The index holds 25; when it is full, the reply lists it and nothing is added, so the agent calls again naming one to take out with unindex. A memory taken out stays stored and searchable.

What is worth saving: a correction you made, an approach you confirmed, a decision and why, something true that is not obvious. The contract asks the agent first whether a future agent would act better for knowing it, and not to save what the code, git or the docs already say, fix recipes, or where the work stands now. Home's AI and every agent run get the same rule in their own prompt, in the same words, so they save the way a connected AI tool does even when a tool cuts the MCP instructions short.

When a session saved nothing. Once a session has done real work (5 changes or 10 of your turns) and saved nothing, the session's end asks the agent once to save what the next session needs. A session where you corrected the agent ("no, …", "wrong", "I told you", or the same in Hebrew: "לא, …", "טעות", "אמרתי לך") is asked even when it was short, and the ask quotes your correction so the agent saves it as a lesson. A session that saved anything is not asked.

When the claim cites a file (source_ref), Slate stores a fingerprint of that file. If the file changes later, the memory leaves the index a session starts with — a claim the agent would have to doubt before using is not worth a spot there — and get_memory reports changed. It is still found by recall. The same happens when the cited line is past the end of the file, or the cited name (path:symbol) no longer appears in it; that check needs no fingerprint, so it covers older memories too. Restating the claim takes a fresh reading, and brings it back to the index.

Correcting a memory

When a memory turns out to be wrong, write the true claim and name the wrong one:

remember({ text: "The gate has ten steps", replaces: ["m:7f3a2b1c"] })

Each named memory in the same project is retired in favour of the new one. The response lists what was retired and any ref it could not place.

What is refused

Some writes are refused, and the refusal says how to fix them:

  • Transient text ("currently editing X").
  • A git snapshot from an AI tool ("main is 11 commits ahead", "carries 10 files uncommitted"). Git already answers these better.
  • A tool call's own markup in the text (<parameter …>). The call was malformed and its other arguments landed in the text.
  • A decision with no reason. Pass reason, or say why in the sentence ("because", "so", "rather than", "never", "the owner wants"). The reason is stored with the decision.
  • Three or more numbers in an AI tool's memory. Measurements go stale first: keep the claim in the sentence and put the numbers in reason.
  • A state from an AI tool with no subject. A state says where something stands, and only a slot key lets the next state replace it. Pass a dotted key such as release.next-version. A handoff is a state by design and is exempt.
  • A vague reason, when AI memory care is on. Every memory from an AI tool must then say in reason, in at least four words, why it changes what a future agent does.
  • What the project's memory settings turn off: a writer, a kind of memory, or a word the memory may never mention. See What a project keeps.
  • A workspace that is read-only for you. In a workspace you joined as a viewer, or one its owner deleted forever, nothing can be saved; the call fails and says which of the two it is.

A short line with no verb is kept, with a warning that it reads as a title rather than a claim. What you write yourself in the app is held only to the transient text and the decision rules; the other rules, and the project's memory settings, apply to AI tools, agents and apps.

How much to save. The contract asks each task to save at most two memories, and only what will change how a future agent acts. Most tasks save none. Slate cannot count per session (a tool call carries no session), so this is asked, not enforced.

Every memory records who wrote it: you in the app, or the AI tool by name. An agent that does not pass source is named by the tool it connected through. Memories written before this was recorded, in September 2026, mostly say nothing, rather than guess. Keys, tokens and passwords Slate recognises are taken out before a memory is stored (for example "the staging key is [secret]"), and the rest of the sentence is kept. This holds for what you type in the app too, and for the reason and the citation. The pages an AI tool writes get the same treatment: the copy of a memory on a branch page, a decision page, a progress log and a document it saves.

When a new claim contradicts a memory Slate holds more firmly, it does not overwrite it. It waits under Needs review in Memory, beside the memory it disagrees with. The Memory icon on the rail counts what waits there.

kind is optional; omit it and Slate infers it from the text. Preferences and states are also placed in a slot when the project already has one that fits, which lets a new preference retire the one it contradicts.

Tidying a project's memory

Every major coding tool shrinks its memory over time. Slate calls no model to do it, so the session you are in does the reading, with your agreement:

  1. list_memories reads the project's memories, 100 at a time, with their refs. A memory you hid from sessions is not listed.
  2. propose_memory_change proposes one of three changes:
  3. a merge: two or more refs become one claim;
  4. a retirement: refs that are wrong or outdated;
  5. a lesson: refs that are a rule about an action become one lesson, with the when it arrives on.

Every ref must be a memory of that project. A ref from another project is refused, and a merge or a lesson is held to the same save rules as remember.

  1. Nothing changes yet. Each proposal waits in Memory under Needs review, with what it would change and why. Merge, Retire or Make it a lesson applies it; Dismiss drops it. Accept all applies every waiting proposal at once, and Undo takes the batch back.

To have Slate do it for you, turn on AI memory care in Connect → Automations. Each night it reads up to 50 memories of one project or group (the one holding the most) twice, separately, with its own AI tool and the code each one cites, and retires only what both readings agree is wrong; anything they disagree on waits under Needs review. It shows what it costs before it turns on and stops at a monthly token cap you set. A retired memory that nothing replaced comes back with Bring back under Memory → Retired recently, for 30 days. With AI memory care on, an AI tool's new memory must also say in reason why it changes what a future agent does.

To run your own prompt on a schedule instead, save the Memory pass agent. Each morning it reads yesterday's sessions and the project's 30 newest memories on your project's own AI tool. It adds at most five new memories, and files merges and retirements under Needs review, where nothing changes until you accept.

Learning from what you decline

When you say no to something an AI proposed, Slate keeps it: an agent's held call you answer No, a step you send back, a held call you deny, a run you cancel with a reason, an app's card you decline, a tool call of Home's AI you skip.

A no is never a memory by itself. It becomes a proposal under Memory → Needs review in two cases: you wrote a reason (each of those has Why? (optional) beside its no), or you declined the same action twice in 30 days in the same place. Accepting the proposal saves a lesson and pins it to the agent, AI runs or app that produced it. At most five such proposals wait at once in a project.

When a lesson becomes a skill

A lesson used in at least three different sessions has become a way of working. Once a day Slate proposes turning it into a skill, under Memory → Needs review, at most three each time. Make it a skill writes it to .claude/skills/<name>/SKILL.md in the project's folder, linked from .agents/skills/<name>, with the lesson and its reason, so all five AI tools read it as instructions. A lesson on a branch goes to its project's folder, not the branch's worktree. A lesson with no project folder on this computer is never proposed. The lesson then stops reaching sessions through the index, so it is not read twice. A proposal you dismiss is not asked again.

Logging progress mid-run

Between the start and the end of a longer piece of work, log_mission_progress appends a session summary to a Progress section — on the branch's Plan page when you have one, otherwise on the branch page — so the work builds up a running record of what happened. It never creates a page. On a trunk branch (main, master, develop) the log keeps only the latest 20 entries, the task's goal does not replace the branch's own, and remember writes only the memory itself, not a copy on the page: a trunk never ends, so anything that only appends to it grows forever. The copies older versions of Slate wrote there are moved, unchanged, to a child page called "Earlier notes on main", the first time Slate starts with a large main page.

Measuring it

Does memory help? One session in four is held out: it gets no memory index, no lessons and no tidy offer, and its agent can still search. For every session, Slate counts the turns that open by correcting the agent ("no, …", "wrong", "I told you"). The Does memory help? widget on the Activity dashboard (hidden until you add it from Edit) compares corrections per session with memory and without it. It shows a result only after 50 sessions in each group. You can turn the holdout off there.

yarn memory:report prints the numbers this design is judged by, from a snapshot of your store: how many sessions used a memory, and how many of the memories offered were cited; what was offered on each channel (including lessons, on channel trigger); reach, which is per tool how many work sessions were given memory out of those captured; the holdout comparison; health, the memories written against the distinct memories sessions used in the window (fewer writes per cited memory is better); quality, the share of the memories AI memory care read that both readings kept (aim for it to rise toward 80%); imported memories per tool; and per project the active memories, index lines and changed citations. --sample 24 writes a sheet of random deliveries to judge by hand.

yarn memory:eval --cwd <project> scores search: it runs recall over a fixed set of questions with known answers and prints recall@5 and MRR, per kind of question (plain memories, updated memories, questions about time, and questions nothing answers). The question set quotes your memory, so it lives beside your store, at memory-eval/questions.json in Slate's data folder, and not in Slate's source code. --half tune and --half report score the questions with odd and even numbers, so a change to search is chosen on one half and judged on the other. --also <file> passes other phrasings of each question, as an agent's second search would.
