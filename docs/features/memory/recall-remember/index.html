Recall & Remember

Slate's memory loop is two verbs. At the start of a task an AI tool calls recall to load context; at the end it calls remember to save what it learned. Everything else — capture, filing, ranking — is built around those two calls.

recall — load context at task start

recall({ query, cwd })

Given a query and your working directory, recall returns what matters for the task ahead:

ReturnedWhen
Branch briefOn a feature branch — what this branch is for, its ticket, its open items and its recent sessions.
Repo conventionsAlways — the conventions Slate has learned for this repository.
Project factsAlways — durable facts about the project.

Results are ranked lexically and locally — keyword coverage between your query and each atom, weighted by recency (a 30-day half-life) and confidence. There are no embeddings and no model call. A coverage threshold keeps recall silent when nothing is genuinely relevant, so it never pads the context with noise.

What a session is handed without asking

Tools with hooks also get memory without calling recall:

  • At session start, a brief of about 600 tokens (2,400 characters). It lists decisions by title, not their full reasoning, and never inlines a plan; the AI calls recall or opens the page when it needs the argument. When the brief runs long, the least useful sections go first: recent sessions, then recent branches, then identity.
  • On each prompt, the memories that match it. When nothing matches, nothing is added. Slate no longer pads the prompt with page text.

A claim whose cited file is gone from this machine is not handed to any session. If the project folder isn't on this machine, Slate can't check the file, so the claim is kept. Nothing is rewritten, and the claim comes back if the file does.

Every memory handed to a session is logged with how it arrived: brief, prompt or recall. That is how Slate measures what sessions actually received.

remember — save what you learned

Call remember with a concise one-line statement. Each call writes one typed knowledge atom — the unit every AI tool shares:

kindWhat it captures
decisionA choice you made ("chose X over Y because Z").
preferenceA durable working preference.
stateA durable fact about where things stand.
factA durable piece of project knowledge.

The atom is scoped to your project via cwd and deduped against what's already known — a near-duplicate strengthens the existing atom, an update supersedes it. remember also appends the statement to the branch's page, so you can read the memory back by hand.

Some writes are refused, and the refusal says how to fix them:

  • Transient text ("currently editing X").
  • A git snapshot from an AI tool ("main is 11 commits ahead", "carries 10 files uncommitted"). Git already answers these better.
  • A decision with no reason. Pass reason, or say why in the sentence ("because", "so that", "rather than"). The reason is stored with the decision.

Every atom records who wrote it: you in the app, or the AI tool by name. Keys and tokens are taken out before an atom is stored (for example "the staging key is [secret]"), and the rest of the sentence is kept.

When a new claim contradicts a memory Slate holds more firmly, it does not overwrite it. It waits under Needs review in Memory, beside the memory it disagrees with.

kind is optional; omit it and Slate infers it from the text. Preferences and states are also placed in a slot when the workspace already has one that fits, which is what lets a new preference retire the one it contradicts. That is worked out for you; there is nothing to pass.

Logging progress mid-mission

Between the start and the end of a longer piece of work, log_mission_progress appends a session summary to a Progress section — on the branch's Plan page when you have one, otherwise on the branch page — so a mission accumulates a running record of what happened. It never creates a page.
