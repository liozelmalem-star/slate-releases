Memory Map

The Memory Map is a visual view of what Slate remembers: the whole corpus at once, every atom placed by what it says, dense areas raised into contours, and the busiest regions named after the words that distinguish them.

It is not an alternative to reading the atoms — the map is the stage and the list is the pane beside it, both on screen together, and one scope picker drives them. There is no view switch to choose between them, and no separate "Recent" view; the list is where you read, correct and retire an atom, and the map is where you see the shape.

It is a visualization over the existing fact and decision data. It doesn't create a new kind of memory or a separate store — the marks are the same facts and decisions that recall reads and that remember writes. Change the underlying data and the view reflects it.

How to read it

  • Position is meaning. Two atoms sit near each other for one of two reasons: their text is similar — weighted so that words the whole corpus repeats stop counting as evidence — or they cite the same place in your code. A citation counts even when the wording shares nothing, which is how two notes about one file find each other after you have described it two different ways.
  • The outer ring is everything unconnected. Atoms that relate to nothing else Slate knows are placed in a band around the edge rather than dropped into the middle, and drawn smaller and fainter — they are a margin, not a place, and two of them sitting side by side means nothing at all. They raise no contours either, so the terrain describes only what Slate has actually connected. The ring is still worth reading: a large one means much of what you have written stands alone, and usually means those atoms want a citation or a rewrite.
  • Contours are density. The nested rings mark where Slate knows the most. Open ground is where it knows little.
  • Colour and shape are kind. A fact is a circle, a decision a filled slab, a preference a hollow one, state a pair — the same vocabulary the chips above the map use. Those chips filter the list, not the map: the map draws each kind as its own form, so hiding three of the four would leave a picture whose shapes no longer match the legend.
  • Size is recall. An atom grows with how often it has actually been used.
  • Retired atoms stay, faintly. Where the corpus used to be dense is part of what the map has to say.

Zoom past a certain point and every atom takes its own label; below that, the region names are the right level of detail. Click an atom to pin its card — edit the text, retire it, jump to the session that taught it, or merge a duplicate.

Positions are stable

The important property, and the reason this is a map rather than a diagram: an atom keeps its place. Open the tab tomorrow and the sync material is still over on the left. That is what makes it navigable from memory instead of re-read from scratch each time.

Keeping that promise takes work behind the scenes. The layout is computed from scratch whenever the corpus changes, and the algorithm that computes it has no preferred orientation or size — left to itself, a recompute would come back rotated, mirrored, or at a different scale. So each new layout is turned, flipped and resized onto the previous one before it is stored, and it is resized to reproduce the previous layout's size exactly rather than whatever size fits it most closely. That distinction is load-bearing: each stored layout is what the next one is measured against, so a fit that shrank the map even slightly would shrink it again on every recompute, and the whole corpus would close up into a single point.

An atom can still move a long way for two reasons. The first is the useful one: when it stops being alone. Add a citation to something on the outer ring, or write a second atom about the same file, and it leaves the ring for wherever its new neighbours are. The second is an update to Slate itself.

Once after an update

Stability holds within a version of Slate, not across one. When an update improves how atoms are placed, the old positions cannot be carried over: fitting a new layout onto the old one reproduces the old one, including whatever the update was meant to fix. So an update that changes the placement drops the previous frame and lays the map out fresh.

In practice, the first time you open Memory after such an update the map recomputes once and everything moves. After that it is stable again until the next placement change.

The map is a lens on your memory, not a source of truth of its own. The facts and decisions it draws live in your local SQLite workspace like every other page.

When it is catching up

Placing a thousand atoms takes about a second, so Slate never does it while you wait. Opening the tab shows the coordinates it already has and quietly recomputes behind you; a small "placing new atoms" note appears while that is happening, and the map sharpens when it lands. The one time this is more than a sharpening is the first open after an update that changed the placement: what you see first is the previous layout, and when the recompute lands the whole map moves at once. Atoms written since the last layout simply are not drawn yet — Slate would rather leave one out for a moment than guess a position and move it later.
