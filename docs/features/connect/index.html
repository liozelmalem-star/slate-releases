Features

Connect

Connect is the one screen for how a workspace reaches the world outside it, with four tabs: AI tools, Sources, Apps and Automations. It sits at the base of the rail beside Trash and Settings, because you come here when something is not answering rather than to do work.

Whose settings these are

Connect is per workspace. Your Personal workspace and your work one run different AI accounts and reach different trackers. Open Connect in Personal and it describes Personal — not the machine, and not whichever workspace you had open last.

Two things on the page are exceptions, and both say so where they are: two of the automations govern something there is only one of on this computer, under a This Mac heading — and the whole Apps tab is per computer, because neither app it lists can hold a second set of settings.

AI tools

One row per tool, five of them, always in the same order: Claude Code, Codex, Gemini, Cursor, OpenCode. A row says what it is at rest — the account it runs under and the model it uses — and opens to show the rest.

The switch does both halves of connecting. Turning a tool on installs Slate into that tool's config directory, so its sessions are captured and it can read and write your workspace; and it records that this workspace runs on that tool, which gives the Console, agents and workflows something to run on. Nobody wants one without the other, so when only one half is true the row says so in amber, and turning the switch on repairs it. When Slate is installed in a tool this workspace does not run, the row also offers Remove Slate, which takes Slate back out of that tool and leaves the workspace as it is.

A tool's account exists once on this computer, not once per workspace. When another workspace runs the same tool on the same account, Slate being installed there is that workspace's doing, so the row says Slate is installed here for Work instead of warning, and offers no Remove Slate: removing it would take Slate out of that tool for the other workspace too.

A workspace with no tool set cannot use its AI worlds. Memory, Activity, the Console and Loop are all filled or run by an AI tool. While this workspace has none set, their tabs stay in the rail, but each one opens on a single message — "Connect an AI tool to use Memory" — with an Open Connect button that lands here, and its list beside it stays empty. The app opens on your pages rather than the Console. Set a tool here and all four work at once, with no reload. Sessions is not affected: it lists every AI session on this Mac, whichever workspace is open.

Two ways in, and only ever one at a time

Some tools can install Slate as a plugin — a directory the tool owns, carrying three hooks, Slate's MCP server, and four slash commands. Slate writes nothing into the tool's config file; the tool records the plugin in its own format, and its own uninstall removes the lot. The rest get hooks written into their config instead.

ToolWhat turning it on does
Claude Codeinstalls the plugin
Codexinstalls the plugin
Geminiwrites hooks — its install asks you to trust a folder, which Slate will not answer for you
Cursorwrites hooks — it can only install plugins from a git address
OpenCodewrites its plugin file — OpenCode loads a module, not a directory

The plugin runs on Node 24 or newer. On a machine without it Slate uses the config route instead — and if Node disappears from a machine that already had the plugin, Slate takes the plugin back out rather than leaving a server that cannot start beside a working one.

You always have exactly one. On every launch Slate checks each tool and each account: where the plugin is installed the old hooks are removed, and a connected tool with neither gets back what it can have. Without that, everything happens twice — two session briefs in one context window, two nudges at the end of a turn.

What Slate writes into a config

For the three tools that take hooks, connecting writes a single line into ~/.gemini/settings.json, ~/.cursor/hooks.json, and OpenCode's own config. Those files are global: they apply to every project on the machine.

The line names one small script Slate generates in its own data directory and rewrites on every launch, so everything that can move — the app bundle, the checkout — moves inside that script rather than inside four other products' config files. When the script cannot find what it should run, it exits 0 in silence: a hook that cannot run belongs to a session that has nothing to do with Slate. It is safe to delete, and Slate writes it back on its next launch.

What you see in a Claude Code session

Loading your memory and capturing it both happen in the model's context, where you never read them. In Claude Code, Slate says so in one line each time.

WhenWhat prints
The session startsSlate · <branch> · 5 facts, 3 decisions, 3 sessions — what it just loaded
The session saves memorySlate · saved 3 memories from this session · <page>, and a desktop notification
Slate interrupts a stopStop hook feedback: Slate: this session did real work … but saved nothing yet. — three lines at most, and the model then ends with one short line instead of a second summary

Each prints at most once per session, and a session with nothing to load says nothing. Claude Code before 2.1.163 shows the interruption as Stop hook error: instead, because it has no other way to hand the text to the model. The notification goes through the terminal, so it looks like any other Claude Code raises. Claude Code only: the other four tools have no field for a line addressed to you, and a wrong key there is dropped silently by some and throws away the whole message in others.

Four commands in every session

The plugin also puts Slate in the / menu. Type /slate in Claude Code:

CommandWhat it does
/slate:briefWhat Slate knows about this project, in a few lines
/slate:recall <what>Search your memory, and check any code it cites
/slate:remember <fact>Save one fact, in your words
/slate:openOpen this branch's page in the Slate app

When turning a tool off does not work

Disconnect can fail, and it tells you rather than reporting success. Two things have to come out — the plugin, and any hooks the old route left — and Slate names whichever did not, hooks first, because those are the half that would keep running. If the plugin will not come out, the message gives the exact command to run in a terminal, such as codex plugin remove slate@slate. Either way Slate remembers you turned the tool off, so the next launch does not put it back.

Accounts

A tool's servers, sign-in and history live in a config directory, and four tools can have more than one: CLAUDE_CONFIG_DIR, GEMINI_CLI_HOME, CODEX_HOME, CURSOR_CONFIG_DIR. Open a row and pick which account this workspace uses, or add one by naming it and its directory. You can pick before you connect, because the account decides where Slate gets installed. What an account is, and why two workspaces naming the same one share its sign-in, is CLI Config Profiles.

OpenCode has no documented config-directory variable. It reads exactly one configuration, so there is no account to choose, and equally no wrong one to land in.

Models

Every tool offers a model list, and the row shows it once this workspace runs the tool. Leave it on its own default and Slate passes no model, so the CLI picks. The tool you mark default is the one this workspace reaches for when nothing more specific is named; a project can still override any of it.

Checking it actually works

A connected tool that is not working looks exactly like a connected tool nobody used, so "no sessions captured" has never told you which of the two it was. Slate keeps the plugin itself current: its hooks and its MCP server run the Slate the app is running, not the copy the tool installed. A tool that caches a plugin by version, as Codex does, still gets today's Slate the moment the app updates, and the copy inside the plugin is used only on a machine without the app. Every release is also a new plugin version, and the next launch refreshes what each tool holds. Run this in a terminal to check the rest:

"$HOME/Library/Application Support/app.slate.workspace/hooks/slate-hook" doctor

It reports, per tool: how many hooks are installed, whether each one points at a file that exists and can run, and when a session of that tool last reached Slate. Three outcomes matter:

  • n hook(s) OK with a recent session — working.
  • BROKEN — the hook cannot run, and the line says why and which file to fix. This is Slate's fault and Slate should fix it.
  • OK but nothing recorded — the wiring is sound and something outside Slate is stopping it. Usually one of: the tool has not been used since you connected it, the tool needs its hooks approved once, or the account cannot sign in.

Two of those last cases are worth naming, because both are silent:

  • Codex runs no plugin hook until you trust it. It ships a hook-trust step, and until you clear it in Codex, codex plugin list says installed, enabled while nothing at all runs.

Slate checks for this itself. Each tool's panel compares the sessions the tool wrote on this machine in the last 7 days with the sessions Slate's hooks recorded, and when fewer than half were recorded it says so — for example "Codex ran 9 sessions in the last 7 days and Slate saw 1" — with the step that fixes it.

  • Gemini CLI cannot sign in on a personal Google account. It returns IneligibleTierError and never starts, so Slate's hooks there are correct and unreachable. An API key or a Code Assist licence is the only way round it.

Sources

Every connection this workspace has, in one list, and whether each one works right now. It reads only the accounts the AI tools tab names. Reading the CLI's default instead would put one account's whole estate on another workspace's screen. So a workspace that has named no tool reads nothing, and says why rather than listing the wrong servers.

At the top are six roles: Tracker, Code, Chat, Calendar, Design, Docs. A role reads ready only when a connection behind it is working, needs you when the one it has needs a sign-in, set up when it has only servers nobody has checked, and none when nothing on this machine can answer it. A role with nothing behind it is still shown, because "you have no calendar" and "nobody asked about the calendar" are different answers.

Below is the list:

  • A toolkit (one server that carries many integrations) is one row. Its chevron opens what it carries. One sign-in fixes all of them, so the row has one Sign in button, and it says when they stopped together.
  • GitHub read over gh is a row, even though no config declares it.
  • Your Claude account's connectors are one row. Only Claude Code can use them.
  • Every other server follows, the ones only one tool declares first: no tool reads another tool's MCP configuration, so a calendar configured in Cursor is invisible to anything running in Claude Code.

Each row says how it stands. For what Slate reads itself, that is Live, Needs sign-in, Connect, Unavailable or Soon, and a failure says when it last worked. For a server Slate does not read, it is what the AI tool reported the last time it started it — Connected in Claude Code, Needs sign-in in Claude Code, or that it could not connect. A server neither has spoken for says Set up, not checked. It is never counted as ready. A group that needs you opens by itself.

Each row offers the one step that fixes it. Sign in for a tool Slate reads is the same sign-in as the Work pane's, so one started here shows there. Sign in for a server only an AI tool reaches runs that tool's own login. A source that is not this workspace's — declared for every directory on the machine — says so rather than hiding it.

Apps

Claude Desktop, VS Code and the Codex desktop app host Slate's MCP server and run nothing. They are not tools in the sense above: they start no sessions, so there is no account to pick, no model to set, and no capture hook to install. Two of them had rows at the bottom of AI tools, promising capture that cannot happen there; they are their own tab now.

Turn one on and Slate's tools are available inside that app: the assistant there can read and write your workspace, recall what you have already decided, and save what it learns. Each row names the config file the switch writes, because that file is the connection — one entry in a file that app owns.

An app is on only because you turned it on. Once you connect one AI tool, Slate keeps tools you install later registered on every launch. Apps are left out of that: a new app row starts off, and only its own switch turns it on.

An app you do not have has no row. With none installed the tab says so instead of offering switches that would configure nothing.

The Codex app has no switch of its own, and says why. It reads ~/.codex/config.toml — the same file the Codex row on AI tools writes — so it is connected the moment that tool is, and a second switch here would be two controls over one file, where "off" would disconnect your CLI. Its row says whether Slate is in that file and links to Change on AI tools. The Codex switch there can read off while Slate is still in the file: it is on only when Slate is installed and this workspace runs on Codex, and that row says so. This is a difference between the products, not a choice Slate made: Anthropic ships Claude Desktop with a config file of its own, and OpenAI ships one file for both.

This tab is per computer, not per workspace. Neither app can point at a second config directory, so there is one file and one answer for the machine — the one place in Connect where switching workspace changes nothing.

What Slate does not get from them is your transcript. A CLI writes its session to a file Slate can read, so Slate sees what happened whether or not the assistant chose to save anything. An app that only hosts the MCP server gives Slate exactly what the assistant calls remember with, and nothing else — and neither app can be interrupted at the end of a turn to be asked again, because neither has a hook to interrupt it with. So memory from these two is best-effort. That is a limit of the products, not of Slate, and Connect says so rather than implying the two tabs are equivalent.

They matter because they are the only way in for somebody who has installed none of the five CLIs.

Automations

Everything Slate does when you are not asking it to, and a switch for each — with what turning it off costs, said in the app. Full detail is in Automations.

What is not here

Settings holds what belongs to the app and this computer — your account, the workspaces this machine holds, appearance, the terminal, shortcuts, and the version. One of its tabs is not the machine's: Data moves the open workspace's file and restores that workspace's snapshots.
