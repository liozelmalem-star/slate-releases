Features

Connect

Connect has two tabs, Agents and Integrations. It sits at the base of the rail beside Trash and Settings, because you come here when something is not answering.

Connect is per workspace. Personal and a work workspace run different AI profiles and reach different trackers. Connect always describes the workspace you are in, not the machine.

What Slate runs on its own is in Automations › Built-in, one answer for the whole app. See Automations.

Agents

The tab is laid out like Integrations. Connect an agent heads it, with one line on what connecting does. Under it are three filters with counts, All 16, On this Mac and Connected, and Find an agent, which searches by name. Then every tool is a row: its logo, its name, a line on how it stands, and on the right a status word and one button.

The tools are always listed in this order: Claude Code, Codex, Cursor, GitHub Copilot, Antigravity, OpenCode, Gemini, Cline, Grok Build, Kiro, Qwen Code, Droid, Hermes Agent, Goose, Kilo Code and Auggie. The first six are measured end to end. The ten newest were checked against their CLIs on 2026-11-06 and show unverified in Features by Agent where nobody has run a feature yet. A row shows the profile it runs under and its model. Click its logo or name to open the tool's dialog. A profile is one login of that tool on this computer: its config folder. Your account is your Slate sign-in, in Settings.

Every tool is a row, and a row never moves. Turning a tool on or off changes its status word and its button, not its place. Under Connected, a tool you turn off keeps its row until you pick another filter. The count updates at once.

Connect does two things. It installs Slate into the tool's config directory, so its sessions are captured and it can read and write your workspace. It also records that this workspace runs on that tool, which gives Home, automations and skills something to run on. Disconnect undoes both. When only one half is true, the row says so in amber and Connect repairs it: Slate is installed here, but nothing runs on it, or Runs here, but Slate is not installed — sessions are not captured. When Slate is installed in a tool this workspace does not run, the button is Remove Slate, which takes Slate out of that tool and leaves the workspace as is. The dialog names the config file Slate writes and has the same Connect or Disconnect.

Slate writes to none of these files until you connect a tool, on first launch too.

For Claude Code, Codex and Gemini, whose transcripts Slate reads, the dialog has a Capture switch. The ten newest tools have none yet. Off, Slate stops recording that tool's sessions. The tool stays connected. Cursor's dialog has Capture sessions / Stop capturing, which turns its capture hook on or off. OpenCode has no capture control. Auto-capture in Automations › Built-in turns capture off for all of them at once.

A tool's profile exists once per computer. When another workspace runs the same tool on the same profile, the row says Slate is installed here for Work and offers no Remove Slate, because removing it would break the other workspace. Disconnecting there only stops this workspace running on the tool, and the row says so first.

A workspace with no tool cannot chat on Home, run automations, build apps, learn memories or record activity. The Automations, Memory, Activity, Apps and Toolkit icons stay in the rail, dimmed. Hover says why, and a click does nothing. Memory, Activity and Apps open anyway once they hold something. Home opens as a doc: the agents, what connecting one unlocks, Open Connect, and what works without AI (Tasks, Projects, Artifacts). Set a tool and everything works at once, with no reload.

One place decides which tool runs. Connect sets the workspace's tool, and a group or project can override it in its settings. Home, the ⌘J panel, New session and automations show the tool that will run, with a link back here. When a project runs more than one tool, Home and New session let you pick one for that turn. Sessions lists every AI session on the computer.

A tool's dialog lists the MCP servers it declares, read from the profile this workspace runs it under. A tool this workspace does not run lists nothing and says to turn it on. With none, it says Nothing besides Slate itself. and Add an MCP server opens the New dialog in Toolkit.

  • A gateway (one server carrying many integrations) is one row. Its chevron opens what it carries. It has one Sign in and says when they stopped together.
  • Your Claude account's connectors are one row under Claude Code, the only tool that can use them.
  • A server the tool declares for every directory says every workspace. That answers "why is this on my Personal screen".

Each server shows how it stands. For what Slate reads itself: Live, Needs sign-in, Not turned on, Unavailable or Not read yet, and a failure says when it last worked. Not turned on offers Turn on. Not read yet offers Let an agent read it, or Read with Claude Code for one only your Claude account reaches. For a server Slate does not read, the state is what the tool last reported: Connected in Claude Code, Needs sign-in in Claude Code or Claude Code couldn't connect. A server neither has spoken for says Set up, not checked. Sign in for a tool Slate reads is the sign-in Tasks uses. For a server only an AI tool reaches, it runs that tool's own login. Refresh and any waiting sign-in sit above the list.

Claude Desktop is connected with Claude Code. Turning Claude Code on also puts Slate into Claude Desktop, if installed. Turning it off leaves Desktop alone, because Desktop has one setting for the machine and another workspace may still run Claude Code. The Codex desktop app reads the Codex CLI's config, so it is connected whenever Codex is.

Two ways in, one at a time

Some tools install Slate as a plugin: a directory the tool owns, with five hooks (six for Claude Code) and four slash commands. The tool records it in its own format, and its own uninstall removes it all. The MCP server is not in the plugin. Every tool reaches it through one slate entry in its own config. OpenCode and GitHub Copilot have no plugin route, so they get hooks written into their config. So do Claude Code, Gemini and Cursor when their plugin cannot be installed or run. Codex takes no hooks in config. Where its plugin cannot run, it keeps only the MCP entry.

The MCP entry is a URL on the running app (http://127.0.0.1:47366/mcp) with Slate's private key in a header (ADR 0106). No session starts its own process. Slate writes the entry into the tool's config file itself, never through the tool's command line, readable by you only. Claude Desktop and VS Code keep a stdio entry running the slate-mcp binary. With Slate closed, a tool lists the server as failed and the session-start hook says why. Open Slate and start a new session.

The plugin needs Node 24 or newer. Without it, Slate uses the config route for tools that have one. If Node disappears from a machine that had the plugin, Slate removes the plugin rather than leave a server that cannot start. Slate finds Node the way your terminal does: an app opened from Finder has no shell PATH, so Slate asks your shell once per launch where node is. That finds fnm, nvm, volta and asdf installs.

You always have exactly one. On every launch Slate checks each tool and profile. Where the plugin is installed the old hooks are removed, and a connected tool with neither gets back what it can have. Otherwise everything happens twice: two session briefs in one context, two nudges at the end of a turn.

Slate decides from its own record of what it installed in each profile, kept in its data folder. When a profile matches the record, the launch runs no tool command and writes nothing. A profile with no record is left alone unless you connected it. Every profile you connected is checked each launch, and one that has lost Slate (plugin uninstalled, settings rewritten) is connected again. Only turning a profile off in Connect keeps it off.

What actually ran. Every launch rewrites the small launcher in Slate's data folder to name the running Slate, and every tool reaches Slate through it or through an entry the launch repair keeps on the same build. When a tool starts Slate's MCP server, the server records which tool, account and Slate it is. A tool's dialog shows what its last session ran: this Slate and when, one started before this Slate was built (the next session runs this one), or another Slate, named. The last case also shows in amber on the row. A session on the HTTP entry always talks to the running Slate. One on a host's stdio entry keeps the server it started with.

What Slate writes into a config

On the config route, connecting writes hook entries into ~/.claude/settings.json, ~/.gemini/settings.json, ~/.cursor/hooks.json, ~/.config/opencode/opencode.json and ~/.copilot/hooks/slate.json (under a profile, into that profile's folder). Claude Code, Gemini, Cursor and GitHub Copilot get one entry per event: five for Gemini and GitHub Copilot, six for Claude Code and Cursor. Claude Code's sixth runs after a RemoteTrigger or Bash call and records a cloud session that call started (see Sessions). Cursor's sixth is a prompt hook that applies the account rule of the folder you are in. OpenCode gets one plugin module with two events. These files are global: they apply to every project on the machine.

Every entry names one small script Slate generates in its data directory and rewrites on every launch, so everything that can move (the app bundle, the checkout) moves inside the script. When the script cannot find what to run, it exits 0 silently. It is safe to remove, and Slate writes it back on the next launch.

What turning a tool off puts back

Slate's record also holds what each file contained before Slate first wrote to it. On disconnect, a file only Slate has changed goes back to those exact bytes, and a file Slate created is removed. If you or the tool edited the file after Slate, Slate removes only its own parts and keeps your edit.

If disconnect fails, it says so. Two things must come out, the plugin and any hooks the old route left, and Slate names whichever did not, hooks first because those keep running. If the plugin will not come out, the message gives the terminal command, such as codex plugin remove slate@slate. Either way Slate remembers you turned the tool off, so the next launch does not put it back.

Profiles

A tool's servers, sign-in and history live in a config directory. Most tools can have more than one: CLAUDE_CONFIG_DIR, GEMINI_CLI_HOME, CODEX_HOME, CURSOR_CONFIG_DIR, COPILOT_HOME and the variable in each newer tool's record (Antigravity, Auggie, Kilo Code and OpenCode have none). In a tool's dialog, pick the Profile this workspace uses, or Add one by naming it and its config folder. For Claude Code, Codex and Cursor, the add form offers other config folders already in your home folder, such as ~/.claude-work, as buttons under Found here. Gemini offers none, because its variable names a replacement home folder. Choose folder… picks any other. A path that does not exist yet is fine: the tool creates it on sign-in. You can pick before connecting, because the profile decides where Slate is installed. Cursor is the exception: CURSOR_CONFIG_DIR moves only its sign-in. cursor-agent reads its servers, hooks and plugins from ~/.cursor and writes its history there (or where CURSOR_DATA_DIR says) for every profile. So Slate writes them there once for all Cursor profiles. Turning one profile off leaves them in place while another connected Cursor profile still uses them. See Project environments for why two workspaces naming one profile share its sign-in.

OpenCode, Antigravity, Kilo Code and Auggie have no config-directory variable and read exactly one configuration, so there is no profile to choose.

Models

A tool's dialog shows its model list once this workspace runs the tool. Until then it says to turn the tool on. On Its own default, Slate passes no model and the CLI picks. Make default marks the tool this workspace reaches for when nothing more specific is named, shown with a default badge. A group or standalone project can override any of it.

Checking it actually works

A connected tool that is not working looks the same as one nobody used. Slate keeps the plugin current: its hooks and MCP server run the Slate the app is running, not the installed copy. A tool that caches a plugin by version, as Codex does, still gets today's Slate the moment the app updates. The copy inside the plugin is used only on a machine without the app. Every release is a new plugin version, refreshed on the next launch. To check the rest, run in a terminal:

"$HOME/Library/Application Support/app.slate.workspace/hooks/slate-hook" doctor

It prints one line per tool. A tool with no hooks says not connected. Otherwise it gives how many hooks are installed and when a session of that tool last reached Slate:

  • n hook(s) OK · last session <when>: working.
  • n BROKEN of m: a hook cannot run. The lines under it say why and name the file. This is Slate's fault. The command then exits with an error code.
  • n hook(s) OK · no session recorded yet: the wiring is sound and something outside Slate is stopping it. Usually the tool has not been used since you connected it, it needs its hooks approved once, or the account cannot sign in.

Two silent causes:

  • Codex runs no plugin hook until you trust it. Until you clear its hook-trust step, codex plugin list says installed, enabled while nothing runs.
  • Gemini CLI cannot sign in on a personal Google account. It returns IneligibleTierError and never starts. An API key or a Code Assist licence is the only way round.

Slate checks for the first kind itself. On the Activity doc, the Do sessions save memory? card (off by default) compares the sessions the tool wrote on this machine in the last 7 days with the sessions Slate's hooks recorded. When the tool wrote at least 3 and fewer than half were recorded, it says so, for example "Codex ran 9 sessions in the last 7 days and Slate saw 1. Its sessions got no memory from Slate and saved none.", with the fix.

Integrations

The Integrations tab holds the apps this workspace connects and what those connections let it serve. Each workspace keeps its own.

Connect an integration

A list with one row per integration: its logo, name, one line on what Slate reads, its state and one button. Disconnect shows when you point at a connected row. Apps Slate can connect now come first. GitHub (read through your gh), Jira, GitLab, Notion, Trello, ClickUp, Linear, Mattermost (your own server), monday.com, Basecamp, Plane (Plane Cloud), Shortcut and Todoist sign in through each app's official server. Bitbucket, Gitea (and Forgejo), Gerrit, YouTrack, Zulip and Rocket.Chat offer no sign-in Slate can use, so you paste a token. All sit in one list, most used first by the Stack Overflow Developer Survey's share of developers, then apps the survey omits, A to Z. Below, Coming soon lists apps Slate cannot connect yet, each with its reason. Slack, Microsoft Teams, Discord, Google Chat, Gmail, Outlook and Asana say Needs Slate's own app of that vendor, which Slate has not registered. Azure DevOps and Zoom say No server Slate can sign in to yet. Issues, Reviews and Messages narrow the grid to apps whose work shows in that group of Tasks (mail is under Messages), each with a count. Find an integration searches. An app you hid from Tasks is listed under the grid as Hidden from Tasks, with Show.

Press Connect, approve Slate on the app's own sign-in page in your browser, and what you owe there shows in Tasks. No agent is involved. GitHub's Connect turns on reading through your gh sign-in. A signed-in gh alone is not enough: Slate reads nothing from GitHub until you press Connect.

  • The sign-in is Slate's own and stays on this computer, so a restart or update never asks again. When the app ends it (new password, admin removed access), the row says Needs sign-in with Sign in again. A connection is judged by its own sign-in only. An agent's server reading the same app never makes it look signed in.
  • An app can accept the sign-in and still refuse Slate's reads because of an app setting. The tile and banner then say Unavailable with the change needed, or the app's own words. GitLab is one: "GitLab blocks Slate until you turn on “Allow connection to GitLab” in a GitLab group you own."
  • A connected app Slate cannot read yet says Not read yet and waits as a logo under Not reading yet in Tasks, not as a 0. Slate then teaches itself to read it, once: the tile says Learning how to read your tasks in Notion… while your agent works out how, through Slate's own connection. Slate keeps the answer. If nothing is found, the tile says Couldn't find your tasks in Notion. with Try again. This is how Notion is read, because every Notion workspace keeps its tasks in a database of its own making.
  • Jira and Trello say your admin may need to allow Slate first. Atlassian lets an organisation choose which apps connect, and Trello's server follows the same controls.
  • Mattermost runs on your own server. Connect asks for its address (for example https://chat.example.com) and signs in at the Agents plugin's MCP server on it, /plugins/mattermost-ai/mcp-server/mcp. Your admin must first turn on that MCP server and OAuth dynamic client registration, offered from Mattermost's Enterprise plan up. Once connected, the tile shows the address and replaces the plain Mattermost tile.
  • Bitbucket, Gitea, Gerrit, YouTrack, Zulip and Rocket.Chat connect with a pasted token. Connect opens a short form: the server address (all but Bitbucket), the account name the app wants beside the token (Zulip's email, Gerrit's username, Rocket.Chat's user ID), and the token, with where to make it and which read-only permissions to tick. Slate asks the app who the token belongs to before keeping it. A refused token is not kept, and the form says why. The token is kept only on this computer, in a file only your user account can read. If the app later refuses it, the tile says Needs sign-in with Paste a new token. Zulip and Rocket.Chat show only messages that name something this workspace works on, the same filter every chat and mail reader uses.
  • Your agents can read what you connect. An app connected through its own server (not a pasted token) can be read from any AI session in this workspace, in every agent, with no setup in them: connected_tools and read_connected use Slate's sign-in while Slate is open. Only tools that read are offered. See Connected MCP tools.
  • Disconnect forgets Slate's sign-in or pasted token. Its tasks leave with the next sync, unless a server one of your agents declares still reads it.
  • Another app, the last tile, connects any MCP server: name the app, give its https address, and sign in the same way.
  • An app connected here is read here and not through an agent's server for the same app, so one task never comes from two places.

What is not here

Settings holds what belongs to the app and this computer: Account, Workspaces, Appearance, Terminal, Keyboard and About (version, updates, logs). What Slate runs on its own is in Automations › Built-in. Moving, exporting and restoring a workspace's file are in Settings → Workspaces, in the workspace's dialog.
