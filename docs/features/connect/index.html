Features

Connect

Everything about how a workspace reaches the world outside it used to be in three places: which AI tool a project ran was on the project page, what Slate was installed into was in Settings, and the background loops were somewhere else again. Three screens for one question — why isn't this working? — and nothing said which to open.

Connect is that one place. It sits at the base of the rail with the other administration, because you come here when something is not answering rather than to do work, and the rail groups it with the things the workspace picker governs.

Whose settings these are

Connect is per workspace, and that is the point rather than a detail. Your Personal workspace and your work one run different AI accounts, reach different trackers, and should not be able to see each other's. Open Connect in Personal and it describes Personal — not the machine, and not whichever workspace you had open last.

The one exception is stated on the page: two of the automations govern something there is only one of on this computer, and they sit under a This Mac heading. Everything else is yours alone.

AI tools

One row per tool, five of them, always in the same order. A row says what it is at rest — the account it runs under and the model it uses — and opens to show the rest.

The switch does both halves of connecting. Turning a tool on installs Slate into that tool's config directory, so its sessions are captured and it can read and write your workspace; and it records that this workspace runs on that tool, which is what gives the Console, agents and workflows something to run on. Nobody wants one without the other: a tool Slate is installed in but nothing runs is watched and useless, and one a workspace runs but Slate is not installed in cannot be watched at all.

When only one half is true the row says so in amber, and turning the switch on repairs it.

What actually gets written, and why it cannot rot

There are two ways in, and which one a tool gets is settled below. This section is about the older one — Gemini, Cursor and OpenCode, the three that cannot install a plugin.

For those three, connecting writes hooks into the tool's config: ~/.gemini/settings.json, ~/.cursor/hooks.json, and OpenCode's own config. Those files are global: they apply to every project on the machine, including the ones that have nothing to do with Slate.

What goes into them is a single path, to a small script Slate generates in its own data directory. Slate rewrites that script on every launch; nothing else in the chain moves.

That indirection exists because the alternative rotted. Slate used to write the path of the thing it wanted to run — a checkout in a dev build, the app bundle in a release one — straight into those files. A path is a promise about a directory and a global config outlives directories, so deleting a worktree, renaming a clone or moving a folder to another disk meant every session of that tool, in every unrelated project, printed a MODULE_NOT_FOUND stack trace on the hooked event. Measured: 17 lines, exit 1, on every turn, until Slate was next launched.

The script can do the one thing a bare path cannot — fail silently. When it cannot find what it is supposed to run, it exits 0 and says nothing, because a hook that cannot run belongs to a session that has nothing to do with Slate and should be invisible there. Verified for all five tools with the target deleted: no output, exit 0.

It is safe to delete. With it gone the hooks simply stop firing, and Slate writes it back on its next launch.

Two ways in, and only ever one at a time

Some tools can install Slate as a plugin instead — a directory the tool owns, carrying the same three hooks, the same MCP server, and four slash commands. Slate writes nothing into the tool's config file itself; the tool records the plugin there in its own format, and the tool's own uninstall removes the lot.

Turning a tool on installs the plugin where that works, and writes hooks where it does not:

ToolWhat turning it on does
Claude Codeinstalls the plugin
Codexinstalls the plugin
Geminiwrites hooks — its install asks you to trust a folder, which Slate will not answer for you
Cursorwrites hooks — it can only install plugins from a git address
OpenCodewrites its plugin file — OpenCode loads a module, not a directory

Both are supported. Neither is a stopgap.

The plugin runs on Node 24 or newer. On a machine without it Slate uses the config route instead — and if Node disappears from a machine that already had the plugin, Slate takes the plugin back out rather than leaving a server that cannot start sitting beside a working one.

You always have exactly one. On every launch Slate checks each tool and each account: if the plugin is there, the old hooks are removed; if a tool was connected and has neither, Slate puts back what that tool can have — the hooks for the four that have them, and for Codex, whose only route is the plugin, its MCP server. Without that, everything would happen twice — two session briefs in one context window, two nudges at the end of a turn — or, if an install half-failed, not at all.

If you already had Slate connected, the first launch after updating moves those tools onto the plugin and cleans up what the old way left behind: the hooks, and the second copy of Slate's MCP server that would otherwise list every Slate tool twice.

What you see in a Claude Code session

Slate used to work entirely out of sight: it loaded your memory at the start of a session and captured it at the end, and both went into the model's context where you never read them. In Claude Code it now says so, in one line each time.

WhenWhat prints
The session startsSlate · <branch> · 5 facts, 3 decisions, 3 sessions — what it just loaded
The session saves memorySlate · saved 3 memories from this session · <page>, and a desktop notification
Slate interrupts a stopSlate · asked this session to record what it learned

Each prints at most once per session, and a session with nothing to load says nothing. The desktop notification goes through the terminal, so it looks like any other notification Claude Code raises.

Claude Code only. The other four tools have no field for a line addressed to you, and Slate does not guess at one — a wrong key there is silently dropped by some tools and makes others throw away the whole message.

Four commands in every session

The plugin also puts Slate in the / menu. Type /slate in Claude Code:

CommandWhat it does
/slate:briefWhat Slate knows about this project, in a few lines
/slate:recall <what>Search your memory, and check any code it cites
/slate:remember <fact>Save one fact, in your words
/slate:openOpen this branch's page in the Slate app

They cost nothing until you type one.

When turning a tool off does not work

Disconnect can fail, and it tells you rather than reporting success. Two things have to come out — the plugin, and any hooks the old route left — and Slate reports whichever did not, hooks first, because those are the half that would otherwise keep running.

If the plugin will not come out, the message names the exact command to run in a terminal for that tool. Either way Slate remembers you turned the tool off, so the next launch does not put it back.

Accounts

A tool's servers, sign-in and history live in a config directory, and some tools can have more than one — CLAUDE_CONFIG_DIR, GEMINI_CLI_HOME, CODEX_HOME. Open a row and pick which account this workspace uses, or add one by naming it and the directory it points at.

Choosing an account is available before you connect, because it decides where Slate gets installed. A config directory exists once on this machine, so every workspace naming it shares that sign-in.

A tool with no config-directory variable — Cursor, OpenCode — reads exactly one configuration, so there is no account to choose, and equally no wrong one to land in.

Models

Only for a tool Slate can actually drive, and only once this workspace runs it. Codex and Cursor are captured rather than driven, so they have no model to set; the row says so instead of offering a control with nothing behind it.

The tool you mark default is the one this workspace reaches for when nothing more specific is named. A project can still override any of it.

Checking it actually works

A connected tool that is not working looks exactly like a connected tool nobody used. Slate writes a hook into the tool's own config; the tool runs it, gets nothing, and says nothing — no warning, no error, no failed session. So "no sessions captured" has never told you which of the two it was.

Slate keeps the plugin itself up to date. Its version is the app's version, so every Slate release is a new plugin version, and the next launch refreshes what each tool holds. Before 0.1.22 the plugin said 0.1.0 forever, so no tool ever saw a newer one and every install stayed frozen at whatever it was on the day you connected.

Run this in a terminal to check the rest:

slate-hook doctor

It reports, per tool: how many hooks are installed, whether each one points at a file that exists and can run, and when a session of that tool last reached Slate. Three outcomes matter:

  • n hook(s) OK with a recent session — working.
  • BROKEN — the hook cannot run, and the line says why and which file to fix. This is Slate's fault and Slate should fix it.
  • OK but nothing recorded — the wiring is sound and something outside Slate is stopping it. Usually one of: the tool has not been used since you connected it, the tool needs its hooks approved once, or the account cannot sign in.

Two of those last cases are worth naming, because both are silent:

  • Codex runs no plugin hook until you trust it. It ships a hook-trust step, and until you clear it in Codex, codex plugin list says installed, enabled while nothing at all runs.
  • Gemini CLI cannot sign in on a personal Google account. It returns IneligibleTierError and never starts, so Slate's hooks there are correct and unreachable. An API key or a Code Assist licence is the only way round it.

Sources

Everything this workspace can reach through MCP, folded across every AI tool it runs, grouped by the role it fills — tracker, code, chat, calendar, design, docs.

It reads only the accounts the AI tools tab names, and that chain is the design. A tool's servers live in a config directory, and which directory is exactly what the other tab decides. Reading the CLI's default instead would put one account's entire estate on another workspace's screen under a heading claiming it belonged there.

So a workspace that has named no tool reads nothing, and says why rather than showing a confident list of the wrong servers.

Two things the list is careful to distinguish:

  • A source only one tool declares. No tool reads another tool's MCP configuration, so a calendar configured in Cursor is invisible to anything grounding in Claude Code. Narrowest reach sorts first, because that is the shape of the failure.
  • A source that is not this workspace's. A tool can declare a server for every directory on the machine, so it genuinely resolves here whatever you are working on. Hiding it would be the lie; the row says whose it is.

Sources is read-only. It tells you what you have; connecting a source to Slate is still done in the tool that owns it.

Automations

Everything Slate does when you are not asking it to, and a switch for each — with what turning it off costs, said in the app rather than left for you to guess.

Full detail, including which are per-workspace and which are per-machine, is in Automations.

What is not here

Settings still holds what belongs to the app and this computer — your account, the list of workspaces this machine holds, appearance, the terminal, shortcuts, and the version. Its tab list is grouped the same way this world is, because one of its tabs is not the machine's: Data moves the open workspace's file and restores that workspace's snapshots.

The rule both places follow: a heading answers does changing this affect my other workspace?, wherever that question can be asked.
