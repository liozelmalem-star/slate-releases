Features

Connect

Connect is the one screen for how a workspace reaches the world outside it, with three tabs: AI tools, Apps and Background jobs. It sits at the base of the rail beside Trash and Settings, because you come here when something is not answering rather than to do work.

Whose settings these are

Connect is per workspace. Your Personal workspace and your work one run different AI profiles and reach different trackers. Open Connect in Personal and it describes Personal — not the machine, and not whichever workspace you had open last.

Two things on the page are exceptions, and both say so where they are: some of the background jobs govern something there is only one of on this computer, under a This Mac heading — and the whole Apps tab is per computer, because neither app it lists can hold a second set of settings.

AI tools

One row per tool, five of them, always in the same order: Claude Code, Codex, Gemini, Cursor, OpenCode. A row says what it is at rest — the profile it runs under and the model it uses — and opens to show the rest. A profile is one login of that tool on this Mac: its config folder. Your account is something else — your Slate sign-in, in Settings.

The switch does both halves of connecting. Turning a tool on installs Slate into that tool's config directory, so its sessions are captured and it can read and write your workspace; and it records that this workspace runs on that tool, which gives the Home, agents and workflows something to run on. Nobody wants one without the other, so when only one half is true the row says so in amber, and turning the switch on repairs it. When Slate is installed in a tool this workspace does not run, the row also offers Remove Slate, which takes Slate back out of that tool and leaves the workspace as it is. Each row names the config file Slate writes for that tool.

An open row also has a Capture switch, for the tools whose transcripts Slate reads. Turn it off and Slate stops recording that tool's sessions. The tool stays connected, and other tools are not affected. The machine-wide Auto-capture in Connect → Background jobs still turns capture off for all of them. Cursor's row has Capture sessions / Stop capturing instead, which turns its capture hook on or off.

A tool's profile exists once on this computer, not once per workspace. When another workspace runs the same tool on the same profile, Slate being installed there is that workspace's doing, so the row says Slate is installed here for Work instead of warning, and offers no Remove Slate: removing it would take Slate out of that tool for the other workspace too. For the same reason, turning the switch off there only stops this workspace running on the tool; Slate stays installed, and the row says so before you click.

A workspace with no tool set cannot chat on Home or run Routines. Both run on an AI tool. While this workspace has none set, the Routines tab stays in the rail but opens on a message that says why, with an Open Connect button that lands here. Home still opens: it shows the Set up Slate card, whose first step is Connect an AI tool, and an Open Connect button in place of the chat. Memory and Activity are filled by capture, which needs no AI tool, so they work either way. The app always opens on Home. Set a tool here and Home and Routines work at once, with no reload.

One place decides which tool runs. This switch sets the workspace's tool; a group or project can override it in its settings. Home, the ⌘J panel, New session and a routine all show the tool that will run, with a link back here, and none of them keeps a choice of its own. Sessions is not affected: it lists every AI session on this Mac, whichever workspace is open.

An open row lists the MCP servers that tool declares, read only from the profile this workspace runs it under — a tool this workspace does not run lists nothing and says to turn it on, because reading the CLI's default instead would put another workspace's servers on this screen. With none declared, Add an MCP server opens the New dialog in Toolkit.

  • A gateway (one server that carries many integrations) is one row. Its chevron opens what it carries. One sign-in fixes all of them, so the row has one Sign in button, and it says when they stopped together.
  • Your Claude account's connectors are one row, under Claude Code: only Claude Code can use them.
  • A server the tool declares for every directory on this Mac says every workspace: it resolves here whatever you are working on, and saying so is the answer to "why is this on my Personal screen".

Each server says how it stands. For what Slate reads itself, that is Live, Needs sign-in, Connect, Unavailable or Not read yet, and a failure says when it last worked. Not read yet offers Let an AI tool read it, or Read with Claude Code for one only your Claude account reaches. For a server Slate does not read, it is what the AI tool reported the last time it started it — Connected in Claude Code, Needs sign-in in Claude Code, or that it could not connect — and one neither has spoken for says Set up, not checked, never ready. Sign in for a tool Slate reads is the same sign-in as the Tasks pane's; for a server only an AI tool reaches, it runs that tool's own login. Waiting sign-ins and Refresh sit above the list.

Claude Desktop is connected along with Claude Code. Turning Claude Code on also puts Slate into Claude Desktop, when it is on this Mac, so its assistant can read and write your workspace too. Turning Claude Code off leaves Desktop as it is: Desktop keeps one setting for the whole machine, and another workspace may still run Claude Code under a different profile. The Codex desktop app reads the Codex CLI's own config file, so it is connected whenever Codex is.

Two ways in, and only ever one at a time

Some tools can install Slate as a plugin — a directory the tool owns, carrying three hooks, Slate's MCP server, and four slash commands. Slate writes nothing into the tool's config file; the tool records the plugin in its own format, and its own uninstall removes the lot. A tool with no plugin system gets hooks written into its config instead, and so does any tool whose plugin cannot be installed or cannot run.

ToolWhat turning it on does
Claude Codeinstalls the plugin
Codexinstalls the plugin
Geminiinstalls the plugin, as a Gemini extension
Cursorinstalls the plugin, as a link in Cursor's local plugins folder
OpenCodewrites its plugin file — OpenCode loads a module, not a directory

The plugin runs on Node 24 or newer. On a machine without it Slate uses the config route instead — and if Node disappears from a machine that already had the plugin, Slate takes the plugin back out rather than leaving a server that cannot start beside a working one.

Slate looks for Node where your terminal does. An app opened from Finder does not get your shell's PATH, so Slate asks your shell once per launch where node is. This is how a Node installed by fnm, nvm, volta or asdf is found.

You always have exactly one. On every launch Slate checks each tool and each profile: where the plugin is installed the old hooks are removed, and a connected tool with neither gets back what it can have. Without that, everything happens twice — two session briefs in one context window, two nudges at the end of a turn.

Slate decides this from its own record of what it installed in each profile, kept in its data folder on this machine. When a profile already matches the record, the launch runs no tool command and writes nothing. A profile Slate has no record of is left alone.

What Slate writes into a config

For the three tools that take hooks, connecting writes a single line into ~/.gemini/settings.json, ~/.cursor/hooks.json, and OpenCode's own config. Those files are global: they apply to every project on the machine.

The line names one small script Slate generates in its own data directory and rewrites on every launch, so everything that can move — the app bundle, the checkout — moves inside that script rather than inside four other products' config files. When the script cannot find what it should run, it exits 0 in silence: a hook that cannot run belongs to a session that has nothing to do with Slate. It is safe to delete, and Slate writes it back on its next launch.

What you see in a Claude Code session

Loading your memory and capturing it both happen in the model's context, where you never read them. In Claude Code, Slate says so in one line each time.

WhenWhat prints
The session startsSlate · <branch> · 5 facts, 3 decisions, 3 sessions — what it just loaded
The session saves memorySlate · saved 3 memories from this session · <page>, and a desktop notification
Slate interrupts a stopStop hook feedback: Slate · this session did real work but saved nothing yet. Two lines at most, with no page id, and the model then ends with one short line instead of a second summary
A plan was made and not savedStop hook feedback: Slate · you made a plan. Ask the user whether to save it as a Plan page in Slate…, then the model asks you with a click

Each prints at most once per session, and a session with nothing to load says nothing. Claude Code before 2.1.163 shows the interruption as Stop hook error: instead, because it has no other way to hand the text to the model. The notification goes through the terminal, so it looks like any other Claude Code raises. Claude Code only: the other four tools have no field for a line addressed to you, and a wrong key there is dropped silently by some and throws away the whole message in others.

Four commands in every session

The plugin also puts Slate in the / menu. Type /slate in Claude Code:

CommandWhat it does
/slate:briefWhat Slate knows about this project, in a few lines
/slate:recall <what>Search your memory, and check any code it cites
/slate:remember <fact>Save one fact, in your words
/slate:openOpen this branch's page in the Slate app

What turning a tool off puts back

The record also holds what each file contained before Slate first wrote to it. When you disconnect, a file that only Slate has changed since goes back to those exact bytes, and a file Slate created is deleted. If you or the tool edited the file after Slate did, Slate removes only its own parts and keeps your edit.

When turning a tool off does not work

Disconnect can fail, and it tells you rather than reporting success. Two things have to come out — the plugin, and any hooks the old route left — and Slate names whichever did not, hooks first, because those are the half that would keep running. If the plugin will not come out, the message gives the exact command to run in a terminal, such as codex plugin remove slate@slate. Either way Slate remembers you turned the tool off, so the next launch does not put it back.

Profiles

A tool's servers, sign-in and history live in a config directory, and four tools can have more than one: CLAUDE_CONFIG_DIR, GEMINI_CLI_HOME, CODEX_HOME, CURSOR_CONFIG_DIR. Open a row and pick which Profile this workspace uses, or Add one by naming it and its config folder. The add form offers the config folders the tool already has in your home folder, such as ~/.claude-work, as buttons, and Choose folder… picks any other. A path that does not exist yet is fine: the tool creates it when you sign in. You can pick before you connect, because the profile decides where Slate gets installed. What a profile is, and why two workspaces naming the same one share its sign-in, is CLI Config Profiles.

OpenCode has no documented config-directory variable. It reads exactly one configuration, so there is no profile to choose, and equally no wrong one to land in.

Models

Every tool offers a model list, and the row shows it once this workspace runs the tool. Leave it on its own default and Slate passes no model, so the CLI picks. The tool you mark default is the one this workspace reaches for when nothing more specific is named; a group, or a project on its own, can still override any of it.

Checking it actually works

A connected tool that is not working looks exactly like a connected tool nobody used, so "no sessions captured" has never told you which of the two it was. Slate keeps the plugin itself current: its hooks and its MCP server run the Slate the app is running, not the copy the tool installed. A tool that caches a plugin by version, as Codex does, still gets today's Slate the moment the app updates, and the copy inside the plugin is used only on a machine without the app. Every release is also a new plugin version, and the next launch refreshes what each tool holds. Run this in a terminal to check the rest:

"$HOME/Library/Application Support/app.slate.workspace/hooks/slate-hook" doctor

It reports, per tool: how many hooks are installed, whether each one points at a file that exists and can run, and when a session of that tool last reached Slate. Three outcomes matter:

  • n hook(s) OK with a recent session — working.
  • BROKEN — the hook cannot run, and the line says why and which file to fix. This is Slate's fault and Slate should fix it.
  • OK but nothing recorded — the wiring is sound and something outside Slate is stopping it. Usually one of: the tool has not been used since you connected it, the tool needs its hooks approved once, or the account cannot sign in.

Two of those last cases are worth naming, because both are silent:

  • Codex runs no plugin hook until you trust it. It ships a hook-trust step, and until you clear it in Codex, codex plugin list says installed, enabled while nothing at all runs.

Slate checks for this itself. Each tool's panel compares the sessions the tool wrote on this machine in the last 7 days with the sessions Slate's hooks recorded, and when fewer than half were recorded it says so — for example "Codex ran 9 sessions in the last 7 days and Slate saw 1" — with the step that fixes it.

  • Gemini CLI cannot sign in on a personal Google account. It returns IneligibleTierError and never starts, so Slate's hooks there are correct and unreachable. An API key or a Code Assist licence is the only way round it.

Apps

The work apps this workspace connects, as one catalog, and what those connections let it serve.

Connect an app

Connect an app is a grid with one tile per work app, each with its own logo. The apps Slate can sign in to by itself, through each app's own official server, come first — GitHub (read through your gh), Jira, GitLab, Notion, ClickUp, Linear, monday.com, Basecamp, Shortcut and Todoist — most used first, by the Stack Overflow Developer Survey's share of developers using each; apps the survey does not cover follow, A to Z. Below them, Coming soon lists the apps Slate cannot connect yet, in the same order, each saying why — Slack, Teams, Gmail, Outlook and Asana need Slate registered with that vendor first. Solve, Review and Reply narrow the grid to the apps whose work shows in that group of Tasks (mail is under Reply), and Find an app searches it.

Press Connect, approve Slate on the app's own page in your browser, and what you owe there shows up in Tasks. No AI tool is involved, and nothing has to be set up in one first. GitHub's Connect runs its gh sign-in.

  • The sign-in is Slate's own and stays on this Mac, so a restart or an update never asks again. When the app ends it (you changed your password, an admin removed access), the row says Needs sign-in and offers Sign in again. A connection is judged by its own sign-in only: if an AI tool's server already reads the same app, that read never makes the connection look signed in.
  • An app can accept the sign-in and still refuse Slate's reads, because of a setting in the app. Its tile and the banner then say Unavailable and, in one sentence, what to change — or the app's own words when Slate does not know the message. GitLab is one: "GitLab blocks Slate until you turn on “Allow connection to GitLab” in a GitLab group you own." The setting is in the group's Settings, General, Permissions and group features; a group made before GitLab 19.5 has it off.
  • A connected app Slate has not managed to read yet says Not read yet on its tile, and waits as a logo under Not reading yet in the Tasks pane, instead of a 0 that would only mean nobody could read it. Its tile offers Teach Slate, which asks your AI tool once how to read it; Slate keeps the answer and reads it on its own from then on. This is how a Notion workspace is read: every Notion workspace keeps its tasks in a database of its own making.
  • Jira says your Jira admin may need to allow Slate first: Atlassian lets an organisation choose which apps may connect.
  • Disconnect forgets Slate's sign-in to that app. Its tasks leave with the next sync, unless a server one of your AI tools declares still reads it.
  • The last tile, Another app, connects any MCP server: name which app it is, give its https address, and sign in the same way.
  • When you connected an app here, Slate reads it here and not through an AI tool's server for the same app, so one task never comes from two places.

Each workspace keeps its own connections.

Background jobs

Everything Slate does when you are not asking it to, and a switch for each — with what turning it off costs, said in the app. Full detail is in Background jobs.

What is not here

Settings holds what belongs to the app and this computer — your account, the workspaces this machine holds, appearance, the terminal, shortcuts, and the version. One of its tabs is not the machine's: Data moves the open workspace's file and restores that workspace's snapshots.
