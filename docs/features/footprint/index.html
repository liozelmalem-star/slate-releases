What Slate Costs Your Machine

When nothing changes, Slate does nothing. If you are not typing, no file changed and no AI session is writing, Slate should use almost no CPU, and it should wake your Mac as little as it can. Slate's own tests measure it against the limits on this page, and a change that goes over one fails them.

The limits only go down. When a change makes Slate cheaper, its limit is lowered in the same change. No limit is ever raised.

The limits

Each number below is the most Slate may use. Slate usually uses less: each limit was set from the middle value of five measured runs, with room added for a busy machine (twice the measured CPU; 10% more memory, size and wake-ups). The tables are written from the limits file the tests read, so this page cannot disagree with them.

"% of one core" means the share of one processor core. 100% is one core fully busy, and your Mac has several.

How they are measured

The tests measure Slate in four parts. None of them uses your data or your machine: the test makes its own stores and launches its own copy of the app.

  • The server. Slate's server runs on three made-up stores: one for a new user, one for six months of use, and one for a heavy user. They are built from a fixed seed, so they are the same store on every machine. The server is started, left to settle, and then watched for a fixed time while nothing happens. The test records the CPU it used, how often it woke up to run code, and its memory at the end: the memory it has written to, as Activity Monitor shows it, not pages macOS can take back at any time.
  • The server while AI sessions work. The same server, on the six-months store, with two made-up AI sessions in a made-up home folder: one in a project folder, one in a plain folder, and one of them writing every 2 seconds. The test records the CPU the server used, and counts every program it started on its own (such as git), through stand-ins that log each start. While nothing but the sessions' own writing changes, that count must be zero. Your real sessions are never read.
  • The server in use. The heavy store, with 600 MB of made-up AI sessions captured (three still running), and Tasks, Sessions and Memory opened. Two minutes after launch the test reads the memory the server's code still holds once everything it no longer uses is cleared.
  • The app. A test copy of Slate opens each screen in turn and stays on it, idle. The test adds up the CPU of every process that copy owns: the app itself, its server and the web view helpers macOS starts for it. Then the window is hidden and measured once more.
  • The size. The download (.dmg), the installed app (.app), and the part of the app and its server built for each kind of chip.

A number that is over its limit is measured a second time, and counts only when both runs are over. This keeps a short spike on a busy machine from failing a change.

The limits are measured on one Mac, named under the tables. A slower Mac takes longer to do the same work, so it may show a higher percentage for the same idle Slate.

Check it yourself

You can see what Slate uses on your own Mac with Activity Monitor (in Applications → Utilities).

  1. Leave Slate open on any screen and do not touch it for a minute.
  2. In the CPU tab, search for Slate. You will see the app and its server (slate-mcp). Add their % CPU values. The tables also count the web view helpers macOS runs for Slate's window, so Slate's real total is a little higher than this sum.
  3. In the Energy tab, look at Slate's Energy Impact and Avg Energy Impact. An idle Slate should sit near zero. A high average while you were not using it is worth reporting.
  4. Hide the window (⌘H) and look again. That is the "Window hidden" row.

Your numbers can be higher than the idle limits for a good reason: while an AI session is writing, Slate reads it as it happens, and that is work you asked for. The "while AI sessions work" row is the limit for that. Slate reads what a session wrote, and does not start programs on a timer to check on it.

A session that keeps working is not a reason for the screen to keep moving. Its dot on the rail and in Sessions moves when the session starts working or starts waiting on you, then holds still. Slate's own tests reject any animation that never ends, except while something finishes on its own, such as a page loading or an app being built.
