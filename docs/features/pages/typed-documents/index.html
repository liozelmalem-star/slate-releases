Typed Documents & Hierarchy

Every page is the same row in the same table, but two columns give it meaning: doc_type says what kind of document it is, and status says where it stands. Together they turn a flat page store into a structured workspace that the AI memory tools can navigate.

Document types

Setting a page's doc_type pre-fills a structured template so you start with the right sections instead of a blank block. The DocType enum lives in @slate/schema (doc-type/types.ts):

DocTypePurpose
generalA plain knowledge page.
designA design document.
planAn implementation or work plan.
reviewA review write-up.
meetingMeeting notes.
test-planA test plan.
bug-reportA bug report.
projectA top-level project container.
repoA code repository under a project.
branchA feature branch under a repo.
missionA tracked unit of work. See Missions.

Status

A typed page also carries a status from PAGE_STATUSES:

StatusMeaning
draftStarted, not yet active.
activeIn progress.
doneCompleted.
canceledAbandoned.

The hierarchy

Some doc types are structural. They form a nesting the memory layer relies on (@slate/schema, doc-type/rules.ts):

project
└── repo
    └── branch
        └── knowledge pages
            (plan | design | test-plan | bug-report | review | meeting | general)

Knowledge pages don't have to sit under a branch — they can also live directly under a project or a repo. What can nest under what is enforced by ALLOWED_DOC_CHILDREN, so the tree stays valid: you can't, for instance, drop a repo inside a branch.

The hierarchy isn't bureaucracy — it's what makes the memory tools work without you naming an explicit page id. When an AI tool calls recall or remember, Slate resolves a target from the current branch, repo, and project by walking this structure. A decision remembered on a feature branch lands on that branch's Decisions section; a repo convention lands in the repo's Notes. No structure, no place to route it.

Filling one in

A knowledge page no longer generates itself. To have a brain write into it, start a session from the page — Start session on the page's own header, or from the Sessions tab — and the agent launcher hands the CLI the page, its lineage (project → repo → branch), the branch's goal and next open item, and the decisions already recorded in that project. See Sessions → Starting a session from a page.
