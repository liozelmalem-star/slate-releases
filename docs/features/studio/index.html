Features

Toolkit

Each AI coding tool wants its instructions in its own place and format. Hand-kept copies drift. Toolkit keeps one source and writes an adapter for every tool.

In the app, Toolkit shows everything a project's agents read, one tab per kind: Skills, Commands, Subagents, Rules, Instructions, MCP servers, Hooks, Plugins, Output styles and Config files, then agents. Its edits are committed like any checkout's, in Projects → Code → Changes.

The source of truth

You edit two things, both checked into the project:

SourceRole
AGENTS.mdThe cross-tool entry point: how to work in this project.
.slate/config.toml (the manifest) and skills/, one SKILL.md per skill.

Generated adapters

yarn studio sync reads the manifest and writes each tool's adapter. Most outputs are generated, listed in a Slate block of the project's .gitignore, and never hand-edited. Codex's project skills are checked in as symlinks so Codex finds them in a fresh worktree.

ToolGenerated paths
Claude Code.claude/skills/, .mcp.json, CLAUDE.md
Cursor.cursor/skills/, .cursor/mcp.json, .cursor/rules/slate.mdc
Codex.agents/skills/ (tracked), .codex/config.toml (generated)
Gemini CLI.gemini/skills/, .gemini/settings.json
OpenCode.opencode/skills/, .opencode/opencode.json
GitHub Copilot.github/skills/, and the .mcp.json Claude Code reads

The manifest's rules line names the real rules file, AGENTS.md by default. Codex, Cursor, Gemini and OpenCode read that name themselves. CLAUDE.md is a symlink to it. Every adapter carries the same skills and MCP configuration in the shape its tool expects.

If a tool's skills folder is itself a link (often to a folder shared between projects), sync writes nothing through it and prints a skills skipped line naming the folder and the link.

Sync writes outside the project in one case. When .slate/ lists MCP servers, a sync you start writes them into the machine-wide Claude Desktop config (macOS and Windows, where the app is installed) and into ~/.cursor/mcp.json. You start one with yarn studio sync, with Sync now, or by changing a .slate/ skill or the rules file in Toolkit. Two syncs never write there: the one Slate runs itself when .slate/ changes, and any sync inside a linked git worktree. STUDIO_SKIP_DESKTOP=1 stops it too.

Commands

yarn studio sync     # write the adapters from AGENTS.md + .slate/
yarn studio check    # fail on drift (part of yarn receipt)
yarn studio status   # per-tool table of what is projected
yarn studio prove    # sources, adapters, symlinks, and a live probe of each installed tool

yarn studio check keeps a stale CLAUDE.md or .cursor/ out of main.

In the app

The side panel's picker starts with Your agents (what you keep for every project), then the projects that have a folder, by group, with or without a .slate/. Groups and plain docs are not projects. If Slate cannot read a project's folder, the doc says so. A project with more than one .slate/ gets a second picker, each named by its folder.

Every project has the same tabs: Overview, Suggestions with the number waiting, one tab per kind with its count, then Agents. A kind with nothing in it is not listed. Hovering a tab says when a tool loads that kind: a skill when the task matches its purpose, a command when you type /name, a rule when the file in use matches it, instructions at the start of every session. The + in the title row asks which kind to add and opens that kind's New dialog.

Overview is where Toolkit opens. It shows one row per kind: its name, its first five items in one grey line, and how many it holds. An empty kind is not drawn. A row opens that kind's tab. When suggestions wait, a card at the top says how many and its Review button opens Suggestions. Your agents has no Overview and opens on Skills.

An empty kind keeps its tab and a New … button. Only tools this workspace connects get a mark. A personal file such as settings.local.json is marked this computer only. A config file that does not parse is listed with the reason and what its tool does about it. Gemini CLI and OpenCode, for example, refuse to start.

How often each item ran

Rows on Skills, Commands, Subagents and MCP servers show how often the item ran in this project's sessions in the last 30 days: ran 4× · 3h ago, then 1 failed or 1 stopped by you when that happened. Hover for the runs by tool. An unused item says not run in 30 days. Until the first session in the project ends, rows say not recorded yet. Until 30 days are recorded, an unused item says not run since the day recording began. When no tool that reads an item records its runs, the row says not measured:

KindTools whose sessions show it
SkillsEvery agent: a slash command, a Skill call, or a read of the skill's SKILL.md
CommandsClaude Code
SubagentsClaude Code: the subagent type each Task call names
MCP serversClaude Code and Codex, which name each call mcp__<server>__<tool>

When a session's turn ends, Slate reads its transcript and stores one row per use, at the same moment as the session's receipt. The rows stay in the workspace's database on this computer. Rereading a session replaces its rows, so nothing is counted twice. A worktree session counts for the project's main checkout. Failed means the call returned an error. Cursor records no call results and a skill records none, so neither counts as failed. Stopped by you means you interrupted the turn while the item ran (Claude Code's interrupt, Codex's aborted turn), and that call is not counted as failed. No model call is made.

When you accept an Improve, Slate keeps how often the item ran, and how many of those runs you stopped, in the 30 days before. After 30 more days, hovering its row compares them: The 30 days before: ran 6×, 4 stopped by you. The 30 days after: ran 4×, 1 stopped by you. Until then it gives the day the 30 days end. Only the latest Improve of an item is shown.

Other places link to an item here: a session's Setup used (Sessions), the skill a kind of work runs in Workflow (Tasks), the skill an accepted lesson became (Memory), a subagent's type under a session, and each skill in the composer's / list.

When a project has Toolkit changes, the header shows N changes to commit in Code and opens Changes on that project. It counts every file Toolkit writes and updates as soon as you add or remove an item. Your agents has no such chip, because account folders are not in git. Files holding MCP servers, hooks and settings (.mcp.json, .cursor/mcp.json, .claude/settings.json and the like) can hold secrets and local paths, so Changes lists them unticked with a note. Tick one only when you mean to commit it.

With a .slate/, the toolbar also shows a status pill such as In sync or 1 tool behind that opens Agents.

A .slate/ project stays published while Slate runs. Slate watches .slate/, AGENTS.md and CLAUDE.md, and a moment after any change, from Slate, a terminal, an agent or git pull, it runs the sync. Editing a skill needs no sync, since tools read it through links. Adding, removing or renaming a skill, or changing config.toml or the rules file, is what the watch catches. This sync writes only inside the project. Sync now and yarn studio sync also write MCP servers to the machine-wide configs, as above.

Suggestions

Suggestions lists changes to the project's AI setup, worst first. Each says what was counted and has one button that makes the change, plus Dismiss (Keep for a removal). Nothing changes until you click. A dismissed suggestion is never offered again. An accepted Fix or Improve can return after 30 days, because a server can break again and a skill can fall out of use again.

KindWhen it is suggestedThe button
FixAn MCP server failed 3 of its last 5 calls. It shows the last errorOpen server opens MCP servers
CopyA skill or MCP server ran here, and a tool you used in 3 or more sessions here cannot see itAdd for <tool> links the skill into a folder that tool reads, or copies the server into its file
NewYou gave a general-purpose subagent the same task in 3 sessions, or typed a /command with no skill or command behind it in 3 sessionsCreate it opens the New form
ImproveYou typed a skill's /name 3 times and the AI never picked it, or you stopped it 3 timesOpen it opens the skill
RemoveIt did not run in 20 or more sessions of the tools that load it, counted from when its file was madeRemove takes it out of every folder and file that keeps it. A subagent's or command's row names the file

A lesson Memory proposes as a skill waits here as New. Accepting it in either place writes the skill once.

Counts use the same 30 days as the run counts, plus one row for every session read, so a session that used nothing still counts. Slate counts when you open Suggestions, at most once an hour per project, and adds at most 3 new suggestions a day. No model runs. A Remove is suggested only when every tool that loads the item records that kind of use, because the button removes it for all of them. A server Gemini CLI loads, or a subagent Cursor reads, is never called unused. A session that ended before the item's file was made does not count against it. A Copy or Remove of a skill is not suggested in a project with .slate/, which decides which tools get each skill.

Toolkit's rail entry shows how many wait.

An agent can add to Suggestions through the MCP tool propose_setup_change: a fix, copy, create, improve or removal of a skill, command, subagent or MCP server, with a sentence on why. It sits beside Slate's own, and the 3-a-day cap does not apply. Nothing is written until you accept. A New skill or subagent can carry its whole file. Once you accept or dismiss a change, the same change is refused. Also refused: a New for a name the project already has, and a removal of a subagent or command that names any file other than its own. An instructions file such as CLAUDE.md is never removed from a suggestion.

Start using .slate

A project without .slate/ shows Start using .slate at the top of its Toolkit tab. Each skill is kept once in .slate/skills/ and published to every tool you pick. Before writing, it says what it will do:

  • create .slate/config.toml, listing the tools and every skill;
  • move each skill from .claude/skills, .agents/skills and the other tools' folders into .slate/skills/. Where two tools keep different copies, you pick which stays. studio sync then links each tool's folder back;
  • make the instructions one file. With neither file, it creates AGENTS.md. With AGENTS.md and a CLAUDE.md that has its own text, that text is appended to AGENTS.md under From CLAUDE.md and CLAUDE.md becomes a link. With only CLAUDE.md, it stays the real file and sync makes AGENTS.md the link;
  • leave MCP servers in each tool's own file, since a server listed in .slate/ is also written to the machine-wide Claude Desktop and Cursor configs on every sync.

A skill folder that links elsewhere in the project is copied, and its target is left alone. The same holds when a tool's whole skills folder links to a shared folder outside the project. An AGENTS.md that is itself a link (often to CLAUDE.md) is first made a real file with the same text, so the only copy is never lost. Nothing is committed: Projects → Code → Changes shows every file, and discarding one brings it back. Before removing a skill folder or CLAUDE.md that git never tracked, Slate keeps a copy in the project's git folder (slate-adopt/), never committed and kept after you commit the adoption.

Adding

The + opens a form for the open kind, such as New skill on Skills. Where an item can go to more than one place, the form shows a card per place with the tools that read it, and any number can be ticked. A line under the cards names every tool that will read the item.

New skill also opens from a kind of work in Tasks' Workflow box (Tasks) and from an automation's Follows (Automations). Toolkit switches to that project with a name and description filled in. Create writes the skill, binds it to what asked, and goes back. Cancel goes back with nothing written.

  • Skill: a name, what it does, and where it goes: .slate/skills (when the project has one: every tool, with a group and a blank doc or a copy of an existing skill), .claude/skills, .agents/skills. Ticking .slate/skills greys out the others, since .slate/ publishes into them. In tool folders the skill is written once and the others link to it. Who starts it is you or the AI (default), only you, or only the AI. Claude Code reads that as disable-model-invocation: true (only you) or user-invocable: false (only the AI). Other tools let both start a skill.
  • Command, subagent, rule, output style: a name, a few fields and the tools' folders. The fields are written in each tool's own shape, and a Writes box shows each file's header before you press Create.
  • Rule: when it applies (Always, When files match with patterns such as packages/server/** separated by commas, When relevant, or Only when mentioned) and a description. These are Cursor's four types (alwaysApply, globs, description in its .mdc). Claude Code reads a rule only always or by files, as paths: in .claude/rules/<name>.md, so the last two choices drop .claude/rules. A Codex rule is a command policy: the command's first words, the decision (Allow, Ask first, Forbid) and why.
  • Subagent: when to hand work to it, the model (Same as the session, Fast, Strongest) and its tools (All, Read only, or picked from read, search, edit, run commands and web). Each tool gets its own words: Claude Code model: inherit | haiku | opus and tools:, Cursor model: fast and readonly: true, Gemini CLI model: flash | pro, Codex model_reasoning_effort and sandbox_mode = "read-only", OpenCode mode: subagent and a tools: map. OpenCode keeps the session's model. A Codex subagent is its .codex/agents/<name>.toml plus an [agents.<name>] table in .codex/config.toml that holds the description.
  • Command: a description and, for Claude Code only, an argument hint. A Gemini command is TOML (description, prompt). A Cursor command is a plain file.
  • Output style: a description and Keep coding instructions (on: adds to Claude Code's coding instructions. Off: replaces them).
  • Instructions: the instructions files the project lacks.
  • MCP server: a name, a command or URL, optional NAME=value variables, and the tools to add it to, each in its own format: OpenCode's command is one list and its variables are environment, Gemini spells an HTTP server httpUrl, Codex uses a [mcp_servers.<name>] table. Each ticked tool shows its file. Variables are stored as plain text in files at the project root that are often committed, so keep real keys out of a shared project.
  • Hook: a tool (Claude Code, Cursor or Gemini CLI), an event from its list, an optional matcher such as Bash|Edit, the command, and a timeout (seconds for Claude Code and Cursor, milliseconds for Gemini). A Claude Code hook can go in settings.local.json to stay on this computer. Codex hooks are not editable yet.
  • Plugin: its name and the tools to enable it for: Claude Code's enabledPlugins, Codex's [plugins."<name>"], OpenCode's plugin list. Installing stays the tool's own command.

Editing and removing

A row opens its file on its own tab. Markdown opens drawn, like a README: header fields on top, then the text, with a Preview / Markdown switch. A rule, subagent, command or output style shows the same fields as the New form above its text. A choice saves at once and a text box when you leave it. Only the keys that field writes change, and other keys, comments and key order stay. A model the three choices do not name (sonnet) stays until you pick one. A header that does not parse hides the fields until fixed in the text. Text saves when you stop typing. The rules file saves when you leave the box, or with ⌘S. A config that would no longer parse is not saved. The check parses each file as its tool does, so Gemini's settings.json and OpenCode's opencode.json may carry comments and Claude Code's and Cursor's JSON files may not. With a .slate/, editing the rules file syncs it to every tool. A Config files row opens the file as on disk, so an MCP server's variables in .gemini/settings.json, .codex/config.toml or opencode.json show there. An MCP server's own row never shows them.

A .slate/ skill opens in its editor, which can hold more than one file, publish to some tools only, and show its History (any commit can be restored). Its row menu can rename, duplicate, copy to another project or Remove… it. Removing takes its folder out of .slate/skills/ and its copy in every tool. Until you commit, discarding it in Projects → Code → Changes brings it back.

Every other row has a trash icon titled Remove <name>. It asks first with Remove <name>?, Keep it and Remove <name>, naming the files and tools it reaches. A skill is removed from every tool folder that keeps it, with its links. A subagent, rule, output style or command is its file, and a Codex subagent's [agents.<name>] table goes too. An MCP server is removed from every tool's file, and the file stays. A hook row takes all its commands and the file stays. A plugin named in a config file is turned off. A plugin that is a file in .opencode/plugins has no trash icon. Instructions and Config files rows are never removed from here.

A skill behind a tool folder that links to a shared folder elsewhere is not removed there. Slate says which folder kept it.

An MCP server row opens a panel listing each connected tool, with Remove from for a tool that has the server and Add to for one that does not. It says when a server will not load yet: Claude Code waits for approval of a .mcp.json server, and Codex reads .codex/config.toml only in a project it trusts. Slate never approves a server for you. A JSON file with comments is never rewritten, because the comments would be lost. A server's variables and headers never reach the screen. A hook row opens its commands, each with Remove.

When two tools keep different files under one skill name, the row says 2 copies. Open it to compare, then Use this copy for all agents to keep one and point the other folders at it.

Your agents

What each agent keeps for every project, in its own config folder and plugins, laid out like a project with the same tabs and counts, except there is no Agents tab. Home folders have no git and nothing to publish.

New skill adds a skill for every project. It goes in ~/.claude/skills (Claude Code), ~/.agents/skills (Codex, Gemini CLI, OpenCode and Cursor) or both. Ticking both writes it once and links the other folder to it.

Each tab has chips at the top that pick one profile (~/.claude-personal, ~/.codex) or plugin at a time, with its count for that kind. Two profiles of one tool often keep the same skill in different places. A profile that could hold the kind has a chip even when empty. A row opens its file to read or edit, and a config saves only if it still parses.

The + adds to the picked profile on every tab where its tool keeps that kind: a subagent in ~/.claude-alt/agents, a hook in that profile's settings file, an MCP server in ~/.codex/config.toml. Output styles exist only in Claude Code profiles. A row's trash removes it from that profile after a note that every project on this computer stops seeing it. A removed file goes to the Trash. Skills and commands a plugin brings have no trash. Remove the plugin instead.

Only the profiles the current workspace uses are read. When a workspace names none, every profile found on this computer is read. Claude Code's user MCP servers live in .claude.json, which also holds sign-in data, so Toolkit does not list, open or change it. Add those with claude mcp add --scope user.
