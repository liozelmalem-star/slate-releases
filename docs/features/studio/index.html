Features

Skills

Every AI coding tool wants its instructions in its own place and its own format, so five copies kept by hand are five copies that drift. Skills keeps one and projects it into all of them. Change the source, run one command, and every adapter is rewritten.

The source of truth

Two things, both checked into the repo, are the only ones you edit:

SourceRole
AGENTS.mdThe cross-tool entry point — how to work in this repo.
.slate/config.toml, the manifest, and skills/ — one SKILL.md per skill.

Generated adapters

yarn studio sync reads the manifest and writes a per-tool adapter. Most outputs are generated and gitignored — you never hand-edit them. Codex repo skills are checked in as symlinks so Codex can discover them in a fresh worktree:

ToolGenerated paths
Claude Code.claude/skills/, .mcp.json, CLAUDE.md
Cursor.cursor/skills/, .cursor/mcp.json, .cursor/rules/slate.mdc
Codex.agents/skills/ tracked in the repo, .codex/config.toml generated
Gemini CLI.gemini/skills/, .gemini/settings.json
OpenCode.opencode/skills/, .opencode/opencode.json

AGENTS.md is the rules file itself — the name Codex, Cursor, Gemini and OpenCode read on their own — and CLAUDE.md is a symlink to it, so the entry point stays one file however a tool asks for it. Each adapter carries the same skills and the same MCP configuration, in the shape that tool expects.

Commands

yarn studio sync     # write the adapters from AGENTS.md + .slate/
yarn studio check    # fail on drift (runs pre-push)
yarn studio status   # per-tool table of what is projected
yarn studio prove    # the full gate: sources, adapters, symlinks, live CLI probes

yarn studio check is the guardrail: a stale CLAUDE.md or .cursor/ cannot slip into a push.

In the app

The side panel's picker lists every project with a folder, with or without a .slate/. Groups and plain pages are not projects, so they are not listed. A project whose folder is not on this computer says so and names the path. The picker's last entry, Your AI tools, shows the skills and setup you keep for every project (see below).

Every project gets the same tabs, whether or not it has a .slate/. The side panel lists one tab per kind of thing the project's AI tools read, each with its count and a + that opens that kind's New dialog, then Tools and Changes:

Output styles (.claude/output-styles) gets a tab once the project has one.

A kind with nothing in it still has its tab, so its first item can be added. Only the tools this workspace connects get a mark. A personal file, such as settings.local.json, is marked this computer only. A config file that does not parse is listed with the reason and what its tool does about it: Gemini CLI and OpenCode refuse to start, for example.

The toolbar says how many edits wait to be committed and, with a .slate/, holds a status pill such as In sync or 1 tool behind that opens Tools.

A .slate/ project stays published by itself while Slate runs. Slate watches each project's .slate/ folder and its AGENTS.md, and a moment after either changes it runs the sync — whoever made the change: Slate, a terminal, an AI tool or a git pull. Editing a skill needs no sync at all, since the tools read it through links; adding, removing or renaming one, or changing config.toml or AGENTS.md, is what the watch catches. This background sync writes only inside the project. Sync now on Tools (and yarn studio sync) also writes the project's MCP servers into the machine-wide Claude Desktop and Cursor configs.

Start using .slate

A project without a .slate/ shows Start using .slate at the top of its Skills tab. It keeps each skill once, in .slate/skills/, and publishes it to every tool you pick. Before anything is written, it says what it will do:

  • create .slate/config.toml, listing the tools and every skill;
  • move each skill from .claude/skills, .agents/skills and the other tools' folders into .slate/skills/. Where two tools keep different copies, you pick which stays. studio sync then links each tool's folder back to it;
  • make the instructions one file. If the project has no AGENTS.md, it creates one. If CLAUDE.md has its own text, that text is added to the end of AGENTS.md, and CLAUDE.md becomes a link to it;
  • leave MCP servers in each tool's own file. A server listed in .slate/ is also written into the machine-wide Claude Desktop and Cursor configs on every sync, which starting to use .slate in one project should not do.

A skill folder that is a link to a folder elsewhere in the project is copied, and the folder it points to is left alone. Nothing is committed: Changes shows every file, and Discard brings it all back.

Adding

The + beside a tab opens a form for that kind. Where an item can go to more than one place, the form shows one card per place, with the tools that read it, and any number can be ticked. A line under the cards names every tool that will read the new item.

  • Skill: a name, what it does, and where it goes: .slate/skills (when the project has one: every tool, with a group and a blank page or a copy of an existing skill), .claude/skills, .agents/skills. Ticking .slate/skills greys the others out, since .slate/ publishes into them. In tool folders the skill is written once and the other folders link to it, so there is one file to edit.
  • Command, subagent, rule, output style: a name, and the tools' folders. Each is started in that tool's own shape: a Gemini command is TOML, a Cursor rule an .mdc file, and a Codex subagent is its .codex/agents/<name>.toml plus its [agents.<name>] table in .codex/config.toml. Formats differ, so each folder gets its own file.
  • Instructions: the instructions files the project does not have yet.
  • MCP server: a name, a command or a URL, optional NAME=value variables, and the tools to add it to, each written in its own format: OpenCode's command is one list and its variables are environment, Gemini spells an HTTP server httpUrl, Codex keeps it as a [mcp_servers.<name>] table.
  • Hook: a tool (Claude Code, Cursor or Gemini CLI), an event from that tool's own list, an optional matcher such as Bash|Edit, the command, and a timeout: seconds for Claude Code and Cursor, milliseconds for Gemini. A Claude Code hook can go in settings.local.json so it stays on this computer. Codex hooks are not editable yet, because Codex's project hooks file has not been measured.
  • Plugin: its name and the tools to turn it on for — Claude Code's enabledPlugins, Codex's [plugins."<name>"], OpenCode's plugin list. Installing it stays the tool's own command.

Editing and deleting

A row opens its file in place, on its own tab. A markdown file opens drawn, like a README: its header's fields on top, then the text, with a Preview / Markdown switch at the top. Edits save by themselves when you stop typing. A config that would no longer parse is not saved, and the file on disk stays as it was: the check parses each file the way its tool does, so Gemini's settings.json and OpenCode's opencode.json may carry comments and Claude Code's and Cursor's JSON files may not. With a .slate/, editing AGENTS.md syncs it out to every tool.

A .slate/ skill opens in its editor, which can hold more than one file, publish it to some tools only, and show its History (any commit can be restored). Its row's menu can rename, duplicate, copy it to another project or delete it.

Every other row has a trash icon, and an open file a Delete button; both ask first. A skill is deleted from every tool folder that keeps it; an MCP server from every tool's file; a hook row takes all its commands; a plugin is turned off. Instructions and settings files are never deleted from here.

An MCP server row opens a panel that lists each connected tool, with Remove from for a tool that has the server and Add to for one that doesn't. It says when a server won't load yet: Claude Code waits for approval of a .mcp.json server, and Codex reads .codex/config.toml only in a project it trusts. Slate never approves a server for you. A JSON file with comments is never rewritten, because Slate would lose them. A server's variables and headers are never sent to the screen. A hook row opens the commands that run there, each with Remove.

When two tools keep different files under the same skill name, the row says 2 copies. Open it to compare them, then Use this copy for all tools to keep one and point the other folders at it.

Your AI tools

What each AI tool keeps for every project, in its own account folder and its plugins, laid out like a project: the same tabs in the side panel, each with its count — Skills, Commands, Subagents, Rules, Instructions, MCP servers, Hooks, Plugins and Settings. Home folders have no git and nothing to publish, so there is no Tools or Changes tab, and nothing is added from here yet.

Each tab has chips at the top that pick one account (~/.claude-personal, ~/.codex) or plugin at a time, with how many of that kind it holds: two accounts of one tool often keep the same skill, and they are different places. A row opens its file to read or edit; a config is saved only if it still parses.

Only the accounts the current workspace uses are read. When a workspace names none, every account found on this computer is read. Claude Code's user MCP servers live in .claude.json, which also holds sign-in data, so Skills does not list or open that file.
