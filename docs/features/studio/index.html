Features

Toolkit

Every AI coding tool wants its instructions in its own place and its own format, so five copies kept by hand are five copies that drift. Toolkit keeps one and projects it into all of them. Change the source, run one command, and every adapter is rewritten.

In the app this is the Toolkit place: everything a project's AI tools read, one tab per kind — Skills, Commands, Subagents, Rules, Instructions, MCP servers, Hooks, Plugins, Output styles and Config files — then AI tools. Its edits are committed where every checkout's are: Projects → Code → Changes.

The source of truth

Two things, both checked into the project, are the only ones you edit:

SourceRole
AGENTS.mdThe cross-tool entry point — how to work in this project.
.slate/config.toml, the manifest, and skills/ — one SKILL.md per skill.

Generated adapters

yarn studio sync reads the manifest and writes a per-tool adapter. Most outputs are generated, and sync lists them in its own block of the project's .gitignore. You never hand-edit them. Codex project skills are checked in as symlinks so Codex can discover them in a fresh worktree:

ToolGenerated paths
Claude Code.claude/skills/, .mcp.json, CLAUDE.md
Cursor.cursor/skills/, .cursor/mcp.json, .cursor/rules/slate.mdc
Codex.agents/skills/ tracked in the project, .codex/config.toml generated
Gemini CLI.gemini/skills/, .gemini/settings.json
OpenCode.opencode/skills/, .opencode/opencode.json

The rules line of the manifest names the real rules file. It is AGENTS.md unless the manifest says otherwise, and that is the name Codex, Cursor, Gemini and OpenCode read on their own. The other of the two names, CLAUDE.md, is a symlink to it, so the entry point stays one file however a tool asks for it. Each adapter carries the same skills and the same MCP configuration, in the shape that tool expects.

If a tool's skills folder is itself a link (often to a folder shared between projects), sync skips it. It writes nothing through the link, and yarn studio sync prints a skills skipped line that names the folder and the link.

Sync writes outside the project in one case. When .slate/ lists MCP servers, a sync you start writes them into the machine-wide Claude Desktop config (macOS and Windows, where the app is installed) and into ~/.cursor/mcp.json. You start one with yarn studio sync, with Sync now, or by changing a .slate/ skill or the rules file in Toolkit, which runs a sync afterwards. Two syncs never write there: the one Slate runs by itself when .slate/ changes, and any sync inside a linked git worktree. Setting STUDIO_SKIP_DESKTOP=1 stops it too.

Commands

yarn studio sync     # write the adapters from AGENTS.md + .slate/
yarn studio check    # fail on drift (part of yarn receipt, the gate before a push to main)
yarn studio status   # per-tool table of what is projected
yarn studio prove    # sources, adapters, symlinks, and a live probe of each installed tool

yarn studio check is the guardrail: a stale CLAUDE.md or .cursor/ cannot slip into main.

In the app

The side panel's picker starts with Your AI tools, which shows the skills and setup you keep for every project (see below). After it come the projects that have a folder, by group, with or without a .slate/. Groups and plain pages are not projects, so they are not listed. If Slate cannot read a project's folder, the page says so and asks you to check that the folder still exists. A project with more than one .slate/ gets a second picker beside it, for which one to show; each is named by its folder.

Every project gets the same tabs, whether or not it has a .slate/. The side panel lists one tab per kind of thing the project's AI tools read, each with its count, then AI tools. Each tab's subtitle says when a tool loads that kind: a skill when the task matches what it says it is for, a command when you type /name, a rule when the file a tool works on matches it, and instructions at the start of every session. The + in the side panel's title row opens the New dialog for the kind that is open:

Output styles (.claude/output-styles) has a tab too.

A kind with nothing in it still has its tab, so its first item can be added. Its empty state holds a New … button for it too. Only the tools this workspace connects get a mark. A personal file, such as settings.local.json, is marked this computer only. A config file that does not parse is listed with the reason and what its tool does about it: Gemini CLI and OpenCode refuse to start, for example.

Toolkit's edits are committed in Projects → Code → Changes, the source control every checkout uses. When a project has Toolkit changes, the header shows N changes to commit in Code, and it opens Changes on that project. It counts every file Toolkit writes, the config files below included, and updates as soon as you add or remove an item. Your AI tools has no such chip: account folders are not in git. The files that hold MCP servers, hooks and settings (.mcp.json, .cursor/mcp.json, .claude/settings.json and the like) can hold secrets and paths from this computer: Changes lists them unticked, with a note saying why. Tick one only when you mean to commit it.

The toolbar says how many edits wait to be committed and, with a .slate/, holds a status pill such as In sync or 1 tool behind that opens AI tools.

A .slate/ project stays published by itself while Slate runs. Slate watches each project's .slate/ folder, its AGENTS.md and its CLAUDE.md, and a moment after any of them changes it runs the sync — whoever made the change: Slate, a terminal, an AI tool or a git pull. Editing a skill needs no sync at all, since the tools read it through links; adding, removing or renaming one, or changing config.toml or the rules file, is what the watch catches. This background sync writes only inside the project. Sync now on AI tools (and yarn studio sync) also writes the project's MCP servers into the machine-wide Claude Desktop and Cursor configs, as the section on generated adapters says.

Start using .slate

A project without a .slate/ shows Start using .slate at the top of its Toolkit tab. It keeps each skill once, in .slate/skills/, and publishes it to every tool you pick. Before anything is written, it says what it will do:

  • create .slate/config.toml, listing the tools and every skill;
  • move each skill from .claude/skills, .agents/skills and the other tools' folders into .slate/skills/. Where two tools keep different copies, you pick which stays. studio sync then links each tool's folder back to it;
  • make the instructions one file. If the project has neither file, it creates AGENTS.md. If it has AGENTS.md and a CLAUDE.md with its own text, that text is added to the end of AGENTS.md under a From CLAUDE.md heading, and CLAUDE.md becomes a link to it. If it has only CLAUDE.md, that file stays the real one and sync makes AGENTS.md the link;
  • leave MCP servers in each tool's own file. A server listed in .slate/ is also written into the machine-wide Claude Desktop and Cursor configs on every sync, which starting to use .slate in one project should not do.

A skill folder that is a link to a folder elsewhere in the project is copied, and the folder it points to is left alone. The same holds one level up: when a tool's whole skills folder is a link to a shared folder outside the project, the skill is copied in and the shared folder keeps its copy. An AGENTS.md that is itself a link (often to CLAUDE.md) is first made a real file with the same text, so making the instructions one file never loses the only copy of them. Nothing is committed: Projects → Code → Changes shows every file, and discarding a file there brings it back. That includes a skill folder or a CLAUDE.md that git never tracked: before it removes one, Slate keeps a copy in the project's git folder (slate-adopt/), which is never committed. The copy stays there after you commit the adoption.

Adding

The side panel's + opens a form for the kind that is open — New skill on Skills, New rule on Rules. Where an item can go to more than one place, the form shows one card per place, with the tools that read it, and any number can be ticked. A line under the cards names every tool that will read the new item.

  • Skill: a name, what it does, and where it goes: .slate/skills (when the project has one: every tool, with a group and a blank page or a copy of an existing skill), .claude/skills, .agents/skills. Ticking .slate/skills greys the others out, since .slate/ publishes into them. In tool folders the skill is written once and the other folders link to it, so there is one file to edit.
  • Command, subagent, rule, output style: a name, and the tools' folders. Each is started in that tool's own shape: a Gemini command is TOML, a Cursor rule an .mdc file, and a Codex subagent is its .codex/agents/<name>.toml plus its [agents.<name>] table in .codex/config.toml. Formats differ, so each folder gets its own file.
  • Instructions: the instructions files the project does not have yet.
  • MCP server: a name, a command or a URL, optional NAME=value variables, and the tools to add it to, each written in its own format: OpenCode's command is one list and its variables are environment, Gemini spells an HTTP server httpUrl, Codex keeps it as a [mcp_servers.<name>] table. Each ticked tool shows the file it will be written to. The variables are stored as plain text in those files, at the project's root, and such files are often committed to git: keep real keys out of a shared project.
  • Hook: a tool (Claude Code, Cursor or Gemini CLI), an event from that tool's own list, an optional matcher such as Bash|Edit, the command, and a timeout: seconds for Claude Code and Cursor, milliseconds for Gemini. A Claude Code hook can go in settings.local.json so it stays on this computer. Codex hooks are not editable yet, because Codex's project hooks file has not been measured.
  • Plugin: its name and the tools to turn it on for — Claude Code's enabledPlugins, Codex's [plugins."<name>"], OpenCode's plugin list. Installing it stays the tool's own command.

Editing and removing

A row opens its file in place, on its own tab. A markdown file opens drawn, like a README: its header's fields on top, then the text, with a Preview / Markdown switch at the top. Edits save by themselves when you stop typing. The rules file is the exception: it saves when you leave the box, or with ⌘S. A config that would no longer parse is not saved, and the file on disk stays as it was: the check parses each file the way its tool does, so Gemini's settings.json and OpenCode's opencode.json may carry comments and Claude Code's and Cursor's JSON files may not. With a .slate/, editing the rules file syncs it out to every tool. A Config files row opens the file as it is on disk, so an MCP server's variables in .gemini/settings.json, .codex/config.toml or opencode.json show there. An MCP server's own row never shows them.

A .slate/ skill opens in its editor, which can hold more than one file, publish it to some tools only, and show its History (any commit can be restored). Its row's menu can rename, duplicate, copy it to another project or Remove… it. Removing a skill takes its folder out of .slate/skills/ and its copy in every tool; until you commit, discarding it in Projects → Code → Changes brings it back.

Every other row has a trash icon titled Remove <name>, and it asks first: the dialog is Remove <name>?, with Keep it and Remove <name>. It names the files and the tools it reaches. A skill is removed from every tool folder that keeps it, with its links. A subagent, rule, output style or command is its file, and the file goes; for a Codex subagent its [agents.<name>] table in .codex/config.toml goes too. An MCP server is removed from every tool's file, and the file stays. A hook row takes all its commands, and the file stays. A plugin named in a config file is turned off; a plugin that is a file in .opencode/plugins has no trash icon. Instructions and Config files rows are never removed from here.

An MCP server row opens a panel that lists each connected tool, with Remove from for a tool that has the server and Add to for one that doesn't. It says when a server won't load yet: Claude Code waits for approval of a .mcp.json server, and Codex reads .codex/config.toml only in a project it trusts. Slate never approves a server for you. A JSON file with comments is never rewritten, because Slate would lose them. A server's variables and headers are never sent to the screen. A hook row opens the commands that run there, each with Remove.

When two tools keep different files under the same skill name, the row says 2 copies. Open it to compare them, then Use this copy for all tools to keep one and point the other folders at it.

Removing a skill takes it out of every tool folder that keeps it, except a copy behind a tool folder that is a link to a shared folder elsewhere: that one stays, and Slate says which folder kept it.

Your AI tools

What each AI tool keeps for every project, in its own config folder and its plugins, laid out like a project: the same tabs in the side panel, each with its count — Skills, Commands, Subagents, Rules, Instructions, MCP servers, Hooks, Plugins and Config files. Home folders have no git and nothing to publish, so there is no AI tools tab.

New skill adds a skill for every project. It goes in ~/.claude/skills (Claude Code), ~/.agents/skills (Codex, Gemini CLI, OpenCode and Cursor) or both; ticking both writes it once and links the other folder to it.

Each tab has chips at the top that pick one profile (~/.claude-personal, ~/.codex) or plugin at a time, with how many of that kind it holds: two profiles of one tool often keep the same skill, and they are different places. A profile that could hold the kind has a chip even with none yet. A row opens its file to read or edit; a config is saved only if it still parses.

The side panel's + adds to the profile that is picked, on every tab where its tool keeps that kind: a subagent goes in ~/.claude-alt/agents, a hook in that profile's settings file, an MCP server in ~/.codex/config.toml. Output styles exist only in Claude Code profiles. A row's trash removes it from that profile, after a note saying every project on this computer stops seeing it. A removed file goes to the Trash, where you can get it back. Skills and commands a plugin brings have no trash: remove the plugin instead.

Only the profiles the current workspace uses are read. When a workspace names none, every profile found on this computer is read. Claude Code's user MCP servers live in .claude.json, which also holds sign-in data, so Toolkit does not list, open or change that file: add those with claude mcp add --scope user.
