CLI Config Profiles

Your AI tools each keep a configuration directory — where auth, settings and history live — and you may well have more than one. A work login and a personal login are different directories, and which one a session uses decides whose account touched that code.

Slate makes that a property of the project, not of the app.

How it works

Open Connect → AI tools and, for every tool, choose the one account this workspace runs it under. A project can override the answer for itself; most never need to, and the table below is what a machine with two accounts looks like:

ProjectClaudeGemini
Acmethe work loginthe work login
Personalyour personal loginyour personal login

That single rule — one account per tool, per project — is what makes everything else unambiguous. Anything that runs picks a tool; the project it runs in supplies the account. So an agent, a Console turn, or a workflow step never stores a login, and moving a workflow between projects re-points it automatically.

Each account is a directory on your machine, shared by every project that names it. The project's panel says so, and names the other projects on that account.

Installing Slate into an account is not a project setting. Writing Slate's MCP server into a config directory covers every project that names it — one directory, one answer — so it lives once, in Connect → Automations → Where Slate is installed, which lists each account and the projects it covers. A project's own panel only declares: which tools, which account, which model.

Which folders a project covers

All of them — the folder on the project itself, and the folder of every repo under it. The project's own folders name them, and a session is judged by the deepest one that contains it. So a checkout that belongs to one project while sitting inside another project's folder is governed by the project it belongs to, and the enclosing project keeps everything else.

Nothing has to be re-saved for this: the list is derived from your pages, so a repo Slate discovered a minute ago is covered a minute ago.

What it governs

  • Which models the project's Console, agents and workflows may run.
  • The Console, when scoped to the project.
  • Agents and workflows that belong to it — including scheduled runs nobody is watching, which is where a wrong account matters most.
  • Sessions you start yourself in a terminal. Slate installs its hooks into each account — as a plugin for Claude Code and Codex, into the config directory for the rest — and they refuse the first prompt of a session running under an account the project does not use.

Models are never restricted — a project can set a default model per tool, but any model may be used.

What it can't govern

  • A tool with no config-directory setting (OpenCode and Cursor today) cannot be pinned to an account, so Slate declines to pretend otherwise: it can be captured, but not governed. The panel says which and why.
  • A project with no folder anywhere covers its pages but not a terminal — Slate matches a terminal session by its working directory, so a project with no directory to match has nothing to match against. Its own folder is not the only one that counts: every repo under it brings its folder along, so a project whose page names no folder still governs the checkouts it holds.
  • Enforcement fails open if Slate itself is broken (an unreadable setting, a crashed hook). That is deliberate: failing closed would make your AI tool unusable in every repo with no way to fix it from inside the broken tool. Two independent layers plus an after-the-fact report cover the gap.

How you know it's working

The project's Overview tab reports every captured session against the accounts the project declares, and flags any that ran under a different one. Without it, "nothing was refused" and "nothing was enforced" would look identical.

Capture follows the same list

Slate captures sessions from every account a project names. Assigning a tool under Connect → AI tools is the whole of it — there is no second list to keep in sync.
