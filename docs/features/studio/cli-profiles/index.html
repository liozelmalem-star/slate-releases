Project environments

Your AI tools each keep a configuration directory — where auth, settings and history live — and you may well have more than one. A work login and a personal login are different directories, and which one a session uses decides whose account touched that code.

Slate makes that a property of the workspace, with a per-project override.

How it works

Open Connect → AI tools and, for every tool, choose the account this workspace runs it under. A project can override the answer for itself; most never need to.

One account per tool, per project. Anything that runs picks a tool, and the project it runs in supplies the account — so an agent, a Console turn or a workflow step never stores a login, and moving a workflow between projects re-points it automatically.

The same switch installs Slate into that account, which is what gets its sessions captured. A config directory exists once on this machine, so every workspace naming it shares that sign-in.

Which folders a project covers

Its own folder, and the folder of every repo under it. A session is judged by the deepest folder that contains it, so a checkout belonging to one project while sitting inside another project's folder is governed by the project it belongs to.

Nothing has to be re-saved for this: the list is derived from your pages, so a repo Slate discovered a minute ago is covered a minute ago.

What it governs

  • The Console, when scoped to the project.
  • Agents and workflows that belong to it — including scheduled runs nobody is watching, which is where a wrong account matters most.
  • Sessions you start yourself in a terminal. Slate installs its hooks into each account — as a plugin for Claude Code and Codex, into the config file for the rest — and they refuse the first prompt of a session running under an account the project does not use.

A model is a starting point, never a limit. A project can set a default model per tool, and any model may still be used.

What it can't govern

  • OpenCode. No documented config-directory variable — CLAUDE_CONFIG_DIR, GEMINI_CLI_HOME, CODEX_HOME and CURSOR_CONFIG_DIR are the four that have one — so it cannot be pinned to an account. It is captured, not governed, and the row says so. Cursor joined the governed tools on 2026-09-20 once CURSOR_CONFIG_DIR was confirmed.
  • A project with no folder at all. A terminal session is matched by its working directory, so a project with no directory has nothing to match against. Every repo under a project brings its folder along, so this only bites a project holding none.
  • A broken Slate. Enforcement fails open: an unreadable setting or a crashed hook lets the prompt through. Failing closed would make your AI tool unusable in every repo, with no way to fix it from inside the broken tool.

How you know it's working

A strip at the top of the project page counts the captured sessions that ran under the accounts the project assigns, and names the ones that did not. Without it, "nothing was refused" and "nothing was enforced" would look identical.
