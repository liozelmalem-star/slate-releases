Slate is local-first: your work is a SQLite file on your machine and nothing leaves it unless you say so. Workspaces are the one deliberate exception — a way for a group to pool the knowledge they each wrote locally without giving up the local file, the offline app, or the single-writer simplicity that makes Slate fast.

The shape in one line: a workspace is either wholly private or wholly a team's, and you switch into one the way you switch branches.

Everything you do inside a shared workspace — pages, decisions, git activity, session records — belongs to that workspace's members by construction. Nothing is marked. There is no rule to get wrong.

Personal, and the ones you share

Your Personal workspace starts private and, unlike every other, fills without being asked: sessions captured from disk, repos with no project page, cross-project notes. It can be shared like any other workspace — every row carries the same switch — but because of what collects there, turning sharing on counts what it would publish and says so before you agree. The failure mode this design removes is the invisible one; a number you have to read is the opposite of invisible.

Every shared workspace is its own store, on its own disk file, on the same schema. That sameness is the point: the real page tree, the real editor, the real Memory graph, the real Activity dashboard and the real search all work in a shared workspace, because it is the same kind of thing they already worked in.

The switcher sits in the top bar and is always visible. That is a correctness requirement, not a design preference. Work landing in the wrong workspace is a privacy incident rather than a bug, so the question this design trades for — am I in the right workspace? — has to answer itself at a glance. Each workspace carries a colour, and a read-only one carries a padlock.

Switching resets the route to the Console first, and the tab strip comes back as that workspace's own. A page id only means something inside one store, so carrying #/page/<id> — or a saved strip of them — across a switch would open a page that does not exist there, or, with worse luck, a different page that happens to share the id, drawn under the title it was saved with.

What follows a switch, and what does not

Everything about the work is per workspace, the screen state included: which pages you have open in the tab strip, in what order, pinned where you pinned them. Every one of those names pages, and a page id only means something inside one store — so each workspace comes back to the strip you left it with, and a workspace you have never opened a page in starts empty.

Some things describe this computer, not an audience, and are identical in every workspace:

Machine-localWhy
Which AI sessions are open, and the Sessions rail's widthThey are processes on this machine, not knowledge a team has.
CLI brain accounts, spawn policy, theme, sidebar widthCredentials and preferences belong to you and to this laptop.
A project's folder pathAn absolute path describes your disk. Publishing it would hand the workspace your directory layout.

They live in a separate machine-level store, so they cannot be duplicated N times and disagree. Routines — agents, workflows and watchers — are not in that list: one is scoped to a project page, so it lives in the same store as the project it reads.

What it is not

It is easier to explain by what was deliberately left out:

  • Not co-editing. Each page has exactly one writer — its author — so there are no merge conflicts, no version column, no 409s, and no way for someone else's edit to reach your disk. A teammate's page opens read-only, with a line saying why. Read-only is the design, not a first step toward editing.
  • Not a sync of your database. Personal never syncs, ever. A shared workspace syncs because a shared workspace is for that; the file you keep your private work in is a different file.
  • Not a two-writer merge. Your rows are yours and theirs are theirs. The replica mirrors in both directions and merges in neither.
  • Not a hosted server. There is no Slate server in front of the database. Postgres Row Level Security is the entire access-control boundary, and no business logic runs in the cloud.

The moving parts

PieceWhat it is
AccountThe billing/organisation tier. A company, or one person — a solo user gets a personal account with one member, the way GitHub treats users and orgs identically.
WorkspaceOne store with one audience. Private (Personal) or a named team. You can belong to many, across accounts.
ReplicaThe local SQLite file for a shared workspace. Where you read and write; the cloud rows follow.
AuthorWho wrote a row. An attribute, shown as an avatar — not a grouping, because the tree is genuinely shared.

A project you created can hold a repo page a teammate created. parent_id lives on the child, so creating a child is not writing the parent — which is how one shared tree composes with one writer per page.

Membership in a workspace is independent of membership in the account that owns it: a contractor joins one workspace, a founder administers all of them. See Workspaces & Invites.

Using it

Sign in. Settings → Account, with GitHub or Google. Slate opens your system browser and the exchange finishes inside the app's own local server, so no code is pasted and no password touches Slate. Your first sign-in provisions an account.

Make or join a workspace. Settings → Workspaces is where workspaces are run: create one, leave one, manage its people, rename it, recolour it, delete it. A workspace you belong to but have not materialised on this machine — accepted on another computer, or left here and wanted back — is offered with Add here rather than provisioned silently.

Switch into it. The switcher in the top bar. Everything below it re-roots.

Work. Normally. That is the whole feature: pages, the block editor, projects, repos, Memory, Activity, search, and the AI in the Console all read and write the workspace you are standing in.

Move something in. Right-click a page in the sidebar — or use the ⋯ in its header — and pick Move to <workspace>. The whole subtree goes, keeping its ids, its properties and its atoms, and it lands at the destination's top level because its old parent is in the store it left. This is a real move across two files, not a change of label; it is read, written, and only then deleted, so a failure leaves the pages in both places rather than in neither.

Read what others wrote. Their pages are in the same tree as yours, rendered by the same PageView, with their avatar on the row and the editor in read-only mode.

Ask your AI. Slate's MCP server offers recall_workspaces and workspace_page so Claude Code, Cursor, Codex or Gemini can answer "has anyone already solved this?". recall stays scoped to the workspace the working directory resolves to; recall_workspaces is the explicit, separate verb for reaching across every workspace you belong to — including ones you have not provisioned here.

How a shared workspace stays in step

TriggerWhen
The background loopEvery 2 minutes, plus once at startup
Sync now in Settings → WorkspacesImmediately

A timer rather than a hook on the write path, on purpose. Pages are written from several places — the UI over HTTP, an AI tool calling MCP, the session watcher's ingestion — and instrumenting each one would be three chances to miss a case, forever. A poll cannot miss a writer it has never heard of.

It is cheap because the diff is cheap: the pass asks the cloud for two columns per row, compares a hash computed over exactly the fields that get published, and sends only what changed — so editing something private, like a page property or a sibling's order, costs nothing. A workspace with nothing new costs one query and no upload.

The same comparison is what withdraws. A row the cloud holds that your replica no longer does — deleted, archived, or moved to another workspace — is tombstoned and blanked upstream, so every member's copy goes on their next pull. That is why the diff asks the cloud rather than keeping a local record of what it sent: a row deleted from SQLite leaves nothing behind to notice its own absence.

Offline is fully supported, and needs no sequencing. You are the sole writer of your rows, so a queue that drains in any order lands the same state. A shared workspace is readable and writable on a plane; the push drains when you reconnect.

What actually leaves your machine

Everything in a shared workspace is meant for its members — that is what putting it there means. What is withheld is the machine-specific and the ambient:

SentNot sent
Page title, block content, and its plain-text rendering (so the cloud can index it) — as written, see the note belowproperties — the JSON bag of typed and captured metadata, including a project's folder path
doc_type, the parent link, and your timestampsposition — the fractional sibling index. Shared workspaces order by type and title
Memory atoms anchored to a page in the workspace: the distilled sentence, its kind, and where it was learnedThe reasoning body behind an atom, and its source reference
Git activity: commits (with aggregate counts), branch created/deleted/merged/switchedfiles.touched and staged — per-file paths from a filesystem watch and from .git/index
Session records: tool, session id, one-line summaryAny transcript content. The activity payload column is not published at all
A repository's normalised git remote, so a teammate's checkout at a different path matchesactivity.repo — the absolute path on your disk
Your display name, email and avatar from the sign-in providerAnything in Personal. Anything in another workspace.

The kind list is enforced by a CHECK constraint in Postgres, not by the client. The boundary is in the database, which is the only place it cannot be forgotten.

The right-hand column withholds fields, not words. A page body and an atom's sentence are sent as written, so a filesystem path you typed into a page — or one an AI tool recorded inside a decision — goes up with the row. What is withheld is the structured place a path is held: properties, and the absolute repo on a commit. Prose is content, and content in a shared workspace is the point of the workspace.

Every shared workspace also keeps an append-only audit log in its own replica: joins, moves in and out, syncs that moved something, and withdrawals. A deletion that cannot be accounted for afterwards is not an audit trail.

Leaving, erasing, and being removed

Four different things, deliberately named apart — confusing them costs somebody either their access or their content, in whichever direction they did not mean.

ActionWhat happens
Stop sharing (Settings → Workspaces)The workspace stops publishing entirely — no push, no pull — and everything you authored is erased from the cloud. The store and all its contents stay on this machine and keep working, exactly like Personal. This is the one to reach for when the answer to "should this be shared" changes.
Leave (Settings → Workspaces)This machine's replica is deleted. Your rows upstream are untouched, so the workspace still shows them.
Erase my workEvery row you authored in that workspace is tombstoned upstream, so every member's replica drops its copy on their next pull. This is the Article 17 request.
Someone removes youRow Level Security stops answering on your next request — there is no cached grant to expire. Your replica is marked read-only rather than vanishing: content you could read yesterday stays readable and exportable.
The owner deletes the workspaceIts rows are gone for everyone. Your replica is marked read-only and you are offered local deletion, rather than content disappearing without notice.
