Working in a Shared Workspace

There is no "publish this page" button, and there is no rule to draw around a subtree. The unit is the container:

this workspace is a team's, so everything in it is the team's.

That is the whole model. A page you create in a shared workspace is shared the moment it exists. A decision your AI records while you work there is the team's. A commit in a repository that workspace owns lands in its activity feed. Nothing is marked, and nothing can be quietly not marked.

The corollary matters as much: work you do not want shared goes in Personal, which never syncs. The boundary is a different file, not a predicate re-evaluated on every pass.

Getting existing work in

A project that already exists in Personal is moved, not copied. Right-click it in the sidebar — or use the ⋯ in its page header — and pick Move to <workspace>.

  • The whole subtree goes. A project takes its repos, its branches, and the plans and designs hanging off them.
  • Ids are preserved. Page ids are UUIDs, so a page already published under one keeps its cloud rows instead of arriving as a second copy.
  • Properties come too, unlike a publish. A project's folder path is what the folder→workspace routing table is projected from, and losing it would un-govern the repository.
  • Its memory comes too — the atoms anchored to the moved pages, and only those.
  • It lands at the top level, because its old parent is in the store it just left. Pointing at that parent would be a dangling reference that renders as nothing.

The move is read, then written, then deleted — in that order, because no transaction spans two SQLite files. A failure between the write and the delete leaves the pages in both stores, which is visible and re-runnable. The other order would lose them.

Moving out of a shared workspace works identically. A project shared with a team that ends is a project you keep.

Read-only, and why there is no merge

Each page in a shared workspace has exactly one writer: its author. Open a teammate's page and you get the real page — real icon, real breadcrumb, real child grid — with the editor in read-only mode and a line saying which of the two reasons applies:

ReasonWhat it means
Another authorSomebody else wrote this page. Their edits reach you; yours would not reach them.
Workspace is read-onlyThe workspace was deleted upstream, or you were removed. Everything stays readable and exportable.

This is what keeps the design affordable. Because a row's author is the only person who can have changed it, "take the remote copy" and "send the local copy" are never in competition — so there are no version columns, no 409 handling and no conflict resolution anywhere in the system.

One thing follows from it that is worth knowing: manual sibling ordering is a Personal affordance. Dragging a page above its sibling writes position on pages you may not own. Shared workspaces order by type and title instead.

Deletions have to travel

A row that simply disappeared from the cloud could not be told apart from a row you had not fetched yet, so an incremental pull would never remove anything and a deleted page would live on every teammate's disk forever. Deletions are therefore tombstones: a row that says "gone", and when.

That creates one hazard the pull handles explicitly. page.parent_id cascades on delete, so applying a teammate's deletion as a plain local DELETE would silently take your children with it — local data loss. The pull re-parents your surviving children to the workspace root before applying a foreign delete, and never relies on the cascade. The count comes back from a sync as reparented, and Sync now reports it, because it is the one outcome that changes what you see without you having done anything.

Memory is shared the same way

An atom — a decision, fact, preference or state recorded by remember or record_decision — is anchored to a page. If that page is in a shared workspace, the atom is the workspace's.

What travels is the distilled sentence, its kind, its subject, its confidence, and where it was learned. Provenance is not decoration: in a team, "which project taught us this" is what makes a claim actionable.

What does not travel:

  • The reasoning body. The published atom is the sentence, not the session it came from.
  • Superseded atoms. Supersede a decision and the old one is withdrawn on the next pass. The one thing worse than a colleague not finding your decision is finding the one you already reversed.
  • Cross-project atoms. An atom with no page — "prefers pnpm", "always run the linter first" — is a private working habit that recall unions into every project on your machine. Those live in Personal and are never moved by anything.

That last exclusion is enforced in the move itself, by a function that refuses unscoped atoms outright rather than by a filter at the call site. It exists because the first implementation asked for "the subtree's atoms" using the same call recall uses — which unions the unscoped ones in, correctly for recall and catastrophically for a move — and carried 33 private facts into a shared workspace on its first real run.

Finding a teammate's memory from your own checkout

You and a colleague clone the same repository to different folders. Their atoms are anchored to their project and repo pages, and those pages record an absolute path — /Users/ana/… — which does not exist on your machine and never will.

So Slate identifies a repository by its git remote, normalized to host/owner/repo, not by where it happens to sit on disk. When you run recall in your checkout and no stored path matches, it asks which repository you are in and finds the page recording that same remote. Their memory resolves against your directory layout.

Some deliberate limits:

  • The remote is the identity. A checkout with no fetchable remote gets nothing — a repository nobody can fetch from is not one two people can be talking about.
  • Never by name. Two unrelated repositories called site do not pool one another's memory; only an exact remote match counts.
  • However you cloned it. git@github.com:Acme/Site.git and https://github.com/acme/site are one repository, because the key is lower-cased and credentials are stripped before it is stored.

Before this, every atom in a shared workspace arrived on a teammate's disk and none of it was reachable. Measured on a real replica: 760 atoms, not one of them scoped in a way the second member could resolve — and recall said nothing, it simply returned empty. The same argument had already been made and answered for the activity feed; atom scope had not caught up.

Telling at a glance which workspace you are in

The switcher in the top bar names it, always, with its colour beside it and a padlock if it is read-only. Colours are yours: stored on this machine, not on the shared row, so recolouring changes what you see and nothing about what anyone else sees.

What a change costs

A page's cloud identity is a hash over exactly the fields that get published — id, parent, title, doc_type, and content. Editing something that is not published, like a page property or the order of its siblings, does not manufacture a change and does not cost a push.

Republishing updates in place. A row is keyed by (workspace, page), so an edit overwrites its own row rather than piling up copies.
