Working in a Shared Workspace

There is no "publish this page" button and no rule to draw around a subtree. The unit is the container: this workspace is a team's, so everything in it is the team's.

A page you create there is shared the moment it exists. A decision your AI records while you work there is the team's. A commit in a repository that workspace owns lands in its activity feed. Nothing is marked, and nothing can be quietly not marked.

Work you do not want shared goes in a workspace you have not shared. The boundary is a different file, not a predicate re-evaluated on every pass.

Getting existing work in

A project that already exists elsewhere is moved, not copied. Right-click it in the sidebar — or use the ⋯ in its page header — and pick Move to <workspace>.

  • The whole subtree goes. A project takes its repos, its branches, and the plans and designs hanging off them.
  • Ids are preserved, so a page already published under one keeps its cloud rows instead of arriving as a second copy.
  • Properties come too, unlike a publish. A project's folder path is what the folder→workspace routing is projected from, and losing it would un-govern the repository.
  • Its memory comes too — the atoms anchored to the moved pages, and only those. An atom anchored to no page is a private working habit, and the move refuses to carry one.
  • It lands at the top level, because its old parent is in the store it just left.
  • It refuses what is not yours to move. A subtree holding anyone else's pages, memory or activity is refused, and so is a move where either workspace is read-only for you. Nothing is copied or deleted when it refuses.

The move is read, then written, then deleted — in that order, because no transaction spans two SQLite files. A failure between the write and the delete leaves the pages in both stores, which is visible and re-runnable. The other order would lose them.

Moving out works identically. A project shared with a team that ends is a project you keep.

Read-only, and why there is no merge

Each page has exactly one writer: its author. Open a teammate's page and you get the real page — real icon, real breadcrumb, real child grid — with the editor read-only and a line saying which of two reasons applies:

ReasonWhat it means
Another authorA teammate wrote this page, and the line names them. Their edits reach you; yours would not reach them.
Workspace is read-onlyThe workspace was deleted upstream, or you were removed. Everything stays readable and exportable.

Who wrote what

In a shared workspace, every page and every memory is signed by the person who wrote it.

  • In the sidebar, a teammate's page carries their picture at the end of its row. Your own pages carry nothing, so the mark always means "somebody else wrote this".
  • Under a page's title, a line says who wrote it — "Written by you" or "Written by Sam".
  • In Memory, a teammate's decision or fact shows their name where your own shows "you".

Personal shows none of this: everything in it is yours.

Names come from each member's profile. Slate keeps a copy of the member list on your machine, refreshed when the app starts and whenever you open the workspace's members in Settings, so pages stay signed while you are offline. A member Slate has not been able to look up yet shows as "A teammate".

This is what keeps the design affordable. Because a row's author is the only person who can have changed it, "take the remote copy" and "send the local copy" are never in competition — so there are no version columns, no 409 handling and no conflict resolution anywhere in the system.

One consequence is worth knowing: your manual sibling order is not published. Dragging a page above its sibling writes a position that only means something beside the pages you own, so on a teammate's machine your pages arrive in the order they pulled, not the order you left them in.

Deletions have to travel

A row that simply disappeared from the cloud could not be told apart from a row you had not fetched yet, so an incremental pull would never remove anything. Deletions are therefore tombstones: a row that says "gone", and when.

That creates one hazard the pull handles explicitly. page.parent_id cascades on delete, so applying a teammate's deletion as a plain local DELETE would silently take your children with it. The pull re-parents your surviving children to the workspace root before applying a foreign delete, and never relies on the cascade. Sync now reports that count as reparented, because it is the one outcome that changes what you see without you having done anything.

Memory is shared the same way

An atom — a decision, fact, preference or state recorded by remember or record_decision — is anchored to a page. If that page is in a shared workspace, the atom is the workspace's.

What travels is the sentence, its kind, its subject, its confidence, and the page it was learned on. Provenance is not decoration: in a team, "which project taught us this" is what makes a claim actionable.

What does not travel is the reasoning body behind the atom and its source reference — the published atom is the sentence, not the session it came from. Supersede a decision and the old one is withdrawn on the next pass, so a colleague cannot find the version you already reversed.

Finding a teammate's memory from your own checkout

You and a colleague clone the same repository to different folders. Their atoms are anchored to their project and repo pages, and those pages record an absolute path that does not exist on your machine.

So Slate identifies a repository by its git remote, normalized to host/owner/repo. When you run recall in your checkout and no stored path matches, it asks which repository you are in and finds the page recording that same remote. Their memory resolves against your directory layout.

  • The remote is the identity. A checkout with no fetchable remote gets nothing.
  • Never by name. Two unrelated repositories called site do not pool one another's memory; only an exact remote match counts.
  • However you cloned it. git@github.com:Acme/Site.git and https://github.com/acme/site are one repository — the key is lower-cased and credentials are stripped before it is stored.
