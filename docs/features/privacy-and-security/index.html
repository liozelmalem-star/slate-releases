Features

Privacy & Security

Slate is a local-first app. Your workspace — every page, session, fact, and decision — lives in one SQLite file on your machine. The app reads and writes it locally. You never have to create an account, and no backend sees your content unless you deliberately share it.

The rule is simple: nothing leaves the machine without an explicit action you take.

The five exceptions

Being honest means naming the cases where bytes do cross the boundary. There are five, and only five.

ExceptionWhat leavesWhy
Brain CLIsYour prompt and context, sent by the CLI to its modelA brain drives a locally installed CLI (Claude Code, Gemini, OpenCode, cursor-agent or Codex) that makes its own model calls under its own auth — you already authed that tool
Workspace sharingEverything in a workspace you created or joined for sharing. Nothing at all from PersonalSharing knowledge with colleagues. You choose the container, not a rule; inert until you sign in
Update checkNothing of yours — a plain request for the release manifest, which reveals your IP and that you run SlateA few seconds after the window opens, then periodically while it stays open — this app's common case is a window left open for days, which once-per-launch could not serve. Also whenever you press "Check for updates" in Settings → About. Switch it off entirely in Connect → Automations; the manual check still works. If an update exists you get a dismissible notice
License activationA one-time activation checkVerifying a purchased license (roadmap — see Licensing & Updates)
TelemetryAnonymous usage signals, opt-inNever any page, session, or file content

The key detail on the first: Slate does not broker tokens on a backend and has no web-search proxy. When a brain calls a model, that traffic belongs to the CLI you installed and authenticated, not to a Slate service. Slate proxies the call through Rust only to keep credentials out of the webview and dodge CORS — the destination and the auth are the CLI's.

The update check and workspace sync each have a switch in Connect → Automations, alongside the local-only background work that never leaves your machine at all. Telemetry is opt-in and lives in Settings → About, with the other things about the app itself. A brain CLI only runs when you ask it to, so there is nothing to switch off.

Slate ships no machine-learning model, and downloads none. Recall ranks your memory by keyword matching computed on your device — there is no embedding model, no inference runtime, and no model host to contact. Until 2026-07-28 an optional setting did fetch a ~87 MB model on first use; it never uploaded anything, but it is gone, and with it the last reason for Slate itself to make a network request you did not ask for.

Workspace sharing, precisely

The second exception is the only one where your own content is stored elsewhere, so it's worth being exact about its edges.

It does nothing until you sign in. No cloud request is made, and the background sync costs one local query and zero network calls while you have joined no shared workspace.

Sharing is a property of the container, and every workspace works the same way. A shared workspace is a different SQLite file, so the boundary is structural rather than a predicate re-evaluated on every sync: an unshared store has no cloud counterpart at all, and nothing in it can leak because there is nothing up there to leak from.

Your Personal workspace starts unshared and is the one that fills without being asked — Slate captures your AI sessions from disk, and repos with no project page and cross-project notes land there by default. It can be shared, like any other, and because of what collects there the switch counts what it would publish and says so before you agree. The failure mode this design removes is the invisible one; a number you have to read is the opposite of invisible.

That is the sharpest change in this design, and it is a privacy improvement rather than a convenience one. The old question was did my rule quietly include something? — invisible, and answerable only by reading a predicate. The new one is am I in the right workspace? — which is on screen in the top bar, permanently, and answers itself at a glance.

Inside a shared workspace, assume everything is shared. That is what putting it there means: pages, memory atoms, git activity and session records all belong to that workspace's members. What is withheld is the machine-specific and the ambient — the properties bag that holds a project's folder path, the absolute path recorded against a commit (the normalised git remote goes instead), per-file path lists from a filesystem watch or .git/index, transcript content, the reasoning body behind a memory atom, and your local sibling ordering. The full list is in Workspaces, and the activity kinds are enforced by a CHECK constraint in Postgres rather than by the client.

Text is not filtered. Withholding a path means withholding the field that holds one. A page body and a memory atom's sentence go up as written, so a path you typed into a page — or one an AI tool recorded inside a decision — travels with the row. Slate does not read or redact prose, and a design that tried to would be guessing at what your writing means.

Nobody can write your pages. Each page has exactly one author, enforced in the database and at the local write paths, so a teammate can read but never modify. Nothing anyone else writes ever reaches a page of yours.

Postgres decides who sees what. The app talks straight to the database, and Row Level Security policies are the entire access-control boundary — a non-member gets an empty result, not someone else's workspace. Those policies have an isolation test suite that must pass before anything built on them ships.

Sharing can be switched off. Settings → Workspaces → Stop sharing stops a workspace publishing at all and erases what it already published, while leaving the store and its contents untouched on your machine. It is the reverse of creating a shared workspace, and it is the answer when the decision changes rather than the content.

Getting something out is a move, and erasing it is a separate act. Moving a page back to Personal takes it out of the workspace and off the server on the next pass. Erase my work tombstones every row you authored there, so every member's copy is dropped on their next sync — that is the Article 17 request, and it is deliberately not the same button as leaving.

Withdrawal removes the page from the cloud, not from anyone's memory of it. Share as you would publish anything: reversible, but not retroactive.

Locality is the architecture

Most cloud assistants face a tradeoff: more context means more of your raw data uploaded to a server. Slate doesn't have that tradeoff, because no server holds your workspace — only the pages you hand it.

WhatWhere
Your Personal workspaceA local SQLite file that never syncs — see Your Data & Export
Each shared workspaceIts own local SQLite file, on the same schema, whose rows are mirrored to and from Postgres
Pages, sessions, facts, decisionsInside that same file
Which workspaces this machine hasA small local registry — names, colours and your role, so the switcher reads while offline
ExportA one-click copy of the SQLite file
Brain credentialsNothing to store — the brain CLIs hold their own auth
Cloud sessionA 0600 file in the app-data root, never inside any database, so an export cannot contain a live token
Auto-capture tokenA 0600 file beside the database — the credential for the local capture port (below)

Because no workspace of yours sits on a backend, locality is the privacy story. The only thing a model ever sees is what you send it in a turn, and the only thing the cloud holds is what is in a workspace you created or joined for sharing.

Security details

No API keys to store. Slate's model providers are brain CLIs (Claude Code, Gemini, OpenCode, cursor-agent or Codex) that you've already authenticated — the CLI holds its own auth. There is no API key to paste into Slate. Your workspace SQLite file holds only your pages, sessions, facts, and decisions.

Nothing is written into another tool's config until you connect one. For Gemini, Cursor and OpenCode, registering Slate as an MCP server means editing a file that belongs to that tool — and installing Slate's recall hooks beside it. For Claude Code and Codex, Slate runs that tool's own plugin install instead, and once the plugin supplies the server Slate removes its own MCP entry from the tool's config, so its tools are not listed twice. Slate will not do any of this on its own. Connect one tool yourself, from onboarding's Tools step or Connect → AI tools, and from then on Slate keeps tools you install later registered too, without asking again. Until you do, launch auto-connect stays off and no file outside Slate's own data directory is touched. Turning that same switch back off removes what Slate put there, and is remembered across restarts.

Every write copies the original aside first, and the copies are bounded. Slate keeps the five newest copies of each file it has rewritten and sweeps the rest at launch. It only ever removes its own — a <file>.bak or <file>.bak-20260101-120000 you made yourself is left alone, because Slate cannot tell one of those from one of its own.

Sign-in never touches the renderer. Cloud sign-in opens your system browser and returns to a loopback address that Slate's own local server is listening on; the server performs the code exchange. No authorization code, token, or password passes through the app's UI, and the session lands in a 0600 file outside the database.

The workspace port only answers the app. Slate's own server — the one that owns your pages, facts and settings — listens on a loopback port that the app talks to over HTTP. Loopback is not a boundary on its own: a web page you visit can be made to POST to a localhost port, and the browser's CORS rules only stop it reading the reply, not sending the request. So the server refuses any request whose Origin is not Slate's own webview, and any request addressed to a hostname that isn't a loopback address — the second is what defeats DNS rebinding, where an attacker points their own domain at 127.0.0.1. A request with no Origin at all is not a browser, so there is nothing for the Origin rule to judge — it must instead present a token Slate mints each run into a 0600 file (slate-server-token) beside the database, which is exactly the protection the database file already has. The one exemption is the sign-in redirect landing, a top-level navigation that can carry no header at all.

The auto-capture port is authenticated. When auto-capture is on, Slate listens on a loopback port so git hooks and shell scripts can push a note straight into Memory. Two things guard it. A web page you visit can be made to POST to a known localhost port, so the server rejects any request that doesn't look like local tooling — that's what stops a browser. And anything that writes must present a token Slate generates each run and stores in a 0600 file beside the database — that's what stops another process on your machine, since only your own account can read it.

That second half matters because what lands here is not inert: a captured note is ranked by recall and can be fed into later AI sessions. If you drive the port yourself, send the token as an x-slate-token header; read it from the slate-server-token file beside the workspace. There is one port and one token on the machine — capture used to run its own second pair, and now does not.

Encryption at rest: Slate encrypts nothing. Every store — workspace.db, each shared workspace file, machine.db, and their WAL sidecars — is written unencrypted. On-disk confidentiality rests entirely on your operating system's full-disk encryption (FileVault, BitLocker, LUKS) and on your user account's file permissions. Slate ships no SQLCipher build, holds no key, and has no passphrase prompt, so anyone with the decrypted volume and your user's read access can read every workspace on the machine. If you are evaluating Slate for content that requires application-level encryption at rest, it does not meet that requirement today. The one file treated differently is the cloud session, which is not encrypted either but is mode 0600 and kept outside every database, so an export cannot carry a live refresh token.

Webview CSP. The Tauri webview runs under an enforced Content Security Policy, so the renderer can't reach arbitrary network origins.

Validated tool arguments. Every MCP tool argument is validated against a strict Zod schema before it runs. Malformed or unexpected input is rejected, not coerced.

Transactional writes. Every change to your workspace is a SQLite transaction. The database runs in WAL mode, which allows concurrent reads while the server writes.

Backups before migrations, and a way back. Slate copies your database aside before applying any schema migration and keeps the last three, so an upgrade can't leave you without a fallback. Settings → Workspaces → Manage → Storage → Restore a backup lists them and puts one back: it applies at the next launch, when nothing has the file open, and the workspace it replaces is kept too — so restoring the wrong one is recoverable as well.

Reporting a vulnerability

Email lioz.elmalem@gmail.com with a description, steps to reproduce, and what an attacker could do with it. You'll get a reply within 72 hours, and a fix inside 7 days for anything critical. Good-faith research under the safe-harbour terms is authorised: don't reach beyond what demonstrates the issue, don't degrade the app for anyone else, and give a reasonable window before disclosure.

A cross-account read through the cloud layer is the highest-severity report this project can receive — the Row Level Security policies in Postgres are that layer's entire access-control boundary. Out of scope: social engineering, upstream dependency issues (report those upstream), vulnerabilities in the brain CLIs themselves, and theoretical issues with no realistic attack path.

The full policy, including the complete attack surface, is SECURITY.md in the source repository.
