Features

Privacy & Security

Slate is a local-first app. Your workspace — every page, session, memory, and decision — lives in SQLite files on your machine: workspace.db for Personal, one more file for each shared workspace, and machine.db for what describes this computer. The app reads and writes it locally. You never have to create an account, and no backend sees your content unless you deliberately share it.

The rule is simple: nothing leaves the machine without an explicit action you take.

The four exceptions

Being honest means naming the cases where bytes do cross the boundary. There are four where your content or your habits can leave, and the connections you set up yourself, described after the table.

The key detail on the first: Slate does not broker tokens on a backend and has no web-search proxy. When an AI tool calls a model, that traffic belongs to the CLI you installed and authenticated, not to a Slate service. Slate starts the CLI as a child process from its Rust layer, so credentials never reach the webview — the destination and the auth are the CLI's.

The update check and workspace sync each have a switch in Connect → Automations, alongside the local-only background work that never leaves your machine at all. Telemetry is opt-in and lives in Settings → About, with the other things about the app itself. Its card says which of the two switches (usage counts and crash reports) is on right now. An AI tool CLI only runs when you ask it to, so there is nothing to switch off.

Connections you set up yourself. Tasks reads your integrations, and Slate makes some of those requests itself. The first two start when you connect the tool, and Disconnect stops them. For an app you connected with a pasted token (Bitbucket, Gitea, Forgejo, Gerrit, YouTrack, Zulip, Rocket.Chat), Slate sends read requests with that token to the address you gave it, and follows no link that leaves that address. For a tool gateway at a web address, and for an app you connected from Slate, it signs in with the token that server issued to Slate and sends it only to that server. GitHub is read through your own gh sign-in. When Connect lists the MCP servers your AI tools already have, a toolkit entry among them is asked for its list of tools at its own address, with the key that tool's config already holds. What these requests carry is what the other server needs to answer. None of them sends a page, a session or a memory of yours. An app you connected from Slate can also be read by your own AI tools, through Slate: when one asks with read_connected, Slate makes that read with its sign-in and hands the answer to that AI tool, in the workspace the session's folder belongs to. The sign-in itself never leaves Slate, and nothing is written.

A cloud session is the same exception, made larger by you. When you press Start in cloud, Claude Code clones your project's GitHub remote, or uploads the project's code when there is none, to Anthropic's computer; Codex runs the task in the environment you set up at chatgpt.com, on its GitHub copy of the code. Each does so under the sign-in you gave it. Slate itself sends nothing, holds no vendor key and calls no vendor service; it runs the CLI and keeps a record of the task in machine.db — what you asked, the messages you sent and where the task came from.

A session you open On my phone is the same exception again. When you turn on On my phone, Claude Code connects the session to claude.ai so the Claude app can reach it, and Anthropic keeps that conversation. The session still runs on this computer. Slate only types /remote-control into the session's terminal; it sends nothing itself.

Telemetry's id and consent are per machine, like the settings around them in that panel — they live in machine.db, never inside a workspace file, so deleting a workspace forever does not touch them. Reset them from the same panel: "New id" replaces the id, and turning both switches off withdraws consent.

Slate ships no machine-learning model, and downloads none. Recall ranks your memory by keyword matching computed on your device — there is no embedding model, no inference runtime, and no model host to contact. Until 2026-07-28 an optional setting did fetch a ~87 MB model on first use; it never uploaded anything, but it is gone, and with it the last reason for Slate itself to make a network request you did not ask for.

Workspace sharing, precisely

The second exception is the only one where your own content is stored elsewhere, so it's worth being exact about its edges.

It does nothing until you sign in. No cloud request is made, and the background sync costs one local query and zero network calls while no workspace is shared. The sync does not renew your sign-in then either.

Sharing is a property of the container, and every workspace works the same way. A shared workspace is a different SQLite file, so the boundary is structural rather than a predicate re-evaluated on every sync: a store you have never shared has no cloud counterpart at all, and nothing in it can leak because there is nothing up there to leak from.

Your Personal workspace starts unshared and is the one that fills without being asked — Slate captures your AI sessions from disk, and git repositories with no project page and cross-project notes land there by default. It can be shared, like any other, and because of what collects there the switch counts what it would publish and says so before you agree. The failure mode this design removes is the invisible one; a number you have to read is the opposite of invisible.

That is the sharpest change in this design, and it is a privacy improvement rather than a convenience one. The old question was did my rule quietly include something? — invisible, and answerable only by reading a predicate. The new one is am I in the right workspace? — which is on screen at the top of the rail, permanently, and answers itself at a glance.

A live artifact reads your workspace and has no way to send it out except one. An artifact a tool publishes live asks the Slate window for pages, memories and sessions of its own project, read-only. It is served with a policy that blocks every connection, image, form and window to any address, and WebRTC is taken away. The one way left is a script from cdnjs, jsDelivr or unpkg: those three hosts can see the address the page asks for, and the page chooses that address. A teammate's live artifact never reads your store. See Artifacts.

An app reads its project and cannot send anything out; it writes only what you allowed. An app is built from files and runs with no origin and no network: no requests, images, fonts, scripts from anywhere, WebRTC, resource hints or frames. It reads its own project. A write needs a permission you granted once, and a memory or page write shows you its words each time before it is saved. A memory an app saves is held until you release it, and is never shared with a team. Whatever an app wrote, a memory you released or a page, reaches an AI tool quoted as data and not as an instruction. Its own data stays on this computer. An app you allow to read your GitHub (github.read) still sends nothing: Slate reads GitHub for it, read only, with your own gh sign-in, from four fixed kinds of address, at most 12 times a minute, and the app never sees the token. An app you allow to read through one of your MCP tools still sends nothing itself: Slate calls the tool for it, only a tool you allowed for that app and ticked as read-only, pinned to the tool's definition so a changed tool asks again, with the app's arguments checked against the tool's own schema, from the servers of the app's own workspace only, at most 20 requests a minute per server; the app never sees an address, a token or the server's own error words. An app you allow to act on GitHub (github.act) still chooses neither the words nor the target: it can only ask to approve, request changes on, comment on or label a pull request in your own lists, with words you wrote or type yourself. Slate shows you a card built from what it read, naming the account that will act, every time, and writes through its own fixed list of four GitHub addresses. At most 5 actions an hour per app and 20 for all apps together, each one written down. A teammate's app never reads your store. Every release checks the no-network claim in the built app: a hostile app tries every way out, and listeners on the release Mac must hear nothing. See Apps.

Inside a shared workspace, assume everything is shared. That is what putting it there means: pages, memory atoms, git activity, a record that a session happened (its branch and time) and artifacts all belong to that workspace's members. What is withheld is the machine-specific and the ambient — the properties bag that holds a project's folder path, the absolute path recorded against a commit (the normalised git remote goes instead), per-file path lists from a filesystem watch or .git/index, transcript content, the reasoning body behind a memory atom, and your local sibling ordering. Four more things are never sent: the page of a captured AI session, a memory that belongs to no page (a global one), a memory you hid from sessions, and a memory an app saved. The full list is in Workspaces, and the activity kinds are enforced by a CHECK constraint in Postgres rather than by the client.

Text is not filtered. Withholding a path means withholding the field that holds one. A page body and a memory atom's sentence go up as written, so a path you typed into a page — or one an AI tool recorded inside a decision — travels with the row. Slate does not read or redact prose, and a design that tried to would be guessing at what your writing means. The one exception is secrets: Slate replaces keys, tokens and passwords it recognises with [secret] in every memory before it is stored, and in the pages an AI tool writes. A page you type yourself is not checked.

Nobody can write your pages. Each page has exactly one author, enforced in the database and at the local write paths, so a teammate can read but never modify. Nothing anyone else writes ever reaches a page of yours.

Postgres decides who sees what. The app talks straight to the database, and Row Level Security policies are the entire access-control boundary — a non-member gets an empty result, not someone else's workspace. Those policies have an isolation test suite that must pass before anything built on them ships.

Your machine keeps a copy of who your teammates are. To sign a teammate's pages while you are offline, Slate stores each shared workspace's member list in machine.db: each member's display name, email address and picture link, and nothing else. It only ever holds people you already share a workspace with. Leaving a workspace removes that workspace's list, and the list is never inside a workspace file, so exporting a workspace does not carry it.

Sharing can be switched off. Settings → Workspaces, then the workspace's Sharing switch, asks first, then stops a workspace publishing at all and withdraws what it already published, while leaving the store and its contents untouched on your machine. Withdrawing blanks the rows in the cloud, and every member's copy drops them on their next sync. Switching sharing on again publishes them again. It is the answer when the decision changes rather than the content.

Getting something out is a move, and erasing it is a separate act. Moving a page back to Personal takes it out of the workspace and off the server on the next pass. Erase my work tombstones every row you authored there (blanked and final), so every member's copy is dropped on their next sync and sharing again does not bring it back — that is the Article 17 request, and it is deliberately not the same button as leaving.

Withdrawal removes the page from the cloud, not from anyone's memory of it. Share as you would publish anything: reversible, but not retroactive.

Locality is the architecture

Most cloud assistants face a tradeoff: more context means more of your raw data uploaded to a server. Slate doesn't have that tradeoff, because no server holds your workspace — only the pages you hand it.

Because no workspace of yours sits on a backend, locality is the privacy story. The only thing a model ever sees is what you send it in a turn, and the only thing the cloud holds is what is in a workspace you created or joined for sharing.

Security details

No API keys to store. Slate's model providers are AI tool CLIs (Claude Code, Gemini, OpenCode, cursor-agent or Codex) that you've already authenticated — the CLI holds its own auth. There is no API key to paste into Slate. Your workspace SQLite file holds only your pages, sessions, memories, and decisions.

Nothing is written into another tool's config until you connect one. For Gemini, Cursor and OpenCode, registering Slate as an MCP server means editing a file that belongs to that tool — and installing Slate's recall hooks beside it. For Claude Code and Codex, Slate runs that tool's own plugin install instead, and once the plugin supplies the server Slate removes its own MCP entry from the tool's config, so its tools are not listed twice. Slate will not do any of this on its own. Connect one tool yourself, from setup's Connect step or Connect → AI tools, and from then on Slate keeps tools you install later registered too, without asking again. Launch auto-connect never reaches Claude Desktop: it gets Slate only when you turn Claude Code on, and keeps it when you turn Claude Code off. Until you do, launch auto-connect stays off and no file outside Slate's own data directory is touched. Turning that same switch back off removes what Slate put there, and is remembered across restarts.

Every write copies the original aside first, and the copies are bounded. Slate keeps the five newest copies of each file it has rewritten and sweeps the rest at launch. It only ever removes its own — a <file>.bak or <file>.bak-20260101-120000 you made yourself is left alone, because Slate cannot tell one of those from one of its own.

Sign-in never touches the renderer. Cloud sign-in opens your system browser and returns to a loopback address that Slate's own local server is listening on; the server performs the code exchange. No authorization code, token, or password passes through the app's UI, and the session lands in a 0600 file outside the database.

The workspace port only answers the app. Slate's own server — the one that owns your pages, memories and settings — listens on a loopback port that the app talks to over HTTP. Loopback is not a boundary on its own: a web page you visit can be made to POST to a localhost port, and the browser's CORS rules only stop it reading the reply, not sending the request. So the server refuses any request whose Origin is not Slate's own webview, and any request addressed to a hostname that isn't a loopback address — the second is what defeats DNS rebinding, where an attacker points their own domain at 127.0.0.1. An Origin header only proves something about a browser — any other program can send whatever header it likes — so it is never accepted as proof on its own. Every request must also present a token Slate mints each run into a 0600 file (slate-server-token) beside the database, which is exactly the protection the database file already has. The app's own window gets the token from Slate itself; a script or another process on the machine can only get it by reading that file, which only your user account can do. Two narrow cases carry no header: a browser's CORS preflight from the app's own window, which runs nothing, and the live event stream, which cannot set headers and carries the same token in its address instead. The two exemptions are the sign-in redirect landings — the cloud account's and a work gateway's — top-level navigations that can carry no header at all. Each acts only on a sign-in Slate itself started, and each started sign-in can be completed once.

The auto-capture port is authenticated. When auto-capture is on, Slate listens on a loopback port so git hooks and shell scripts can push a note straight into Memory. Two things guard it. A web page you visit can be made to POST to a known localhost port, so the server rejects any request that doesn't look like local tooling — that's what stops a browser. And anything that writes must present a token Slate generates each run and stores in a 0600 file beside the database — that's what stops another process on your machine, since only your own account can read it.

That second half matters because what lands here is not inert: a captured note is ranked by recall and can be fed into later AI sessions. If you drive the port yourself, send the token as an x-slate-token header; read it from the slate-server-token file beside the workspace. There is one port and one token on the machine — capture used to run its own second pair, and now does not.

Encryption at rest: Slate encrypts nothing. Every store — workspace.db, each shared workspace file, machine.db, and their WAL sidecars — is written unencrypted. On-disk confidentiality rests entirely on your operating system's full-disk encryption (FileVault, BitLocker, LUKS) and on your user account's file permissions. Slate ships no SQLCipher build, holds no key, and has no passphrase prompt, so anyone with the decrypted volume and your user's read access can read every workspace on the machine. If you are evaluating Slate for content that requires application-level encryption at rest, it does not meet that requirement today. The files treated differently are the cloud session and the work gateway sign-in, which are not encrypted either but are mode 0600 and kept outside every database, so an export cannot carry a live token.

Webview CSP. The Tauri webview runs under an enforced Content Security Policy, so the renderer can't reach arbitrary network origins.

Validated tool arguments. Every MCP tool argument is validated against a Zod schema before the tool runs. An argument of the wrong type, or a missing one, is rejected and nothing is coerced. An argument the tool does not declare is dropped, not rejected.

Transactional writes. Every change to your workspace is a SQLite transaction. The database runs in WAL mode, which allows concurrent reads while the server writes.

Backups before migrations, and a way back. Slate copies your database aside before applying any schema migration and keeps the last three, so an upgrade can't leave you without a fallback. Leaving or deleting a workspace forever also keeps a copy of it first. Settings → Workspaces → (the workspace) → Storage → Restore a backup lists them and puts one back: it applies at the next launch, and the workspace it replaces is kept too — so restoring the wrong one is recoverable as well. If an AI tool connected to Slate still has the workspace open at that point, the restore is refused rather than risked, and the panel tells you to quit those tools and try again.

Reporting a vulnerability

Email lioz.elmalem@gmail.com with a description, steps to reproduce, and what an attacker could do with it. You'll get a reply within 72 hours, and a fix inside 7 days for anything critical. Good-faith research under the safe-harbour terms is authorised: don't reach beyond what demonstrates the issue, don't degrade the app for anyone else, and give a reasonable window before disclosure.

A cross-account read through the cloud layer is the highest-severity report this project can receive — the Row Level Security policies in Postgres are that layer's entire access-control boundary. Out of scope: social engineering, upstream dependency issues (report those upstream), vulnerabilities in the AI tool CLIs themselves, and theoretical issues with no realistic attack path.

The full policy, including the complete attack surface, is .github/SECURITY.md in the source code.
