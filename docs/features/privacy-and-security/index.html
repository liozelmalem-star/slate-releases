Features

Privacy & Security

Your workspace lives in SQLite files on your machine: workspace.db for Personal, one file for each shared workspace, and machine.db for what describes this computer. You sign in once at first launch, with Google or GitHub, through Slate's cloud account. The account holds who you are and your plan, not your work. After that Slate runs offline. Nothing of your work leaves the machine without an action you take.

The agent exception. Slate brokers no tokens and runs no web-search proxy. Its Rust layer starts the CLI as a child process, so credentials never reach the webview. The model traffic belongs to the CLI.

The install id is 16 random bytes made once on this computer and kept in the file install-id in Slate's data folder. Nothing about you or your machine goes into it, and it is not the telemetry id. It places your copy in a stable group when a release goes out in steps. Before an update installs, Slate asks whether that version was stopped, and sends only the version. A newer version, or on a Mac a small patch to it, downloads from GitHub Releases. The update service keeps no table of ids. Its host keeps request logs for a short time. Remove install-id and Slate makes a new one at the next start. With Automatic updates on, an update downloads in the background and installs when you next quit.

Telemetry's id and consent are per machine. They live in machine.db, so removing a workspace does not touch them. In the same panel, "New id" replaces the id, and turning both switches off withdraws consent.

Connections you set up yourself. Tasks reads your integrations, and Slate makes some of those requests itself. They start when you connect, and Disconnect stops them.

  • An app connected with a pasted token (Bitbucket, Gitea, Forgejo, Gerrit, YouTrack, Zulip, Rocket.Chat): read requests with that token to the address you gave, and no link that leaves that address.
  • A tool gateway at a web address, or an app connected from Slate: Slate signs in with the token that server issued to Slate, and sends it only to that server.
  • GitHub: read through your own gh sign-in, after you press Connect on its card.
  • MCP servers your agents already have: a toolkit entry is asked for its list of tools at its own address, with the key that tool's config holds.

None of these sends a doc, a session or a memory. Your agents can also read an app you connected from Slate: when one asks with read_connected, Slate makes the read with its own sign-in and hands back the answer, in the workspace of the session's folder. The sign-in never leaves Slate, and nothing is written.

A cloud session is the agent exception made larger by you. When you press Start in cloud, Claude Code clones your project's GitHub remote, or uploads the code if there is none, to Anthropic's computer. Codex runs the task in the environment you set up at chatgpt.com. Each uses the sign-in you gave it. Slate sends nothing and holds no vendor key. It keeps a record of the task in machine.db: what you asked, your messages and where the task came from.

On my phone is the same again. On my phone makes Claude Code connect the session to claude.ai, and Anthropic keeps that conversation. The session still runs here. Slate only types /remote-control into its terminal.

No model is shipped or downloaded. Recall ranks memory by keyword matching on your device. There is no embedding model and no model host to contact.

Reporting a problem

A report leaves only when you press Send report. Open it from Report this on an error or failure notice, Help → Report a Problem… in the Mac menu bar, ⌘K (Report a problem), or Report… in Settings → About, under Logs. The dialog lists everything that will leave:

  • what you wrote under What happened?;
  • Where you were, such as Tasks or Projects › slate · main, and, if you came from an error, its words;
  • one line with your Slate version, macOS version and chip (Slate 0.1.54 · macOS 26.6 · Apple Silicon);
  • the last 40 lines of the app log, if the box is ticked (it is by default). Show reveals them. Every file path in them becomes ~/… before it is shown, so the lines you read are the lines that leave.

A report carries no doc, conversation, file, account or install id. It goes to Slate's own Supabase project, where anyone can write and only the Slate team can read. It is sent whether or not usage counts and crash reports are on. Afterwards the About row shows the time and a short reference, such as R-7F3A.

Workspace sharing, precisely

It does nothing until you switch a workspace to shared. While none is shared, the background sync costs one local query and no network calls, and does not renew your sign-in.

Sharing belongs to the container. A shared workspace is a different SQLite file. A store you have never shared has no cloud counterpart, so nothing in it can leak.

Personal starts unshared. It also fills without being asked: Slate captures your AI sessions from disk, and git repositories with no project doc and cross-project notes land there. It can be shared like any other. Because of what collects there, the switch counts what it would publish and says so before you agree. The question to ask is "am I in the right workspace?", and the rail shows that at all times.

A live artifact reads your workspace and can send nothing out except through one route. An artifact a tool publishes live asks the Slate window for docs, memories and sessions of its own project, read-only. Its policy blocks every connection, image, form and window to any address, and WebRTC is removed. The one route left is a script from cdnjs, jsDelivr or unpkg: those hosts see the address the doc asks for, and the doc chooses it. A teammate's live artifact never reads your store. See Artifacts.

An app reads its project and writes only what you allowed. An app runs with no origin and no network: no requests, images, fonts, scripts, WebRTC, resource hints or frames. A write needs a permission you granted once. A memory or doc write shows you its words each time before it is saved. A memory an app saves is held until you release it, and is never shared with a team. Whatever an app wrote reaches an agent quoted as data, not as an instruction. An app's own data stays on this computer. A teammate's app never reads your store.

  • github.read: Slate reads GitHub for the app, read-only, with your own gh sign-in, from four fixed kinds of address, at most 12 times a minute. The app never sees the token.
  • MCP read: Slate calls a tool you allowed for that app and ticked as read-only. The tool is pinned to its definition, so a changed tool asks again. Arguments are checked against the tool's own schema. Only servers of the app's own workspace, at most 20 requests a minute per server. The app never sees an address, a token or the server's error words.
  • github.act: the app can only ask to approve, request changes on, comment on or label a pull request in your own lists, with words you wrote or type yourself. Slate shows a card naming the account that will act, every time, and writes through a fixed list of four GitHub addresses. At most 5 actions an hour per app and 20 for all apps, each written down.

Every release checks the no-network claim in the built app: a hostile app tries every way out, and listeners on the release Mac must hear nothing. See Apps.

Inside a shared workspace, assume everything is shared: docs, memories, git activity, a record that a session happened (branch and time) and artifacts. Withheld are the machine-specific and the ambient: the properties bag with a project's folder path, the absolute path recorded against a commit (the normalised git remote goes instead), per-file path lists from a filesystem watch or .git/index, transcript content, the reasoning body behind a memory, and your local sibling ordering. Four more things are never sent: the doc of a captured AI session, a memory that belongs to no doc (a global one), a memory you hid from sessions, and a memory an app saved. The full list is in Workspaces. Postgres enforces the activity kinds with a CHECK constraint.

Text is not filtered. A doc body and a memory's sentence go up as written, so a path you typed in a doc, or one an agent recorded in a decision, travels with the row. The one exception is secrets: Slate replaces keys, tokens and passwords it recognises with [secret] in every memory before it is stored, and in the docs an agent writes. A doc you type yourself is not checked.

Nobody can write your docs. Each doc has one author, enforced in the database and at the local write paths. A teammate can read it and never modify it.

Postgres decides who sees what. The app talks straight to the database. Row Level Security policies are the whole access boundary: a non-member gets an empty result. An isolation test suite for those policies must pass before anything built on them ships.

Your machine keeps who your teammates are. To sign a teammate's docs offline, Slate stores each shared workspace's member list in machine.db: display name, email address and picture link. It holds only people you already share a workspace with. Leaving a workspace removes its list. An export does not carry it.

Sharing can be switched off. In Settings → Workspaces, the workspace's Sharing switch asks first, then stops publishing and withdraws what was published. Your store stays untouched. Withdrawing blanks the cloud rows, and every member's copy drops them on the next sync. Switching sharing on again publishes them again.

Getting something out is a move. Erasing it is a separate act. Moving a doc back to Personal takes it off the server on the next pass. Erase my work tombstones every row you authored there (blanked and final). Every member's copy drops them on the next sync, and sharing again does not bring them back. That is the Article 17 request.

Withdrawal removes the doc from the cloud, not from anyone's memory of it. Share as you would publish anything: reversible, but not retroactive.

Locality is the architecture

No server holds your workspace, only the docs you hand it. The only thing a model sees is what you send it in a turn.

Security details

No API keys. Slate's model providers are agent CLIs (any of the 16 agents, from Claude Code to Auggie) you already signed in to. There is no key to paste into Slate.

Nothing is written into another tool's config until you connect one. For every tool except Claude Code and Codex, Slate edits that tool's MCP config and, where the tool takes hooks, installs its recall hooks beside it. For Claude Code and Codex, Slate runs the tool's own plugin install, and once the plugin supplies the server, Slate removes its own MCP entry so tools are not listed twice. Connect one tool yourself, from setup's Connect step or Connect → Agents. From then on Slate keeps tools you install later registered too. Launch auto-connect never reaches Claude Desktop: it gets Slate only when you turn Claude Code on, and keeps it when you turn Claude Code off. Until you connect a tool, launch auto-connect stays off and no file outside Slate's data directory is touched. Turning the switch off removes what Slate put there, and stays off across restarts.

Every write copies the original aside first. Slate keeps the five newest copies of each file it rewrote and sweeps the rest at launch. It removes only its own: a <file>.bak or <file>.bak-20260101-120000 you made yourself stays.

Sign-in never touches the renderer. Cloud sign-in opens your system browser and returns to a loopback address Slate's local server listens on. The server does the code exchange. No code, token or password passes through the UI. The session lands in a 0600 file outside the database.

The workspace port only answers the app. Slate's server listens on a loopback port. A web page you visit can POST to a localhost port, and CORS only stops it reading the reply. So the server refuses any request whose Origin is not Slate's webview, and any request to a hostname that is not loopback, which defeats DNS rebinding. An Origin header proves nothing about a non-browser program, so it is never proof alone. Every request also presents a token Slate mints each run into a 0600 file (slate-server-token) beside the database. The app's window gets it from Slate. Another process can get it only by reading that file, which only your user can do. Three cases carry no header: a CORS preflight from the app's window (it runs nothing), the live event stream (it cannot set headers, so the token is in its address), and the two sign-in redirect landings (the cloud account's and a work gateway's). Each landing acts only on a sign-in Slate started, and completes it once.

Each workspace stays in its own file, and Slate refuses to mix them. A request to the server must name its workspace. One that does not is refused, not filed into Personal. Slate's own code cannot open a workspace file without naming it. An agent's session works in the workspace of the first folder it names, and is refused another workspace's folder. Each file records which workspace it belongs to, so a misplaced file does not open as another workspace. Only Sessions shows every workspace at once. A test plants a marker in one workspace and asks every part of the server and every agent read for it from another workspace. It must never come back.

The auto-capture port is authenticated. With auto-capture on, Slate listens on a loopback port so git hooks and shell scripts can push a note into Memory. The server rejects any request that does not look like local tooling, which stops a browser. Anything that writes must present the server token, which stops another process, since only your account can read the file. This matters because a captured note is ranked by recall and can be fed into later AI sessions. To drive the port yourself, send the token as an x-slate-token header, read from the slate-server-token file beside the workspace. There is one port and one token on the machine.

Slate encrypts nothing at rest. workspace.db, each shared workspace file, machine.db and their WAL sidecars are unencrypted. Confidentiality rests on your OS's full-disk encryption (FileVault, BitLocker, LUKS) and your account's file permissions. There is no SQLCipher build, key or passphrase. Anyone with the decrypted volume and your user's read access can read every workspace. If you need application-level encryption at rest, Slate does not meet that today. The cloud session and work gateway sign-in files are also unencrypted, but are 0600 and outside every database.

Webview CSP. The Tauri webview runs under an enforced Content Security Policy, so the renderer cannot reach arbitrary network origins.

Validated tool arguments. Every MCP tool argument is checked against a Zod schema before the tool runs. A wrong type or a missing one is rejected, and nothing is coerced. An undeclared argument is dropped.

Transactional writes. Every change is a SQLite transaction. The database runs in WAL mode, so reads continue while the server writes.

Backups before migrations, and a way back. Slate copies your database aside before any schema migration and keeps the last three per store. Leaving or deleting a workspace forever also keeps a copy. Settings → Workspaces → (the workspace) → Storage → Restore a backup lists them. A restore applies at the next launch, and the workspace it replaces is kept too. If a connected agent still has the workspace open, the restore is refused and the panel asks you to quit those tools and retry.

Reporting a vulnerability

Email lioz.elmalem@gmail.com with a description, steps to reproduce and what an attacker could do. You get a reply within 72 hours, and a fix inside 7 days for anything critical. Good-faith research under the safe-harbour terms is authorised: stay within what demonstrates the issue, do not degrade the app for others, and allow a reasonable window before disclosure.

A cross-account read through the cloud layer is the highest-severity report: the Row Level Security policies are that layer's whole access boundary. Out of scope: social engineering, upstream dependency issues (report those upstream), vulnerabilities in the agent CLIs, and theoretical issues with no realistic attack path.

The full policy is .github/SECURITY.md in the source.
