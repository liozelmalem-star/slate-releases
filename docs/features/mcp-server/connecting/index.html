Slate's value as a memory layer only shows up once your AI tools are actually connected to it. Any MCP-capable tool — Claude Code, Cursor, Codex, Gemini, OpenCode — can talk to Slate's stdio MCP server and share the same long-term memory. What each of them can then do is the Tool Reference.

The easy way: Connect → AI tools

Registering Slate with a tool is per config directory, not per project, so it lives once: Connect → AI tools lists each tool, and its switch installs Slate into the account that row names — as a plugin for Claude Code and Codex, as config entries for the rest — and records that this workspace runs on it. A project can override which account it uses; nothing else needs setting per project. Because the server ships as a SEA sidecar binary, there is no Node install and no separate process to babysit — the tool launches the sidecar over stdio.

  1. Open Connect → AI tools.
  2. Pick the tool and the account, and switch Slate on for it.
  3. The tool launches the sidecar over stdio and can now call Slate's tools.

Exact per-tool config differs between Claude Code, Cursor, Codex, Gemini and OpenCode. Use Connect → AI tools as the source of truth for what to register — it is kept in sync with what Slate actually exposes.

Let Studio project the config

You do not have to wire each tool by hand. Studio can project MCP configs for you: write your setup once and Studio materializes per-tool adapters — including MCP configs — for Claude Code, Cursor, Codex, Gemini and OpenCode. See Studio.

Connecting by hand

For using Slate's server without the app driving it. The binary ships inside the app bundle and is self-contained — no Node, no separate install:

/Applications/Slate.app/Contents/MacOS/slate-mcp

Claude Code

Connecting from the app instead? Skip this. Slate installs itself into Claude Code as a plugin, and the plugin supplies the MCP server — so Slate removes a hand-added slate entry on its next launch rather than listing every tool twice.

Add to ~/.claude.json (create the file if it does not exist):

{
  "mcpServers": {
    "slate": {
      "command": "/Applications/Slate.app/Contents/MacOS/slate-mcp",
      "args": []
    }
  }
}

Restart Claude Code. You will see slate listed in /mcp. Dropping the same block into .claude/settings.json at a repo root activates it only inside that project, alongside your global config.

Cursor

Add to ~/.cursor/mcp.json (Cursor → Settings → MCP → Edit), with the same block, then reload Cursor. The Slate tools appear in the agent's tool list.

Any other MCP client

The server speaks stdio MCP (protocol 2024-11-05). Point any MCP-aware tool at the binary with no args:

command: /Applications/Slate.app/Contents/MacOS/slate-mcp
args:    []

Verify it is working

Ask your AI tool:

"Use the slate_capabilities tool to check the Slate contract, then use recall with query 'test' to check if Slate is connected."

You should get a response referencing your workspace. Empty results are fine — it means the connection worked and no matching content exists yet.

How to use it well

Connecting is only half of it. The payoff comes from the rhythm the server asks every connected model to follow, and it sends these as standing instructions:

  • Handshake when available — the model calls slate_capabilities to inspect the contract version, schema hash, tool access levels and mutation safety rules.
  • At the start of a task — the model calls recall with your working directory to load prior decisions, conventions, facts and the active branch brief before acting.
  • At the end of a task — the model MUST call remember for each durable thing the session produced, as one sharp self-contained sentence with a deliberate kind (decision | preference | state | fact). The in-session model has the full context and you already paid for the session, so it distills the memory directly rather than leaving the background pipeline to re-derive it later.
  • As it works a branch — the model keeps the mission current in the same session: log_mission_progress advances the plan, record_decision keeps a decision, create_document adds a plan/design/review the branch should carry.
  • No write probes — the model must never call mutating tools just to discover whether Slate is connected. If recall or remember is missing, it reports a capability mismatch instead.
  • Known write targets only — when a write targets an existing object, its id must come from prior Slate output (get_page, list_pages, search_pages, …) or an explicit user-provided id.
  • Branch-aware targets — append_to_page also accepts a typed target when an id is not known. Use cwd + branch for the branch page, or cwd + branch + doc_type/title for a knowledge page. Slate only writes when that resolves to exactly one resource; ambiguous targets are refused.
  • Every page write is additive — a connected tool can create a page and add to one. Renaming, reparenting, duplicating, trashing and find-and-replace are done in the app, where they can be undone. So there is nothing to dry-run and nothing to confirm: the guard is that the tool does not exist.
  • Structured errors — contract errors are JSON with error.code and error.message, e.g. ambiguous_target, target_not_found.

Follow that across tools and the memory compounds: what Claude Code learned this morning is recalled by Cursor this afternoon. It happens on its own with capable models, and you can prompt it directly too — "Remember that we decided to use X for Y."

Memory is stored in your local Slate workspace under Private → Memory. You can read, edit or delete entries in the app.

An example branch knowledge-page target:

{
  "target": {
    "kind": "knowledge_page",
    "cwd": "/path/to/repo",
    "branch": "feat/example",
    "doc_type": "plan"
  },
  "markdown": "## Progress\nImplemented the contract tests."
}

The contract

Generated from the MCP tool registry and checked by packages/mcp/test/tools/contract.test.ts, so it cannot drift from what the server actually exposes. What each tool is for is the Tool Reference.

<!-- slate-contract:start -->

ToolAccessWrite target
slate_capabilitiesread—
create_documentwrite—
search_pagesread—
list_pagesread—
get_pageread—
resolve_targetread—
create_pagewrite—
append_to_pagewriteid, target.kind:branch, target.kind:knowledge_page; ambiguity=refuse
rememberwrite—
recallread—
log_mission_progresswrite—
record_decisionwrite—
list_decisionsread—
recent_activityread—
activity_statsread—
list_projectsread—
parked_workread—
search_contentread—
get_ticket_contextread—
recall_workspacesread—
workspace_pageread—

<!-- slate-contract:end -->

recall_workspaces and workspace_page read the cloud, so they reach workspaces this machine has never materialised — a workspace you joined on another computer answers here. They need a cloud sign-in (Slate → Settings → Account) and return nothing until somebody shares something. Everything they can see is decided by Row Level Security in Postgres, so they return an empty result — never someone else's workspace — when you are not a member. Both are read-only: a shared page belongs to whoever wrote it, and only its author can change it, which is what removes merge conflicts from the design entirely.

Troubleshooting

"command not found" or "no such file" — Slate is not installed. Run bash scripts/install.sh first.

Tools appear but calls fail — the workspace database may not exist yet. Open the Slate app at least once; it creates ~/Library/Application Support/app.slate.workspace/workspace.db on first launch.

Running from source — if you are running from a cloned repo rather than the installed app, use node with packages/mcp/dist/index.js, built by yarn workspace @slate/mcp build.
