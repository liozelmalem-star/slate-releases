Features

Automations

An automation works for you without being driven: a standup at 7:00, a review of whatever you paste in, a debrief when a coding session ends, a plan for each ticket assigned to you. Every automation, and everything it writes, lives in Automations. Automations also holds what Slate itself runs on its own, under Built-in.

What an automation is

An automation is a job, a trigger and a list of steps, held to rules for what it may do. Make one with the + in the side panel's title row: From a template, Set it up yourself (the empty editor), or Describe it to AI… (an agent writes it from what you say).

Its job

The Job box says what the automation is for, in your words: "Every weekday morning, tell me where each project stands and what to focus on." Every step reads it first. With no job, steps run exactly as written.

What starts it

StartsWhen it runs
By handOnly when you press Run now. You can type something for it to start with.
On a scheduleHow often is every day, every weekday, every week or every month, at an hour and a quarter-hour minute (:00, :15, :30, :45). A weekday is Monday to Friday: a Saturday or Sunday run moves to Monday, same time. A monthly run takes a day from 1 to 28. The list shows "Weekdays · 7:30 AM".
When a session endsAfter Slate captures an AI coding session. With Scheduled automations off in Automations › Built-in, these do not start, and a session that ended meanwhile does not start them later.
When a task arrivesWhen Tasks pulls in a new item from an integration, such as a ticket assigned to you. One read hands the run up to 5 new items. If the automation is already running, new items wait and start one run after it, together. A tracker you just connected starts nothing: its first read brings in everything at once. Your own to-dos never start one. Tasks reads your integrations when you open it, and when you return to the window after more than a minute.

An automation starts on its own only while Runs on its own (under Starts in the editor) is on. A line under the schedule says when it runs next ("Next: Mon 7:30 AM") or "Off, so it will not run on its own." Any automation can be run by hand at any time.

If the computer was asleep when a scheduled run was due, the run starts once on wake. For a report only useful on time, such as a morning brief, switch on Skip a run that is more than two hours late; Automations shows "· skips late runs". Only one automation runs at a time, and a running automation is never started twice. If Slate stops mid-run, the run is marked failed with a line saying so, and a scheduled one runs again a few minutes after Slate is back.

An automation belongs to the workspace you made it in and runs while Slate is open on that workspace. It needs a project. A new automation opens in the project Automations is narrowed to and cannot be saved without one; with none picked, Runs in says Pick a project, and its list offers only groups and projects. The six seeded automations have no project yet: Run now and Turn on ask which project, save it, then go on. Turn off never asks. A scheduled run never starts for an automation with no project. An automation whose project was removed can be edited and switched off, but not on until you pick a project. Moving a group or project to another workspace takes its automations along.

Its steps

Steps run in order, and each one reads what came before:

  • @context is what the run started with: the text you typed at Run now, "A coding session just ended.", or today's date for a scheduled run. After Recent tasks, it is that step's report.
  • @prev is the previous step's answer.

A step can name its own agent, so one step runs on Claude and the next on Gemini. A step that names none uses the automation's tool, and the group or project supplies the account.

Every run writes one report: the last step's answer first, earlier steps after it under their labels.

What it follows

Follows, in the editor under Runs in, picks what every step works by:

  • Slate's own steps: the steps as written. The default.
  • A skill of its project, listed under Skills in project, the same skills Toolkit shows.
  • A subagent of its project, listed under Subagents.
  • + New skill in Toolkit… opens Toolkit's New skill form on the project, with the automation's name and purpose filled in. Create writes the skill, sets the automation to follow it, and returns you to the automation. It is offered only for a saved automation with no unsaved changes.

Every step opens the skill's or subagent's file first and follows it, so the automation's runs count as that skill's use. Slate finds the file in the project's folder at run start. If the skill has left the project, the editor says so and runs follow Slate's own steps until you pick another. Moving the automation to another project clears what it followed.

The thread

An automation opens on its Thread: every run, oldest first. Words you typed sit above the answer they started. Under each run, a line says what it used ("Used jira ×2, github · 1 call waiting for you").

The box under the thread answers the last run. Type a reply and press Send: the automation runs once more, on the same agent in the same folder, reads the last four turns and your words, and answers. Each earlier report is cut to its first 3,000 characters. It is one short run, not the automation's steps. The box is off while the automation runs or cannot run (for example, no project). Before the first run, the box is what the first run starts with, and the button says Start. Run now runs the steps with nothing typed.

A report over 1,600 characters shows its opening; Read the whole report opens it.

What it may do

An automation can use the tools its agent can reach: your MCP servers for Jira, GitHub, Slack and the rest. Setup → May do sets what it may do with them:

  • Reading goes on without asking: searching, listing, opening a ticket or pull request.
  • A call that changes something asks first: posting a message, commenting, creating an issue.
  • Merging, removing things and writing files are refused.

It can also read the apps you connected in Connect → Integrations, even without an MCP server for them: connected_tools and read_connected use Slate's sign-in. Setup shows each at the head of the Allowed row with its logo; clicking opens Connect. An app connected with a pasted token is not among them, nor one the automation's Deny covers whole (mcp__linear__*). The report names the app (linear · list_issues), and the lists below treat that read as a call to the app.

Three lists change this for one automation, the same three an agent run has: Allow, Ask first and Deny. One call per line, as the agent names it; a trailing * covers a whole server (mcp__jira__*).

Slate's rules hook holds these rules, as it does for an agent run. They apply when the automation's agent is connected in Connect with Slate's hooks on. Without the hooks the tool is not held, and Setup says so.

When it asks first

When a run tries a call that asks first, the call is held and the run carries on, saying what it wanted to do. When the run ends, the held call waits as an Ask first card ("Standup's rules held a call: …") in the thread under that run, and on Home.

Yes, do it starts one short run that may make exactly that call; the card then says how it went: "Done: Posted to #acme-dev." or "Not made: …". No closes it. Each call is answered once. Later, on Home, sets the card aside.

What it knows

What it knows lists the memories the automation wrote and previews the memories it is given before a run, each with a pin and a keep-out. It also says what each run reads: its job, the sessions and memories of its project or group, its own last three reports, and your replies. A memory it wrote that was later replaced or retired stays listed, crossed out.

Recent tasks

The first step can be Recent tasks. Before it writes anything, Slate gathers what happened and checks it against your live tools. Only the first step can be one, because later steps read its report.

Context Recent tasks sees

SourceWhat it brings in
SessionsUp to 80 of the newest captured AI sessions in the look-back window, each tagged with its group or project. Each shows its summary on one line, cut at 280 characters
MemoriesUp to 30 memories, picked by pin, recent use and kind, not by date. Each has its kind (decision / preference / state / fact / lesson), its ref and its reasoning. The list stops at about 5,600 characters. A memory whose cited code changed is left out. An automation scoped to a group or project reads that doc's own memory, and a group's includes its projects', plus global.
DocsThe titles of up to 100 docs, newest change first, in the automation's group or project
Prior runsThis automation's own three most recent reports, so it can build on what it already said. Each shows the opening 600 characters

Look back sets how many days of sessions it reads, 1 to 365, starting at 7. Write decisions back to memory lets the report end with a memories block that Slate saves as memory (at most five per run) and removes from the report you read. With the same switch, a memory-proposals block proposes merges and retirements of the memories it was shown, by ref. Each waits in Memory under Needs review until you accept it. Only an automation scoped to a group or project can file one.

Recent tasks can also search the workspace and your connected tools. What it may change is set by the automation's rules: see What it may do.

Grounding on your live tools

Slate's own record shows what was true when written. A ticket that has since moved is invisible to it, so before Recent tasks writes, it checks the world.

Each captured session records its directory and the CLI config it ran under. Slate takes the distinct working contexts from the period's sessions, leaves out folders under /tmp and similar, ranks the rest (real git checkouts first, then by work done) and takes the top three. The run names the others as skipped. For each, one short pass runs in turn with the agent started in that directory under that config, so your project-scoped MCP servers (Jira, GitHub, Slack) load. Each pass works through four steps:

  1. Jira or Linear: issues assigned to you and not Done. This decides what counts as your work.
  2. GitHub: your pull requests for those tickets, with state, CI result and who the review waits on.
  3. Calendar: today's meetings. Skipped when Slate has already read your calendar.
  4. Slack: who is waiting on what, for those tickets and pull requests, in the last three days.

A pass asks only for identifiers, states, names and times. Ticket bodies, comments and message text are never requested or stored.

A Recent tasks report opens with three columns: Assigned to me, Pull requests and Today's meetings. A column whose source needs signing in says so and has a sign-in button, which signs in against the same account and directory the pass used and runs the automation again. A column whose source could not be reached says that, never "Nothing assigned".

The report text then lists what was verified this run and which sources could not be reached. A source is unreachable when the agent said so, or when its CLI reported the server as failed, pending, unknown or needing sign-in. When no project had sessions in the look-back window, nothing is checked and the report says so. Recent tasks may state a ticket or PR status as current only if a tool returned it this run. The seeded Standup and Shutdown end with a Not verified section; a gallery template adds none unless its prompt does.

Where an automation works

An automation runs in its group's or project's directory: the checkout Slate watches for it, or the folder if there is no checkout. That loads your project-scoped MCP servers for every step. The directory is fixed once per run, so editing a group or project mid-run cannot split an automation across two. An automation with no group or project does not run by itself; Automations says so above Run now, which asks you to choose a project first.

A background run costs the same model calls as running the prompts yourself, and nobody watches it, so three limits apply. A whole run shares one spend ceiling of $5; each turn gets what is left, and no turn starts once nothing is left. A tool that does not report spend cannot be added up, so its run is limited to 12 turns. Claude Code is also limited to 30 agent turns inside each turn; other tools have no such flag. A step gives up after four minutes of silence; every word, tool call or result restarts that clock.

The ceremonies

Slate seeds six automations, each a single Recent tasks step, organized by project. All arrive switched off and with no project. Run now or Turn on asks which project, saves it and goes on. Then switch one on to run it on its schedule.

AutomationStartsLooks backWhat it produces
Standupdaily, 07:003 daysWhere each project stands and today's focus
Shutdowndaily, 18:001 dayWhat moved today, loose ends, and tomorrow's first move
Planningweekly, Monday 08:007 daysWhat to commit to for the week ahead, per project
Weekly reviewweekly, Friday 17:007 daysWhat shipped, what's in flight, what's blocked
Retroweekly, Friday 17:007 daysWhat went well, what dragged, one concrete change
Monthly reviewmonthly, day 1, 09:0030 daysTrajectory, the decisions that mattered, one thing to change

Standup, Shutdown, Weekly review and Retro also write decisions back to memory, up to five a run. Planning and Monthly review do not. None skips a late run.

Each is an ordinary automation: change its time, scope it to one project, or add a step after Recent tasks ("turn this into three Slack-ready bullets").

The memory pass

Memory pass is a template that keeps memory small and true. It runs daily at 08:30, reads yesterday's sessions and the group's or project's memories, adds at most five new ones (a correction you made, an approach you confirmed, a decision and why) and proposes merges and retirements for review. Nothing runs until you save it, scoped to a group or project, and switch it on. It runs on its agent under the account you already gave that tool.

The Memory care automation

Turning on AI memory care in Memory adds an automation, Memory care, to Automations. It runs daily at 03:00, skips a night it missed, and has one step that reads the night's memories twice. Its switch, cost and monthly token cap are in Built-in. It follows Scheduled automations too.

The Automations place

Automations opens on its Overview. Latest shows the newest report from each automation plus a live card for any run in progress. History holds every report, grouped by automation, newest first. Its find box narrows by automation name, a word in a report's title or opening lines, or a date ("Oct 8" or "2026-10-08"); every word you type must match. A renamed automation keeps its history under its new name. A report opens only when you pick one. If reports cannot be read, Overview says so with Try again; No reports yet appears only when there are none.

Under Overview is Built-in: what Slate itself runs, each with its switch (address /loop?view=built-in). It was a Settings tab until 2026-11-06. See Built-in automations.

Below Built-in are your own automations, grouped by what starts them: Running, On a schedule, When a session ends, When a task arrives and By hand. Pick one for three tabs: Thread, Setup (job, start, where it works, what it may do, steps) and What it knows. Run now, Edit and the on/off switch sit above them. Edit opens the editor; Overview returns to the first screen.

A report goes for good rather than to Trash: Delete forever… asks once ("Delete forever?"), and the automation can run again. Deleting an automation forever keeps its reports.

⌘K searches reports too, through their own index over title and body, listed under Reports (at most four), then Artifacts.

The report finds you

When a run finishes, a native OS notification carries the report's opening line, cut at 180 characters, and Slate shows a Report ready toast with the title. A failed run shows an Automation failed toast, and the error stays under Last run. When your agent's own sign-in lapses, you get one notification, on the first run that fails that way. A report opens in Automations, beside earlier runs, wherever you open it from.
